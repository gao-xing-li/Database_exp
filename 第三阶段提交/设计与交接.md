# B 库存设计、接口与交接

2026-11-26。按[第 10–13 周共同决策](../10-13周小组分工/问题决策.md)实现库存线。第 13 周沿用分工计划的默认排班，A 负责双会话实验，B 整理阶段交付和报告。

## 实现决定

| 项目 | 本轮采用的做法与理由 |
|---|---|
| 运行基线 | 从本地 v1.0 阶段基线 `e2225bf` 的脚本新建 `AnimeGoodsStoreDB_Week6App_Stage3`。新库与原演示库分别使用自己的登录和配置。新增库存对象放在第三阶段，应用根据配置选择入口。 |
| 手工库存调整 | `AdjustInventory(product_id, delta, reason, employee_id, reorder_point)` 一次写入数量及可选警戒值。调整量为零时拒绝，警戒值仍可以用 `SetInventoryReorderPoint` 单独更新。历史商品缺库存行时先在事务内建立零库存。Web 员工取登录绑定。 |
| 补货量 | `RestockQuantity(product_id, target_qty)` 计算 `max(目标 − (在手 − 预留), 0)`。目标传 `NULL` 或 `DEFAULT` 时用警戒值。达到警戒值返回 0，未知商品或负目标返回 `NULL`。有商品、缺库存行时按可售 0 和默认警戒值 0 算。建议量供查看，验收数量来自实际补货单。 |
| 审计粒度 | 同一写入语句中，每件在手量或预留量实际变动的商品记一条。分别保留前后在手量、前后预留量和差额。数量未变的警戒值维护及零库存建档不增加流水。 |
| 调整记录 | 每次手工调整分配一个 `InventoryAdjustmentSeq` 编号，流水中的 `source_id` 即该编号。流水同时保存原因和员工，作为调整记录。序列允许因回滚产生空号。 |
| 直接库存 DML | 无业务来源的直接 SQL 增删改记为 `DIRECT`，来源和员工为空，以 `sql_login` 保留连接身份。流水中的商品内部编号保留历史，即使此后移除商品资料仍能查到。 |
| 补货验收 | 只收 `RESTOCK`、`ORDERED` 且明细未入库的单据，整单按人工填好的 `ordered_qty` 入库，逐项置 `received_qty = ordered_qty`，同时写验收人、时间和 `RECEIVED`。同一单据的状态锁串行化重复验收。 |
| 加锁顺序 | 按商品内部编号升序逐项锁定商品及其库存行。单商品内先锁 `Product` 再锁 `Inventory`，与 v1.0 Web 商品维护和结账的既有顺序一致。整单验收先锁本单表头和明细。 |
| 分类层级 | 在现有 `ProductCategory` 增加可空自引用父级。旧分类起初都是根节点。子树结果带起点、深度、编号路径，叶子返回自身，未知编号返回空行集。查询用路径跳过已访问编号，并设置 100 层上限。 |

## 销售侧调用合同

库存触发器读取当前 SQL 会话的 `inventory_audit` 上下文。销售过程在同一连接、同一业务事务中，于首次库存变动前传入类型、实际操作员工和内部订单编号。业务处理结束或出错时清理。Web 过渡结账已经传入员工和订单。A 合并 SQL 结账时由 SQL 过程负责上下文及事务，替换过渡调用。

```sql
EXEC dbo.SetInventoryAuditContext
    @business_type = 'SALE', @employee_id = @employee_id, @source_id = @order_id;
-- 在同一事务中完成已通过检查的库存扣减。
EXEC dbo.SetInventoryAuditContext;
```

| 类型 | `source_id` | 人员与原因 |
|---|---|---|
| `SALE` | `SalesOrder.order_id`，可关联查询 `order_no` | 实际执行结账的登录员工 |
| `RESTOCK` | `PurchaseOrder.purchase_id`，可关联查询 `purchase_no` | 入库员工 |
| `ADJUSTMENT` | 调整流水的序列编号 | 调整员工及非空原因 |
| `DIRECT` | 空 | 数据库连接登录名 |

多商品扣库在准备更新订单状态之前，先按商品编号取得一致的锁。订单规则触发器按共同决策在扣库前检查可售量。最终扣减语句仍带可售数量条件。库存流水表由触发器在原事务中写入，事务回滚也撤回该次流水。连接上下文随会话保存，调用方需要显式清理。 [Microsoft Learn](https://learn.microsoft.com/en-us/SQL/relational-databases/system-stored-procedures/sp-set-session-context-transact-sql?view=sql-server-2017)

```sql
SELECT product_id, employee_id, source_id, reason, before_on_hand, after_on_hand, on_hand_delta
FROM dbo.InventoryAudit
WHERE business_type = 'SALE' AND source_id = @order_id
ORDER BY product_id, audit_id;
```

先清理所有演示会话事务，再运行 [B 基线](测试/baseline.sql)和 A 的订单基线。B1 脚本在外层事务内执行真实验收过程并停在提交之前。独立调用时过程自行提交。显式外层事务调用时过程只设保存点，外层会话决定最终提交或回滚。若错误使外层事务变为无法提交，外层会话须完整回滚。 [Microsoft Learn](https://learn.microsoft.com/en-us/sql/t-sql/language-elements/save-transaction-transact-sql?view=sql-server-2017)

| 场景 | 观察点与验收预期 |
|---|---|
| 订单持有 P，补货请求 P | A 完成 P × 2 后保持事务，B 的 P × 5 等待。A 提交时最终 P=13，A 回滚时最终 P=15。两种情况都对照表头、明细和流水。 |
| 补货写入后保留事务 | B1 内可读到 P=15。另一会话按隔离级别观察。B2 回滚后 P=10，补货单回到 `ORDERED`，本次流水为零。 |
| 统一加锁顺序 | P/Q 反向加锁由第 13 周实验脚本构造。复验正式业务过程时两侧均先锁 P 再锁 Q，核对实测是否由循环等待转为普通等待。 |
| 两笔订单各买 6 件 | 从 P=10 开始，一单成功；另一单库存不足，P=4。订单过程和正式结果随 A 的交付合入。 |
