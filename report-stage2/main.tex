\section{实验目标与阶段安排}
\subsection{从关系数据库到可操作应用}
第一阶段已经在SQL Server中建立了商品，库存和订单等数据。第5--9周继续把这些记录连成实际业务，先检查表结构怎样表达店铺规则，再补齐约束和操作流程，最后通过网页完成销售，并到数据库核对结果。



\subsection{总体思路与实现范围}
这次设计从已有业务结构出发。ER检查先把商品，订单和人员之间的关系整理清楚，函数依赖分析再判断字段为什么这样保存。第六周据此保留15张业务表和96个字段，将迁移集中在三项采购约束上，应用开发便可以沿用这些对象继续组织操作。

应用选择现货销售作为完整流程，商品建档后入库，店员登记商品与数量，确认结账，顾客再查询本人订单。围绕这笔销售，商品资料和库存数量分开维护，登记单价保留顾客确认的价格，库存扣减与订单完成放在同一事务中。页面再按店长，店员，库存员和顾客的职责安排入口，每个角色看到的内容对应自己的工作。

网页登录通过新增的 \code{WebUser} 表绑定员工或会员，另加两个编号序列，五类受限数据库身份和顾客订单行级过滤。这样既能承接原有业务资料，也能确定操作由谁发起。原有预售和采购数据继续保留，履约与验收界面留待后续扩展。

\subsection{实验环境}
应用使用Python 3.12和Flask，通过pymssql连接SQL Server，运行环境由Conda管理。实验另建 \code{AnimeGoodsStoreDB_Week6App}，依次装入基础数据，迁移和应用安全结构。后面的操作主要在网页完成，SSMS用来核对同一笔业务实际保存了什么。

\section{第5周 ER 模型与业务规则检查}
\subsection{实体划分与联系表达}
这次ER建模从已经存在的15张表往回检查，先确认每张表表示的业务对象，再看对象之间怎样联系。商品类别，IP和人员资料可以独立存在，一笔订单则通过明细记录所购商品。这些联系既给出了连线的依据，也为后面检查唯一性，参与约束和业务状态提供了线索。

\Needspace{0.68\textheight}
\subsection{商品与库存的基数和参与约束}
群像商品主要对应一部作品，具体角色商品则可以同时登记作品和角色，所以IP与角色按商品情况填写。填入角色时，组合外码会核对它所属的IP，两项资料因此保持一致。每件商品还须归属一个类别，供目录分类和查询使用。

库存以 \code{product_id} 同时作为主码和外码，所以一件商品至多对应一条当前库存。原结构允许商品已经建档而库存行尚未建立，网页中再遇到这种情况，就要区分没有库存记录与库存为零。应用因此在新增商品的同一事务里补建零库存行，后续入库便能从明确的零开始。

\shot[0.57\textheight]{er-product.png}{商品与库存模块 ER 图}{fig:erproduct}

图中用最小和最大次数标记参与联系的范围，下划线标记主码，AK辅助标记候选码，问号和斜线分别表示可空与派生属性。可售数量由实际库存减去预留量得到，查询时计算，库存变化后就能按同一口径得到当前可售量。

\medskip
\Needspace{0.68\textheight}
\subsection{销售订单与人员联系}
销售订单先记录收银员工，购买者可以是会员，也可以是散客。具体商品放在明细中，以 \code{order_id, product_id} 共同定位一行。同一商品再次加入同一订单时，修改这一行的数量即可。数量和登记单价共同描述这笔订单中的购买情况，因此由订单与商品一起确定。

订单与明细的关系还要结合状态理解。创建草稿时允许暂时没有商品，结账则要求至少一条明细。外码负责维持明细与订单的关联，结账检查接着核对订单状态和内容，成功后再将明细转为只读。这几项检查分别对应建单，编辑和完成的不同阶段。

\shot[0.57\textheight]{er-sales.png}{销售，明细与人员模块 ER 图}{fig:ersales}

订单中的收银员工还要与登录身份对应。业务角色表保存员工职责，网页登录后核对员工的启用状态和账户绑定职责，收银操作再沿用这个身份，订单中便能留下实际经办者。

\medskip
\Needspace{0.72\textheight}
\subsection{预售与采购规则及原结构问题}
会员取消预订后还可能重新预订，这两次记录需要分别保留。因此预订使用各自的编号标识，同一活动与会员的组合可以重复，不能直接作为候选码。提货再核对原会员和商品，一条预订最多形成一笔提货订单，使后续交易能够追溯到原来的预订。

采购采用一场预售最多一张采购单的约定，普通补货单的活动编号为空。检查原结构时，发现同活动多单和补货关联活动等记录仍可能通过已有约束，因此将这些差异整理出来，分别确定后续处理的位置。

\Needspace{0.50\textheight}
\subsection{规范化示例与分解性质}
为了说明现有商品表与类别表为什么分开，先在理论上把它们合成一个关系。
\[
R(\mathit{product\_id},\mathit{product\_name},\mathit{category\_id},\mathit{category\_name})
\]
商品ID决定商品名与类别ID，类别ID又决定类别名。如果每件商品都带着一份类别名称，改一次类别名就要改多行。还没有商品的类别难以单独插入，最后一件商品被删除时，类别本身也可能跟着丢失，更新异常便由这种重复保存产生。

把商品资料与类别资料分开以后，得到下面两个关系。
\begin{align*}
R_1 &= (\mathit{product\_id},\mathit{product\_name},\mathit{category\_id}) \\
R_2 &= (\mathit{category\_id},\mathit{category\_name})
\end{align*}
两个关系共有类别ID，类别ID能够决定 \(R_2\) 的全部属性，所以按类别ID连接时，可以把商品与所属类别重新对应起来，这个分解是无损的。原来的两组依赖分别留在 \(R_1\) 和 \(R_2\) 内部，检查可以在各自关系中完成，因此依赖也得到保持。

这个合并关系用于解释现有结构的分解性质。原库中的商品和类别已经分开，规范化检查支持继续保留这部分设计，第六周的实际迁移集中处理采购约束中发现的问题。

\subsection{保留字段的设计理由}
\textbf{商品同时保留IP和具体角色。} 群像商品通过IP表示所属作品，具体角色商品再填写角色，两个字段因此有各自的用途。在角色非空的记录中，角色ID也能决定IP，这就带来了一份重复信息。角色ID不是商品表超码，IP也不是主属性，这部分条件依赖不满足严格第三范式。保留这两个字段能够覆盖上述商品情况，组合外码负责核对角色归属，维护这份冗余是相应的代价。

\textbf{保留历史值，派生值尽量查询计算。} 目录价描述商品当前的售价，明细单价记录这笔购买确认的价格。把登记单价保存在订单中，目录以后调价时，历史交易仍有原来的依据。订单总额由明细数量乘单价求和，可售量由实际库存减预留量得到，这两项随查询计算，维护时只需保证来源记录和计算口径一致。

\medskip
\Needspace{0.74\textheight}
\subsection{需求快照与到货记录}
预售需求也有类似的时点区别。采购决策时保存一份需求快照，之后的取消或重订改变当前需求，当时的决策依据仍能留下。计划采购量还会结合已有库存等情况确定，因此作为经营决定单独保存，需求快照和额外备货量供判断时参考。

订金实收和退款额按实际收付保留。当前设计将它们作为已经发生的金额记录，保留原值能够追溯收付情况。若以后建立实收额始终等于数量乘固定订金单价的规则，再依据这项规则分析可计算冗余。

\code{received_qty} 保留实际记录的到货量，现有约束将它限定在零到采购量之间。整单状态与每行到货量的联动仍待完成，保留字段可以继续表达当前的收货情况。若后续实现严格的整单收货，再结合完整流程判断到货量是否能够由状态和采购量推导。

\begin{table}[H]\centering\small
\begin{tabularx}{\textwidth}{P{3.4cm}Y P{3.2cm}}
\toprule 选择 & 采用理由 & 还需保证什么 \\
\midrule
保留商品IP与角色 & 支持群像商品及角色商品的不同表达。 & 校验角色归属IP，避免不匹配。 \\
保留明细成交价 & 保存交易历史，允许之后调整商品售价。 & 登记时保存目录标价，结账沿用，完成后禁止修改。 \\
查询计算总额与可售量 & 数值由现有记录确定，避免重复维护。 & 查询与页面使用一致计算口径。 \\

\end{tabularx}\caption{结构保留与受控冗余的取舍}

这些取舍使15张业务表继续保留，实际调整集中在采购规则上。规范化分析在这里帮助区分了独立资料，历史事实和派生值，也说明了每份冗余的用途及维护责任。

\section{迁移方案与回归结果}
\subsection{三项结构调整及执行顺序}
先留一份未迁移的基线，再在相同数据的副本上执行调整，后面才能对照变化。脚本检查旧结构与冲突记录，满足前提后才在一个事务中建立索引和替换CHECK，冲突时列出记录并停止，保留原数据供核对。

\begin{lstlisting}[language=SQL]
CREATE UNIQUE INDEX UX_PurchaseOrder_PresaleID
ON dbo.PurchaseOrder(presale_id)
WHERE presale_id IS NOT NULL;

ALTER TABLE dbo.PurchaseOrder WITH CHECK
ADD CONSTRAINT CK_PurchaseOrder_TypePresale CHECK
((purchase_type='PRESALE' AND presale_id IS NOT NULL)
 OR (purchase_type='RESTOCK' AND presale_id IS NULL));

ALTER TABLE dbo.PurchaseOrder WITH CHECK
ADD CONSTRAINT CK_PurchaseOrder_Status CHECK
(purchase_status IN ('CREATED','ORDERED','RECEIVED','CANCELLED'));
\end{lstlisting}

普通补货没有活动编号，唯一索引因此只检查非空的 \code{presale_id}，多张补货单仍可保存。已取消的采购单也受它限制，所以同一活动最多一张采购记录，取消后另建采购单仍会被拒绝。旧约束移除与回滚由完整迁移脚本处理。

采购类型与活动编号要成对检查，预售采购关联活动，普通补货的活动编号为空，两种记录各有明确条件。状态域同时移除部分到货，落实整单到货的状态约定。明细到货量与整单状态的同步则留待验收流程继续处理。

建立约束时使用 \code{WITH CHECK} 检查既有行，脚本同时启用 \code{XACT_ABORT} 和筛选索引所需选项。旧结构不符或已迁移过时就停止，避免在错误前提下改表。

\subsection{冲突处理与实际调试}

\subsection{查询与写入的执行过程}
以搜索商品为例，页面将输入的名称或编号交给Flask路由，后端确认登录身份和搜索词长度，再让Repository查询商品与库存。查询结果返回后刷新表格，SQL和参数绑定统一放在数据访问层，后续写入也沿用这条调用路径。

\begin{lstlisting}[language=Python]
# services.py
with self.connection(user) as repo:
    return repo.products("%" + term + "%", user["role"] in STAFF)
\end{lstlisting}
\begin{lstlisting}[language=SQL]
-- repository.py 中查询的参数绑定形式
WHERE (p.product_name LIKE %s OR p.product_code LIKE %s)
\end{lstlisting}
百分号和搜索词拼成LIKE的参数值，SQL语句本身保持固定。输入中的引号也按参数内容处理。商品名，数量和价格等写入值采用同样的参数绑定方式，数据访问层统一管理语句与输入。

新增商品比查询多了一层需要一起完成的修改。资料通过编号，类别，角色归属和价格检查后，商品与零库存行要在同一事务里保存，失败时一起撤销。删除则要再看库存和历史引用，已经参与交易的商品用停售保留记录，避免历史订单失去原来的商品关联。

库存调整先根据增减量算出实际量，再检查它至少能够覆盖预留量，警戒值也在这一步保存。草稿登记时核对会员，商品，数量和页面标价，结账继续检查当前身份与订单状态。写入成功后重新查询结果，页面显示的便是数据库实际保存的状态。

这些操作的失败也由后端统一接收并转为页面提示。数量不足时保留草稿，店员可以调整后重试，连接失败则提示暂时不可用。响应与日志共用请求编号，后端另外保存异常细节，页面只显示当前需要采取的处理。

\subsection{草稿与结账的事务边界}
订单先存为 \code{CREATED} 草稿，供店员调整会员和数量，库存留到结账时扣减。原实现会在改数量和结账时取最新售价，按线下销售场景重新核对后，将价格确定的时点放在首次登记。顾客先看目录标价再决定购买，登记时核对页面价格并保存单价，后续刷新，改数量和结账都沿用它，确认金额便能对应到最终记录。若首次登记时页面标价已过期，就提示刷新核对并拒绝本次写入。结账成功后转为 \code{COMPLETED}，保存成交内容。

结账先锁定订单，确认它仍处于草稿状态，会员有效且已经有明细，再按商品ID顺序检查在售状态与可售库存。所有明细共用一个事务，库存扣减和订单完成一起提交。这样遇到后续商品不足时，前面已执行的修改仍在同一事务中，可以随整单撤销。

\begin{lstlisting}[language=SQL]
UPDATE dbo.Inventory
SET on_hand_qty = on_hand_qty - %s,
    updated_at = SYSDATETIME()
WHERE product_id = %s
  AND on_hand_qty - reserved_qty >= %s;
\end{lstlisting}

库存是否足够也放进UPDATE的条件里，只有可售量满足数量时才扣减，再根据影响行数判断结果。这样读取库存以后即使还有其他订单参与竞争，写入时仍会重新受这个条件限制。商品锁按固定顺序取得，配合事务处理并发争用。

\begin{lstlisting}[language=Python]
# db.py 中事务管理的核心结构
try:
    # connection 已建立，cursor 已设置所需 SET 选项
    yield Repository(cursor)
    connection.commit()
except BaseException:
    connection.rollback()
    raise
finally:
    connection.close()
\end{lstlisting}

这段事务管理把整笔销售作为提交单位。业务拒绝，约束错误和执行异常都进入回滚路径，已执行的库存扣减一并撤销，订单继续保持草稿和登记价格。成功时统一提交，最后关闭连接，调用者只需围绕完整操作处理结果。

并发用例设置实际库存3件，预留1件，让两个订单各买2件。结果一笔成功，另一笔返回库存不足，最终实际库存与预留量均为1，恰好保留了预留的数量。该用例检查了两笔订单争用可售库存的情况，更大并发规模下的表现仍待压力测试。

\subsection{小组分工与辅助过程}
郑立峰负责第5--6周的ER模型，规则检查，依赖与范式分析，以及采购约束迁移和回归材料。李维政在这个结构上完成第7--9周应用，连接数据库，区分角色操作，处理结账事务与异常，并进行集成测试和本机流程截图，再将各周结果整理进报告。最终提交前仍需共同核对图，代码和实际结果是否一致。

\subsection{实验认识与当前不足}
这一阶段的设计逐渐围绕完整业务展开。ER图说明对象怎样关联，依赖分析说明字段承担什么含义，应用再把它们组织成能够执行的一次操作。唯一性和类型关联交给数据库约束，订单状态，人员职责和库存则在结账中联合检查，各部分顺着同一条业务流程接起来。

价格规则的修改使这种衔接更具体了。目录维护当前售价，明细保存登记时确认的价格，首次加入草稿时核对两者，之后按记录下来的价格结账。每份数据都有明确的用途和生效时点，保留历史单价的理由也从字段定义落到了实际收银过程。

库存失败案例进一步说明了验证应围绕整笔操作安排。第一件足够，第二件不足，回滚后两件库存都回到原值，测试因此观察到了前后修改怎样一起撤销。迁移前后对照，成功销售和失败回滚分别提供了不同侧面的依据，结论也随实际核对的范围确定。

现货流程目前已有页面，数据库记录和测试结果相互对应。后续扩展预售履约与采购验收时，还需把到货数量，整单状态和库存变化组织成完整操作，并补充相应的成功与失败验证。这部分继续作为当前实现的后续工作。
