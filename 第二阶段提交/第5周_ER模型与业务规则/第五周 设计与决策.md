## 三、已确认的业务决策

| 编号 | 事项 | 最终决策 | 理由与适用范围 |
| --- | --- | --- | --- |
| D01 | 经营规模与范围 | 保持单门店线下经营，现货销售为主、会员预售为辅 | 继续聚焦商品、销售、预售、采购和库存，不引入多门店、物流、普通售后退换货等额外业务 |
| D02 | 商品与 IP、角色 | 一个商品最多属于一个 IP、对应一个具体角色；两者可按业务为空 | 保留第一阶段简化；群像商品允许只有 IP，不增加多 IP、多角色中间表 |
| D03 | 商品销售方式 | 商品不固定划分为现货商品或预售商品，通过活动和订单表达不同销售方式 | 同一种商品可以先预售，到货后的剩余数量再作为现货销售 |
| D04 | 同商品销售明细 | 同一订单中的同一种商品合并为一条明细，不考虑同一订单内同商品不同成交价 | 保留 `(order_id, product_id)` 联合主键；购买多件通过数量表达 |
| D05 | 订单明细与历史内容 | 创建中的销售订单可暂时没有明细；完成结账前必须至少存在一条明细；完成后固定交易内容，不支持修改或删除来撤销交易 | 说明订单的业务含义与历史保存要求；当前尚未完整强制，不在第五周展开状态机或实现方案 |
| D06 | 预订处理粒度 | 一条预订整体取消或整体提货；最多形成一笔预售提货销售订单 | 不支持部分取消、部分提货或多条预订合并结账 |
| D07 | 同活动采购数量 | 一个预售活动最多对应一张采购订单 | 未采购时为零张，形成采购后为一张；不支持针对同一活动拆成多张单或追加第二张单 |
| D08 | 采购供应商 | 每张采购订单只向一家供应商采购 | 订单头保存一个供应商，订单内商品均来自该供应商；现有结构已经满足 |
| D09 | 到货与验收粒度 | 每张采购订单一次完整到货、统一验收，不支持分批到货 | 简化采购执行和库存联动；不新增分批到货、验收批次实体 |
| D10 | 商品资料与库存建立 | 商品资料在开展预售或创建采购订单前建立；首次到货验收入库时必须建立或更新库存记录 | 预售、采购均需引用已有商品；商品资料与库存不要求同时建立，已有库存的再次到货只更新库存 |
| D11 | 库存与金额保存 | 保留实际库存、预留库存；可售库存和订单总金额实时计算 | 减少可直接计算的数据重复保存，继续使用统一库存结构 |
| D12 | 历史事实保存 | 保留历史成交单价、采购决策时的需求快照及实际订金记录 | 当前售价、实时需求与历史事实含义不同；调价或取消预订后仍需解释过去的交易与决策 |
| D13 | 绘图表示法 | 采用教材的 ER 表示法：矩形实体、框内属性、主码下划线、联系菱形、最小/最大基数 | 此前将“接近 UML”理解为普通 UML 类图，现予以纠正；全图与局部图统一，基数按本端实体参与联系的次数读取 |

D07、D09 是本次明确收紧的业务规则。v0.1 尚允许同活动多张采购单，并保留部分到货的状态和数量表达能力，两者必须列入差异清单。

“积极建立商品资料与库存”按业务先后落实：商品资料可在到货前建立；首次验收入库时必须确保库存记录存在。没有库存记录表示尚未建立库存状态，不应直接解释为库存数量为零。

## 四、实体、属性与标识的整理方案

### 4.1 实体范围与一行数据的含义

以现有 15 张表作为核查起点，逐项说明其是否需要独立保存，以及它承载的是业务对象、当前状态还是业务事件。

| 实体 | 对应表 | 一行数据代表什么 | 主要标识 |
| --- | --- | --- | --- |
| 商品类别 | `ProductCategory` | 一种商品分类 | `category_id` |
| 作品或 IP | `AnimeIP` | 一个作品或 IP | `ip_id` |
| 作品角色 | `CharacterInfo` | 属于某个 IP 的一个具体角色 | `character_id` |
| 商品 | `Product` | 一种独立管理的商品款式 | `product_id` |
| 当前库存 | `Inventory` | 单门店中某商品的一条当前库存状态 | `product_id`，同时引用商品 |
| 会员 | `Member` | 一名注册会员 | `member_id` |
| 员工业务角色 | `BusinessRole` | 一种店铺经营职责 | `role_id` |
| 员工 | `Employee` | 一名员工及其当前业务角色 | `employee_id` |
| 供应商 | `Supplier` | 一家供应商 | `supplier_id` |
| 销售订单 | `SalesOrder` | 一笔现货销售或独立预售提货交易的订单 | `order_id` |
| 销售订单明细 | `SalesOrderItem` | 一张订单中一种商品的购买数量和成交单价 | `(order_id, product_id)` |
| 预售活动 | `PresaleActivity` | 围绕一种商品开展的一次预售活动 | `presale_id` |
| 预订记录 | `PresaleReservation` | 一名会员参加一场活动的一次预订事件 | `reservation_id` |
| 采购订单 | `PurchaseOrder` | 一次向一家供应商采购并整批到货的订单 | `purchase_id` |
| 采购订单明细 | `PurchaseOrderItem` | 一张采购订单中一种商品的数量、成本和验收数量 | `(purchase_id, product_id)` |

实体分析将列出主要属性、业务含义、主标识、其他候选标识及必要的可空条件。图中属性名应能对应数据字典，不必重复 SQL Server 的全部物理类型、默认值和约束定义。

### 4.2 需要重点解释的对象

1. **订单明细与采购明细**：承载订单和商品之间的多对多联系，数量、成交价或成本属于这次交易中的商品记录，不能只画一条无属性的多对多关联。
2. **预订记录**：有独立的业务编号、订金、状态和取消信息，属于需要保存历史的预订事件。同一会员可以在同一活动中取消后重新预订，因此不能用 `(presale_id, member_id)` 唯一标识一次预订。
3. **库存**：依靠商品标识存在，但保存当前实际数量、预留数量、警戒值和更新时间，保留独立维护有明确用途。
4. **员工业务角色**：记录经营职责；SQL Server 数据库角色用于访问控制，不作为同一个业务实体混画。

### 4.3 标识分析原则

- 主码也是候选码；除主码外，继续分析商品业务编号、订单业务编号、会员编号和电话等其他候选码。
- `CharacterInfo` 的 `(ip_id, character_name)` 是业务候选码。
- `(character_id, ip_id)` 包含已有主码，属于支持复合引用的辅助唯一约束，不是新的最小候选码。
- `PresaleReservation` 的 `(reservation_id, member_id)` 同样是辅助唯一约束，不另算候选码。
- `SalesOrder.reservation_id` 的过滤唯一索引表达非空关联的条件唯一性，不作为整张销售订单表的普通候选码。
- 联合主键不仅是技术选择，还表达业务限制。销售明细联合主键的保留依据是 D04；采购明细继续按现有“一张采购单中的一种商品”解释，不增加同商品多行、不同采购价等业务。

## 五、教材 ER 图的设计方案

### 5.1 表示方式

实体用矩形表示，属性列在框内，选定主码加下划线；联系用写有 R 编号和业务名称的菱形表示。其他候选码保留 AK 标签作为本项目的辅助说明，含义在图例中明确。

统一采用教材的最小/最大基数记法：`0..1`、`1..1`、`0..*`、`1..*`。基数写在实体与联系之间，表示**该端每个实体参与该联系的最少/最多次数**。例如类别端 `0..*`、商品端 `1..1`，表示一个类别可以有零至多个商品，每个商品必须归属一个类别。它与原 UML 端点读法不同，需要交换原图两端的数量含义，不能只增加菱形。

最小值 0 表示可选参与，1 表示必须参与；最大值 1 或 * 表达一或多，因而不再重复叠加单/双线和箭头。状态、订单类型等附加条件用 N 编号说明。数量、单价等仍由明细实体承载；本周保留从既有关系模式提取的实体范围，不另展开弱实体重构。

### 5.2 图的组织

- 一张完整总图覆盖 15 个实体及主要联系，不把多个实体合并成一个框。
- 根据总图提供商品与库存、销售、预售与采购等局部视图，方便讲解和报告排版。
- 总图、局部图、数据字典与映射清单使用同一套命名和规则。
- 交付可编辑源文件和清晰导出图，选用能够表达上述 ER 元素的绘图工具。

图表达已确认的业务模型；规则清单说明 v0.1 的落实程度。图中以差异附注标明 D07、D09 是本次收紧的要求，不能将图中的业务限制当成数据库已经实现的约束。只维护一套主模型，局部图是同一模型的阅读视图。对状态和订单类型才能决定的条件，使用附注补足，避免把有条件的最低数量画成无条件强制。

### 5.3 关键联系与参与条件

下表按文字方向解释数量，正式绘图时据此标到正确端点。

| 联系 | 一个前者对应多少后者 | 一个后者对应多少前者 | 条件或说明 |
| --- | --- | --- | --- |
| 商品类别—商品 | `0..*` | `1` | 商品必须有类别，类别可暂时没有商品 |
| IP—作品角色 | `0..*` | `1` | 每个具体角色必须属于一个 IP |
| IP—商品 | `0..*` | `0..1` | 无明确 IP 的商品可不关联 IP |
| 作品角色—商品 | `0..*` | `0..1` | 群像商品可无具体角色；指定角色时必须有匹配的 IP |
| 商品—当前库存 | `0..1` | `1` | 首次验收入库后必须有库存记录 |
| 员工业务角色—员工 | `0..*` | `1` | 当前每名员工对应一种业务角色 |
| 会员—销售订单 | `0..*` | `0..1` | 预售订单必须关联会员；现货订单允许散客 |
| 员工—销售订单 | `0..*` | `1` | 表示收银经办联系；员工存在与业务角色正确需分别分析 |
| 销售订单—销售明细 | `0..*` | `1` | 创建时允许零条，完成时至少一条；预售订单明细应匹配该次预订的唯一商品及全部数量 |
| 商品—销售明细 | `0..*` | `1` | 每条明细必须对应一个商品 |
| 商品—预售活动 | `0..*` | `1` | 同一商品可以先后开展多场预售 |
| 员工—预售活动 | `0..*` | `1` | 表示活动创建联系，创建者的店长职责另列规则 |
| 预售活动—预订记录 | `0..*` | `1` | 活动允许尚无预订 |
| 会员—预订记录 | `0..*` | `1` | 每次预订必须属于一名会员 |
| 预订记录—销售订单 | `0..1` | `0..1` | 现货订单不关联预订，预售订单必须关联一条预订；已提货状态应对应完成订单 |
| 供应商—采购订单 | `0..*` | `1` | 每张采购订单只对应一家供应商 |
| 预售活动—采购订单 | `0..1` | `0..1` | 预售采购必须关联活动；普通补货按业务不关联活动；v0.1 尚未完全落实这些限制 |
| 员工—采购订单（创建） | `0..*` | `1` | 每张采购订单必须记录创建员工 |
| 员工—采购订单（完成验收） | `0..*` | `0..1` | 完成验收时必须有验收员工，未完成时为空 |
| 采购订单—采购明细 | `0..*` | `1` | 当前结构允许零条；实际采购、完整验收应有明细，作为流程要求记录 |
| 商品—采购明细 | `0..*` | `1` | 预售采购明细还需匹配对应活动商品 |

采购订单草稿是否有明细不另扩展业务；建模保留当前创建过程的可能性，说明实际采购与验收不能以空明细完成。普通补货可包含多种商品，预售采购按对应活动的一种商品处理。

## 六、业务规则与数据库映射的整理方案

每条规则统一记录：规则编号、业务含义、联系两端最小和最大基数、适用条件、对应表与外键、当前落实方式、缺口及后续方向。

当前落实方式区分为数据库声明式约束、已有演示脚本或样例遵守、人工流程、尚未自动实现。脚本展示某次正确操作，不等于系统已经强制所有操作遵守该规则。

| 典型规则 | v0.1 当前情况 | 本周处理 |
| --- | --- | --- |
| 同订单同商品只占一条销售明细 | 联合主键已保证 | 以 D04 解释保留理由 |
| 完成销售订单至少有一条明细 | 外键未反向保证订单有明细 | 记录完成前检查要求及实现缺口 |
| 商品 IP 与具体角色一致 | 已有 CHECK 与复合外键 | 说明它们共同保证的语义，不重复画成两次业务联系 |
| 提货订单会员与预订会员一致 | 已有复合外键 | 记录已落实的身份一致性规则 |
| 一条预订最多对应一笔销售订单 | 已有非空过滤唯一索引 | 区分条件唯一性与候选码 |
| 一个活动最多一张采购单 | 尚无相应唯一性限制 | 记录新规则与迁移方向 |
| 采购订单一次完整到货 | 当前仍允许部分到货状态及数量 | 记录收紧状态、数量与验收信息的一致性要求 |
| 入库后库存记录存在且数量增加 | 采购验收与库存当前分别维护 | 记录后续入库事务职责 |
| 经办员工符合对应业务职责 | 外键只保证员工存在；数据库角色另管操作者权限 | 分开说明员工身份、业务职责与数据库授权 |
| 预售商品、数量、价格及状态匹配 | 部分已由关联保证，其余仍需跨表检查 | 衔接已有待实现规则，不声称已实现完整提货事务 |

## 七、v0.1 问题清单与保留理由

问题清单按“问题或保留事项—业务证据—影响—处理方向”编写，不以增加表数或改动数量作为成果。

| 事项 | 业务证据与影响 | 处理方向 |
| --- | --- | --- |
| 同活动多张采购单 | v0.1 的 `PurchaseOrder.presale_id` 未限制唯一，与 D07 不一致 | 第五周记录差异，第六周评估活动关联的唯一性限制 |
| 部分到货表达 | v0.1 包含 `PARTIAL_RECEIVED`，明细允许部分 `received_qty`，与 D09 不一致 | 第六周检查状态、字段与约束如何调整；本周不决定删除 `received_qty` |
| 订单完成与历史内容 | 外键无法保证完成订单有明细，现有约束也未完整固定完成后的交易内容 | 本周记录基本业务规则和缺口，后续实现，不展开状态机与权限方案 |
| 到货后库存可能遗漏 | 库存主外键只保证最多一条，不能保证商品一定存在库存；现有库存视图内连接会排除无库存记录的商品 | 首次入库流程确保建立记录；验证时区分未建记录与库存为零 |
| 普通补货活动关联不够严格 | v0.1 仅强制预售采购关联活动，普通补货仍可能填写活动 | 保留普通补货不关联活动的业务含义，第六周结合采购类型规则评估收紧 |
| 商品的 IP 与角色依赖 | 已知角色可确定 IP，但群像商品没有具体角色，仍需保存 IP | 第六周做条件和依赖分析；第五周如实建模，不直接删除 `ip_id` |
| 辅助唯一约束的术语 | 部分唯一组合包含现有主码，容易被误称为新候选码 | 第五周标识分析中澄清，无需仅为术语修改而迁移结构 |
| 历史成交价与需求快照 | 当前售价变化、预订取消不应改写历史交易与决策依据 | 保留，明确各字段的时间含义，不作为无意义重复删除 |
| 明细与预订等关联实体 | 明细含交易属性，预订含独立事件状态和历史 | 保留，解释独立保存和标识选择的理由 |

新旧模型差异首先通过问题清单说明。第六周迁移前需要核查已有数据，不能以重建清空 v0.1 代替数据迁移，也不能将“已有样例没有冲突”当成完整的迁移验证。

## 八、设计说明与验证记录的方案

### 8.1 只用代码回答适合查询的问题

第五周核心是模型与文字分析，不要求新增业务 SQL。仅保留一个短查询文件，提供课程指定三个案例的现场展示入口：

| 案例 | 复用来源 | 讲解内容 |
| --- | --- | --- |
| SO004 多商品订单 | 第四周 `vw_OrderDetail` | 订单—明细—商品，数量与历史单价 |
| SO001、SO002 散客与会员 | 第四周 `vw_OrderDetail` | 会员可选参与；用 DISTINCT 避免明细导致订单重复 |
| P003 库存 | 第四周 `vw_InventoryStatus` | 在库、预留、可售库存与阈值 |

查询只筛选既有视图，不重写第四周连接、不创建视图、不初始化数据库。前提是第一阶段已有表、视图和样例。无结果时确认实例和数据；不以空结果记作案例通过。三个结果都应结合图中对应联系进行解释。

### 8.2 结构问题通过已有材料核对

主外码、唯一性、可空性及 CHECK 直接对照第一阶段 `01_create_tables.sql`、`06_constraint.sql`；约束与权限正反例复用第四周 `06_constraint.sql`、`07_role.sql`，不重新制作同类测试；按用户要求完成的整链复跑结果记入验证记录。

同活动最多一单、整单到货、完成订单必须有明细等，写明“业务要求—现有定义—缺口—后续方向”即可。预订提货与采购关系通过图、映射清单和原始样例解释，不增加专项查询或非法写入测试。

### 8.3 验证材料的复杂度控制

交付一个简短 SQL 文件和一份人工讲解/核对记录。移除本周新增的 PowerShell 运行器、临时建库脚本、JSON 结果集及自动核对材料；无需形成独立测试框架。验证记录以最终整链实测为主，早期环境缺失仅作为历史说明。此次临时复跑工具已清理，不增加交付代码或独立测试框架。
