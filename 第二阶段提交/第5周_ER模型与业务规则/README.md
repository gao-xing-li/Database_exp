## 图的读法与讲解重点

矩形表示实体，菱形表示联系，主码属性加下划线。实体端的min..max表示**本端每个实体参与该联系的次数**：类别端0..*、商品端1..1，表示一个类别可以有多个商品，每个商品恰好属于一个类别。AK、AK1、问号、斜线和N编号的含义见图例。

订单与商品通过明细联系，数量和历史单价属于明细；现货订单可不关联会员；商品与库存分别表达资料和数量；IP/角色字段还需说明群像商品及归属一致性。Δ1、Δ2标出本周确认而v0.1尚未完整落实的采购规则，不能把图上的业务约定解释成SQL已经全部强制保证。

## 从空环境准备本周验收

环境为SQL Server与SSMS，执行者需有建库、创建表/视图/角色和模拟测试用户的权限。下面的准备工具只用Python标准库；不需要安装Flask或Web依赖。

在本目录打开PowerShell：

```powershell
python '../第1-4周_建库代码/prepare_acceptance.py' week5
```

输出为 `../验收准备.local/week5/`。打开SSMS，连接自己的实例，按顺序逐个执行以下文件。每个文件完成且没有非预期错误后再打开下一个：

| 顺序 | 生成文件 | 预期 |
| --- | --- | --- |
| 00 | `00_新建验收库.sql` | 新建 `AnimeGoodsStoreDB_Week5Review`；已存在则51200并停止 |
| 01—02 | `01_create_tables.sql`、`02_insert_sample_data.sql` | 15表及固定样例形成 |
| 03—05 | `03_crud.sql`、`04_query.sql`、`05_view.sql` | 增删改查、九组查询、四个视图可检查 |
| 06—07 | `06_constraint.sql`、`07_role.sql` | 基础约束16 PASS、权限6 PASS，0 FAIL |
| 08 | `08_第五周只读验证.sql` | 本周三个查询分别返回2、2、1行，具体值见下表 |

生成副本已将USE指向本周专用库，并正确转换原始编码。不要把原始01直接在已有业务库运行，也不要在本周库执行第6周migration.sql。只用SSMS手工准备的方法见[基础SQL说明](../第1-4周_建库代码/README.md)。

已有完整v0.1验收库时，可直接选择专用库，在新查询窗口执行本周SQL中三个SELECT；若运行完整原文件，必须先将 `USE AnimeGoodsStoreDB` 改为自己的验收库名。仅改变SSMS数据库下拉框不会覆盖文件中的USE。

## 三个现场展示与通过标准

| 展示 | 操作与预期 | 应说明的ER关系 |
| --- | --- | --- |
| 多商品订单SO004 | 查询返回P001：1×68，P004：2×28，共2条明细、3件、124元 | R09、R10，订单经明细关联商品，数量与单价属于明细 |
| 散客与会员SO001/SO002 | 返回2行，SO001会员为空，SO002对应M002 | R07，现货订单的会员参与可选，多条明细不等于多张订单 |
| 商品库存P003 | 返回1行，在库2、预留0、可售2、警戒值3、LOW_STOCK | R05、B01，可售量由在库减预留计算 |

随后对照问题清单检查原01中的采购定义：活动关联还不唯一、仍允许PARTIAL_RECEIVED，完成订单也未由明细外键保证至少一条明细。此时应能准确解释“图中已确认的规则”和“v0.1已经落实的约束”之间的差异。

原库存视图使用INNER JOIN，无库存行的商品不会显示；订单视图只显示有明细的订单。三个正确样例用于说明模型，不能单靠它们证明所有基数上限和跨表规则都已强制落实。
