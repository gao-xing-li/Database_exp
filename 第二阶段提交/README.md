# 第二阶段提交：第5—9周分阶段验收

本提交按第5周、第6周、第7—9周三个验收单元组织。每个目录都保留本阶段的设计、实现、验证材料和独立操作说明。助教可以直接选择任一阶段，从该阶段 README 开始检查和复现，无需先运行前一周的验收，也无需从最终 Web 应用反推前期成果。

[第1—4周建库代码](第1-4周_建库代码/README.md)单独放在提交根目录，作为各阶段共用的 v0.1 起点。第5周保留原结构做 ER 审查，第6周在独立副本上迁移，第7—9周从基础脚本自动建立自己的应用库，三者使用不同数据库。

## 第5周应展示的内容

本周产出是对 v0.1 的 ER 建模和设计审查。实体说明解释商品、库存、会员、员工、销售、预售与采购；规则映射区分基数、可选参与、条件约束以及数据库已落实的部分；问题清单指出同活动多张采购、部分到货、完成订单明细等差异。

现场展示用原结构的三个只读查询连接模型与样例：SO004两种商品合计124元；SO001为散客、SO002关联会员M002；P003在库2、预留0、可售2，状态为LOW_STOCK。采购规则差异仍应能在本周结构中观察到，不能提前用第6周迁移后的库替代。

交付及逐项步骤见[第5周说明](第5周_ER模型与业务规则/README.md)，已有实测见[第五周验证记录](第5周_ER模型与业务规则/05_验证记录.md)。

## 第6周应展示的内容

本周逐表分析候选码、函数依赖、更新异常与范式，给出独立教学关系的无损连接和依赖保持论证，并解释业务模式为何保留15表及96字段。IP/角色归属、历史成交价与需求快照等字段各有保留理由，订单金额与可售量通过查询计算。

实际迁移落实三项采购限制：非空预售活动关联唯一；PRESALE必须关联活动、RESTOCK不得关联活动；采购状态域移除PARTIAL_RECEIVED。迁移保留业务表和原数据，回归比较全部列、查询、元数据及权限，同时检查合法写入与非法写入。到货数量与整单状态联动、验收入库事务尚未实现。

交付、两个新库的建立方式与执行顺序见[第6周说明](第6周_函数依赖规范化与迁移/README.md)，已有45项回归与冲突证据见[迁移与回归记录](第6周_函数依赖规范化与迁移/03_迁移与回归验证记录.md)。

## 环境与数据库分开准备

SQL部分使用 Microsoft SQL Server 和 SSMS，执行者需要建库、创建对象、授权和模拟测试用户的权限。基础00—05为GB18030，06—07及新增文件为UTF-8；验收准备工具会生成统一UTF-8执行副本，保留原文件字节。具体步骤均写在对应阶段 README。

| 用途 | 专用数据库 | 初始化后应处于什么状态 |
| --- | --- | --- |
| 第5周 | `AnimeGoodsStoreDB_Week5Review` | 完整v0.1，含样例、视图、原约束和角色；不执行迁移 |
| 第6周对照 | `AnimeGoodsStoreDB_Week6Baseline` | 完整v0.1，后续仅作对照 |
| 第6周目标 | `AnimeGoodsStoreDB_Week6Target` | 从Baseline逐列复制数据后执行本周迁移；再执行回归 |
| 第7—9周 | `AnimeGoodsStoreDB_Week6App` | 基础01—07、第6周迁移、Web认证/角色/RLS、序列和样例账号 |

原01脚本会重建表，只用于本次新建的专用空库。已有验收库可按对应说明直接检查，日常使用已有应用库直接启动网页。生成工具不执行SQL；应用初始化发现已有库或配置会停止。不要在原业务库中重建，也不要在有人工演示数据的应用库运行第6周前后对照回归。
