# 第五周实体与 ER 模型设计说明

## 一、设计思路

数据库保存五类事实：商品如何被识别和分类、参与经营的人与供应商、当前库存状态、一次销售或采购中的交易内容、预售从活动到预订和提货的业务事件。由这些事实解释现有 15 张表，保留当前场景中的合理结构。

ER 图是已确认业务规则的表达，实际表结构是 v0.1。两者主要差异是：本次要求一个预售活动最多一张采购单、每张采购单一次完整到货；当前数据库仍允许更宽的情况。图中用 `Δ1`、`Δ2` 标出，具体证据和后续方向见问题清单 P01、P02。

当前没有发现必须为第五周新增的核心实体。订单明细、预订、库存分别承载联系属性、独立事件和当前状态，不能只凭它们依赖其他对象就删除。这里保留 15 个实体是核对后的结果，不是要求概念模型必须永远等于表数量。

## 二、实体、主要属性与独立保存理由

以下列出建模所需主要属性。标识与外码在后两节集中说明；`?` 表示 v0.1 中允许为空，不等于在所有业务状态下均可缺失。完整物理类型、默认值与域仍查第一阶段数据字典和 SQL。

| 实体／表 | 一行数据的含义与保留理由 | 主要属性 |
| --- | --- | --- |
| 商品类别 `ProductCategory` | 一种商品分类；多商品共用分类资料，独立维护 | `category_id`, `category_name`, `description?` |
| 作品/IP `AnimeIP` | 一个作品或 IP；可关联多角色与多商品 | `ip_id`, `ip_name`, `description?` |
| 作品角色 `CharacterInfo` | 某 IP 中的一个具体角色；商品可引用同一角色 | `character_id`, `ip_id`, `character_name` |
| 商品 `Product` | 一种按业务编号管理的商品款式；独立于具体销售方式 | `product_id`, `product_code`, `product_name`, `category_id`, `ip_id?`, `character_id?`, `sale_price`, `product_status`, `created_at` |
| 当前库存 `Inventory` | 单门店某商品的当前库存状态；数量和补货警戒值需要独立维护 | `product_id`, `on_hand_qty`, `reserved_qty`, `reorder_point`, `updated_at` |
| 会员 `Member` | 一名注册会员；可在多次购买和预订中反复引用，散客不建档 | `member_id`, `member_no`, `member_name`, `phone`, `register_time`, `member_status` |
| 员工业务角色 `BusinessRole` | 一种经营职责；员工资料引用的业务分类，不是 SQL Server 权限角色 | `role_id`, `role_name`, `description?` |
| 员工 `Employee` | 一名员工及其当前职责；可承担收银、创建采购、验收等联系角色 | `employee_id`, `employee_no`, `employee_name`, `role_id`, `phone?`, `hire_date`, `employee_status` |
| 供应商 `Supplier` | 一家供货单位；在多次采购中重复引用，不登录本系统 | `supplier_id`, `supplier_code`, `supplier_name`, `contact_name?`, `phone?`, `supplier_status` |
| 销售订单 `SalesOrder` | 一次现货销售或独立预售提货的订单头；保存整笔交易共同信息 | `order_id`, `order_no`, `order_type`, `member_id?`, `cashier_id`, `reservation_id?`, `order_time?`, `order_status` |
| 销售明细 `SalesOrderItem` | 一张订单中一种商品的数量和历史成交价；承载订单—商品联系的属性 | `order_id`, `product_id`, `quantity`, `unit_price` |
| 预售活动 `PresaleActivity` | 围绕一种商品的一次限时预售；同商品可以先后开展多次活动 | `presale_id`, `presale_code`, `product_id`, `start_time`, `end_time`, `presale_unit_price`, `deposit_per_unit`, `pickup_deadline?`, `decision_demand_qty?`, `extra_stock_qty`, `planned_purchase_qty?`, `created_by`, `presale_status` |
| 预订记录 `PresaleReservation` | 一名会员参加某活动的一次预订事件；独立保存订金、取消和状态历史 | `reservation_id`, `reservation_no`, `presale_id`, `member_id`, `quantity`, `reserved_at`, `deposit_paid`, `deposit_refunded`, `reservation_status`, `cancelled_at?` |
| 采购订单 `PurchaseOrder` | 一次向一家供应商采购的订单头；本次确定整单到货，v0.1 原结构更宽 | `purchase_id`, `purchase_no`, `supplier_id`, `purchase_type`, `presale_id?`, `created_by`, `order_time`, `expected_arrival?`, `received_time?`, `received_by?`, `purchase_status` |
| 采购明细 `PurchaseOrderItem` | 一张采购单中一种商品的订购数量、成本和原有验收数量 | `purchase_id`, `product_id`, `ordered_qty`, `unit_cost`, `received_qty` |

## 三、主标识与其他候选标识

主码本身也是候选码。下表“其他候选码”只列主码之外的最小唯一标识，不将所有唯一约束等同于候选码。

| 表 | 主码 | 其他候选码 | 依据 |
| --- | --- | --- | --- |
| `ProductCategory` | `category_id` | `category_name` | 名称非空且唯一 |
| `AnimeIP` | `ip_id` | `ip_name` | 名称非空且唯一 |
| `CharacterInfo` | `character_id` | `(ip_id, character_name)` | 同一 IP 内角色名称唯一 |
| `Product` | `product_id` | `product_code` | 商品业务编号非空且唯一，商品名称不要求唯一 |
| `Inventory` | `product_id` | 无额外候选码 | 同时作为商品外码，单门店一商品最多一条当前库存 |
| `Member` | `member_id` | `member_no`；`phone` | 两者在 v0.1 均为非空且唯一；这是当前业务假设 |
| `BusinessRole` | `role_id` | `role_name` | 业务角色名称非空且唯一 |
| `Employee` | `employee_id` | `employee_no` | 员工编号非空且唯一，电话不作为候选码 |
| `Supplier` | `supplier_id` | `supplier_code` | 供应商编号非空且唯一，名称与电话不保证唯一 |
| `SalesOrder` | `order_id` | `order_no` | 订单业务编号非空且唯一 |
| `SalesOrderItem` | `(order_id, product_id)` | 无额外候选码 | 同订单同商品合并，单独任一字段都不能唯一标识明细 |
| `PresaleActivity` | `presale_id` | `presale_code` | 同商品可有多场活动，商品编号不能标识活动 |
| `PresaleReservation` | `reservation_id` | `reservation_no` | 同会员同活动允许多次历史预订 |
| `PurchaseOrder` | `purchase_id` | `purchase_no` | 采购业务编号非空且唯一 |
| `PurchaseOrderItem` | `(purchase_id, product_id)` | 无额外候选码 | 一张采购单中的同商品按一条数量记录管理 |

辅助唯一约束 `(character_id, ip_id)` 和 `(reservation_id, member_id)` 包含已有主码，服务于复合外键，并非新的最小候选码。销售订单非空 `reservation_id` 的唯一索引只约束关联预订的订单，不是整张表的普通候选码。

## 四、联系如何映射成表与外码

商品归属类别、IP、角色，人员参与销售与采购，均通过引用方中的外码映射。完整逐项清单见 `02_业务规则与映射清单.md` 的 R01—R21，包含全部业务外键及复合一致性约束。

三类联系尤其需要解释：

- **订单—商品的多对多**：通过销售明细拆为两条一对多，明细保存本次购买数量和历史成交价；采购采用相同的订单头与明细结构。
- **会员—预售活动的多对多**：通过预订事件连接。由于同一对会员与活动可以留下多次预订，预订使用独立标识，而非把两端外码当成联合主码。
- **商品—库存的一对一上限**：库存的主码同时是商品外码。库存必须属于商品，商品允许先有资料、后有库存；首次验收入库后必须存在库存记录，这一条件目前依靠流程。

## 五、教材 ER 图阅读方式

矩形上部为中英文实体名，下部为主要属性。主码加下划线；多个下划线字段共同组成联合主码。`AK` 表示其他候选标识，`AK1` 的同组字段共同组成一个候选码，属于本图辅助标记。联系使用菱形，内部写 R 编号和业务名称。

采用教材的最小/最大基数记法：实体旁的 min..max 表示本端每个实体参与该联系的次数。例如类别端 `0..*` 表示一个类别可有零至多个商品；商品端 `1..1` 表示每个商品必须归属一个类别。最小值表达可选/必须参与，不再叠加单/双线和箭头。这与原 UML 端点读法不同。

图中 N01—N08 补充不能仅靠多重性表达的条件。订单创建过程中允许零条明细，因此基础关联为 `0..*`；附注另说明完成时至少一条、完成后交易内容固定。预售订单必须关联会员和预订，普通现货订单可以不关联会员，均通过类型条件表达，不额外创建订单子类。

`Δ1` 标记同活动最多一张采购单；`Δ2` 标记整单完整到货。当前实体属性沿用 v0.1，相关状态和字段的调整只列为问题，不在本周修改数据库。

## 六、保留与取舍

保留单门店、最多一个 IP 和具体角色、一次预订整体处理、现货与预售共用商品和销售结构。它们符合当前课程规模，代价与暂不支持的情况已由设计决策 D01—D13 说明。

保留历史成交价和采购需求快照，因为它们记录特定时点事实；可售库存和订单总金额由当前基础数据计算。商品的 IP 与角色依赖留第六周分析，不能直接删除群像商品仍需保存的 IP。整单到货后 `received_qty` 是否继续独立保存也留第六周判断，本周不预设删除结论。

本周不为失败重试、完整状态机或事务实现增加模型复杂度。上述内容若影响后续流程，记录方向即可。

按多商品订单、散客与会员、库存三个案例讲解，直接复用第四周视图。三个简短查询见 `04_只读验证.sql`，预期、操作和观察见 `05_验证记录.md`。预售提货、采购通过图、映射清单和原始样例解释；约束与权限测试引用第四周成果。样例正确不能直接解释为结构已经强制全部业务规则。
