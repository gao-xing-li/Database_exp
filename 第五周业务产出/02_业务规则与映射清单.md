# 第五周业务规则与数据库映射清单

## 一、清单约定

R 编号与 ER 图的联系菱形一致。A、B 按联系名称中的前后顺序确定：“一 A 对 B”写一个 A 可对应的 B 数量，“一 B 对 A”反之；在教材 min..max 图中，前者标在 A 端、后者标在 B 端，表示本端每个实体参与联系的次数。数量均为已确认业务模型，当前结构存在差异时单独注明。

表中的 `1`（图中写为 `1..1`）表示必须且唯一；`0..1` 表示可选且最多一个；`0..*` 表示可选且可多个。状态和类型条件补充整体关联无法直接表达的最低参与要求。表中“已有约束”依据 v0.1 SQL 定义，正反例复用第四周脚本，本次按序复跑的结果见 `05_验证记录.md`。测试通过仅覆盖已测试约束，不消除清单中明确记录的流程缺口。

## 二、联系、基数、参与约束与映射

| 编号／联系 A—B | 一 A 对 B | 一 B 对 A | 条件、参与要求 | v0.1 表字段与约束映射／当前落实 |
| --- | --- | --- | --- | --- |
| R01 商品类别—商品：归属类别 | `0..*` | `1` | 商品必须有类别；类别可无商品 | `Product.category_id → ProductCategory.category_id`；`FK_Product_ProductCategory` 与非空列 |
| R02 IP—作品角色：拥有角色 | `0..*` | `1` | 角色必须属于一个 IP；IP 可无角色 | `CharacterInfo.ip_id → AnimeIP.ip_id`；`FK_CharacterInfo_AnimeIP` 与非空列 |
| R03 IP—商品：归属作品 | `0..*` | `0..1` | 商品可无明确 IP；指定具体角色时必须有 IP | `Product.ip_id → AnimeIP.ip_id`；`FK_Product_AnimeIP`，可空；N01 补充组合条件 |
| R04 作品角色—商品：表现角色 | `0..*` | `0..1` | 群像商品无具体角色；角色与 IP 必须一致 | `Product.character_id → CharacterInfo.character_id`；`FK_Product_CharacterInfo`；另有 `FK_Product_Character_IP` 复合引用及 `CK_Product_CharacterRequiresIP`，见 N01 |
| R05 商品—库存：具有当前库存 | `0..1` | `1` | 库存必须属于一个商品；首次验收入库后商品必须有库存 | `Inventory.product_id → Product.product_id`；`PK_Inventory`、`FK_Inventory_Product`；最低参与的到货条件尚由流程维护，见 N02 |
| R06 业务角色—员工：承担职责 | `0..*` | `1` | 员工当前必须关联一种经营职责 | `Employee.role_id → BusinessRole.role_id`；`FK_Employee_BusinessRole`，非空；与数据库权限角色不是同一个对象 |
| R07 会员—销售订单：购买 | `0..*` | `0..1` | 现货订单允许散客；预售订单必须有会员 | `SalesOrder.member_id → Member.member_id`；`FK_SalesOrder_Member`；`CK_SalesOrder_TypeFields` 强制预售会员非空，见 N04 |
| R08 员工—销售订单：收银 | `0..*` | `1` | 每单必须有收银员工；员工业务职责另查 | `SalesOrder.cashier_id → Employee.employee_id`；`FK_SalesOrder_Cashier`，非空；外键未强制员工属于销售职责，见 N08 |
| R09 销售订单—销售明细：包含 | `0..*` | `1` | 创建中允许零条，完成时至少一条；完成后固定交易内容 | `SalesOrderItem.order_id → SalesOrder.order_id`；`FK_SalesOrderItem_SalesOrder`，非空；外键不保证父单有明细，完成条件见 N03 |
| R10 商品—销售明细：被购买 | `0..*` | `1` | 每条明细必须对应商品；一单同商品合并数量并采用同价 | `SalesOrderItem.product_id → Product.product_id`；`FK_SalesOrderItem_Product`；`PK_SalesOrderItem(order_id, product_id)` 保证一单一商品一行；数量、价格 CHECK |
| R11 商品—预售活动：开展 | `0..*` | `1` | 每场活动只针对一个商品；同商品可多次开展 | `PresaleActivity.product_id → Product.product_id`；`FK_PresaleActivity_Product`，非空，无商品唯一限制 |
| R12 员工—预售活动：创建活动 | `0..*` | `1` | 每场活动必须记录创建者；店长职责另查 | `PresaleActivity.created_by → Employee.employee_id`；`FK_PresaleActivity_Employee`，非空；职责条件见 N08 |
| R13 预售活动—预订：接受预订 | `0..*` | `1` | 每条预订属于一场活动；只允许开放期内预订 | `PresaleReservation.presale_id → PresaleActivity.presale_id`；`FK_PresaleReservation_PresaleActivity`，非空；时间条件仍需跨表流程，见 B03 |
| R14 会员—预订：发起预订 | `0..*` | `1` | 预订必须属于会员；同会员同活动允许留下多次历史预订 | `PresaleReservation.member_id → Member.member_id`；`FK_PresaleReservation_Member`，非空；未设置 `(presale_id, member_id)` 唯一，事件使用独立标识 |
| R15 预订—销售订单：形成提货单 | `0..1` | `0..1` | 现货不关联预订；预售必须关联；会员必须一致；已提货应对应完成订单 | `SalesOrder.reservation_id → PresaleReservation.reservation_id`；`FK_SalesOrder_PresaleReservation`；`FK_SalesOrder_ReservationMember` 复合引用；`UX_SalesOrder_ReservationID` 对非空预订唯一；类型 CHECK，见 N04 |
| R16 供应商—采购订单：供货 | `0..*` | `1` | 每张采购单只向一家供应商采购 | `PurchaseOrder.supplier_id → Supplier.supplier_id`；`FK_PurchaseOrder_Supplier`，非空 |
| R17 预售活动—采购订单：形成采购单 | `0..1` | `0..1` | **Δ1** 每活动最多一单；预售采购必须有活动，普通补货不关联活动 | `PurchaseOrder.presale_id → PresaleActivity.presale_id`；`FK_PurchaseOrder_PresaleActivity`；`CK_PurchaseOrder_PresaleRequired` 仅强制预售非空；目前无活动关联唯一限制，普通补货也未严格禁止填写活动，见 N05、P01、P05 |
| R18 员工—采购订单：创建采购 | `0..*` | `1` | 每单必须有创建员工 | `PurchaseOrder.created_by → Employee.employee_id`；`FK_PurchaseOrder_CreatedBy`，非空；职责见 N08 |
| R19 员工—采购订单：完成验收 | `0..*` | `0..1` | 未完成验收时为空；完成后必须有验收员工与时间 | `PurchaseOrder.received_by → Employee.employee_id`；`FK_PurchaseOrder_ReceivedBy`；`CK_PurchaseOrder_ReceivedInfo` 保证状态与两项验收信息匹配；角色与整单收齐条件未完整强制，见 N06、N08 |
| R20 采购订单—采购明细：包含 | `0..*` | `1` | 创建时可暂未录明细；实际采购及完整验收必须有明细；**Δ2** 全部明细一次收齐 | `PurchaseOrderItem.purchase_id → PurchaseOrder.purchase_id`；`FK_PurchaseOrderItem_PurchaseOrder`；当前允许空父单及部分收货，见 N06、N07、P02 |
| R21 商品—采购明细：被采购 | `0..*` | `1` | 普通补货可多商品；预售采购明细只对应活动商品 | `PurchaseOrderItem.product_id → Product.product_id`；`FK_PurchaseOrderItem_Product`；联合主键限制同单同商品一行；跨表商品匹配尚未自动保证，见 N07 |

## 三、图中附注 N01—N08

| 编号 | 附加规则 | v0.1 当前机制或缺口 |
| --- | --- | --- |
| N01 | 角色非空则 IP 非空，且两者属于同一角色记录 | CHECK 加复合外键已覆盖；角色端的辅助唯一组合不是新候选码 |
| N02 | 商品资料在预售、采购前存在；首次验收入库时确保库存记录存在 | 前者有外键；后者仍依靠流程，缺记录与零库存不同 |
| N03 | 创建中可无明细；完成时至少一条；完成后固定交易内容 | 当前外键和状态 CHECK 未完整保证；本周只明确业务含义 |
| N04 | SPOT 不关联预订，可无会员；PRESALE 必须有同会员预订，整体提货且商品、数量、价格匹配 | 类型、会员一致和最多一单已覆盖；商品、数量、价格、已提货与完成状态一致仍需流程 |
| N05 | **Δ1** 同活动最多一张采购单；预售单关联一场活动，普通补货不关联活动 | 仅预售关联非空已覆盖，其他限制尚待收紧 |
| N06 | **Δ2** 整单一次完整到货；完成验收时所有明细收齐 | 现有状态域有 `PARTIAL_RECEIVED`，数量仅限制 `0 <= received_qty <= ordered_qty`；头部验收信息一致不等于整单已收齐 |
| N07 | 实际采购、验收有明细；预售采购明细商品匹配活动，普通补货可含多商品 | 现有外键保证引用存在，不强制全部条件 |
| N08 | 收银、创建活动、采购决策和验收经办符合对应经营职责 | Employee 外键只保证员工存在；操作者 SQL 权限另由数据库角色控制，不能据此推断字段中员工职责正确 |

## 四、其他需说明的业务规则

| 编号 | 规则 | 已有机制与本周结论 |
| --- | --- | --- |
| B01 | 实际库存、预留库存非负，预留不超过实际；可售库存为两者之差 | 单行 CHECK 已覆盖数量范围；视图计算可售库存。销售、验收和预留释放的自动联动仍未实现 |
| B02 | 历史成交价独立保存；订单总金额由明细数量乘以单价汇总 | 已有明细字段与聚合查询；商品调价不应改变过去成交价；历史内容固定要求见 N03 |
| B03 | 开放期内预订，订金对应数量；截止前取消退订金、截止后取消不退；整体取消或提货 | 单表状态、取消时间和退款范围有约束；活动时间、订金计算与退款条件仍需跨表处理。本周说明规则，不设计完整过程 |
| B04 | 采购需求快照表示决策时点，而非当前有效预订量 | 保留 `decision_demand_qty`；当前需求由 ACTIVE 预订查询得到，两者允许不同 |
| B05 | 会员只能访问本人数据，供应商不登录系统 | 业务角色规则；会员行范围访问留应用阶段，供应商不建账号；不新增数据库实体 |

本清单记录模型语义与现有保证范围。P 编号见问题清单；V 编号见只读查询与验证记录。尚待后续实现的规则不计为本周数据库功能已经完成。
