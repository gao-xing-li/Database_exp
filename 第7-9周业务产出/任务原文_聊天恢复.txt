第7-9周任务
1. 任务目标
三周任务合并为一个任务。小组需要使用Web应用框架，构建一个Web界面程序，把前两周完成的数据库设计应用到程序中，完成从用户登录、Web界面操作到数据写入的完整流程，并测试Web程序与数据库工作的稳定性与可靠性。
分层结构：程序按照“页面层→业务层→数据访问层→数据库层”组织。页面层负责用户交互，接收用户操作和反馈结果；业务层负责判断业务规则，例如库存是否充足、订单是否允许修改；数据访问层负责连接数据库、执行参数化SQL和读取结果；数据库层负责保存表、约束、视图和数据。初学者可以把它理解为：页面提出请求，业务层作出判断，数据访问层执行SQL，SQL Server保存最终数据。
页面层（Web界面）：使用Web应用框架构建可操作的交互页面，负责商品、库存、订单和订单明细的查询、新增、修改和必要删除的展示与操作入口。前端通过调用后端提供的 API 接口获取和提交数据，并对表单必填项、格式和数值范围进行基础校验与提示。
业务层（服务）：把一次完整业务操作组织起来，例如创建订单时先检查商品和库存，再写入订单及订单明细，最后扣减库存。业务层负责业务规则、事务边界和角色可执行范围，并向页面层返回明确的处理结果。
数据访问层：作为系统中唯一与 SQL Server 直接交互的层级，集中编写商品、库存、订单和订单明细的 SQL 查询与修改方法，统一管理数据库连接、SQL 参数、事务提交、事务回滚和连接释放。所有用户输入必须通过参数化查询传入 SQL 语句，不要将前端和业务层输入直接拼接进 SQL 字符串。该层封装所有 SQL 操作细节，向上层提供干净的数据访问接口，确保 SQL 执行的安全性与一致性。
数据库层：使用SQL Server连接。
角色权限：根据店员、管理员等角色划分可执行的业务操作。页面可以根据角色隐藏按钮，但真正的权限检查必须在后端业务层再次执行，关键数据库操作还应使用受限数据库账户，确保界面权限和后端、数据库权限保持一致。
安全与稳定：在后端设置统一异常处理机制，不在每个页面和业务方法中重复处理错误。将输入错误、未登录、无权限、数据不存在、业务规则不满足、数据库连接失败、数据库约束冲突和事务失败分别归类，使用统一错误码和统一响应格式返回结果。前端只显示面向用户的简明提示，不显示SQL语句、数据库结构、连接信息、服务器路径、异常堆栈和其他内部实现细节；具体错误原因写入后端日志，并记录请求标识、时间、操作名称、用户角色、错误码和处理结果，便于开发人员定位和追踪。

2. 任务
准备v1.0数据库。检查第5-6周的迁移脚本、表结构、主外键和样例数据，确认应用开发使用的是最终版本。
按分层结构搭建Web程序。建立页面层、业务层和数据访问层，说明各层职责和调用关系。页面层通过Web框架接收请求并调用业务层，业务层调用数据访问层，数据访问层连接SQL Server。
实现数据访问层。完成连接打开与关闭、参数绑定、事务连接管理，以及商品、库存、订单和订单明细的基础数据访问方法；禁止在页面层直接拼接SQL。
实现业务层和页面请求处理。完成登录、商品查询与维护、库存查询与调整、订单创建与查询等功能。页面层通过Web框架接收并校验请求，再由业务层执行规则判断，最后调用数据访问层读写数据库，并说明每项功能的输入、处理和输出。
完成Web界面操作。通过Web界面完成商品、库存、订单和订单明细的查询、增加、修改和必要的删除；操作结果应及时反馈。
完成角色界面。至少区分店员和顾客两类角色，展示不同角色能够执行的操作，并对下单、订单明细写入、库存扣减等操作测试正常提交。
完成集成测试与阶段交付。测试Web界面程序、数据库和异常反馈，重点验证参数错误、未登录访问、无权限操作、数据库连接失败、约束冲突等情况；确认前端只能看到统一的友好提示，后端日志能够保留足够的定位信息，再整理代码、脚本、测试结果、操作手册、阶段报告和组内分工，确保其他同学能够复现。

4. 提示与常见问题
Flask（Python）：Flask是轻量级Web框架。用路由函数接收页面请求并调用业务方法，用模板生成页面；访问SQL Server可使用pyodbc或配置相应驱动的SQLAlchemy。数据库连接信息放在配置中，不写死在页面代码里。
Spring Boot（Java）：Spring Boot用于快速构建Java Web应用。Controller接收请求，Service处理业务，Repository或JdbcTemplate访问SQL Server；配置数据库驱动和连接参数。
连接失败：检查服务器地址、数据库名称、用户名、密码、端口和SQL Server服务状态，先用数据库客户端验证连接信息。
查询不安全：不要把用户输入直接拼接到SQL字符串中，所有带输入参数的查询都使用参数化方式，并在后端进行类型、长度、范围和必填项校验。
权限不一致：应用界面隐藏操作不等于数据库权限控制，关键操作仍要在后端业务处理和数据库账户权限中进行限制。
库存和订单不一致：下单流程应同时考虑订单写入、订单明细写入和库存扣减。
异常信息泄露：前端不得直接显示数据库原始错误、SQL语句、异常堆栈、服务器路径或连接信息。后端统一转换为错误码和友好提示，例如“操作失败，请检查输入内容”或“系统暂时无法完成操作”；详细错误应该保留，在后端可以查看。
重复处理错误：不要在每个页面单独判断数据库异常；应在后端建立统一异常处理层，对参数错误、认证失败、权限不足、资源不存在、约束冲突和系统异常分别处理，并保持统一的响应结构。
迁移后结果变化：使用固定样例数据和关键查询进行迁移前后对比，确认数据含义和业务结果没有改变。
