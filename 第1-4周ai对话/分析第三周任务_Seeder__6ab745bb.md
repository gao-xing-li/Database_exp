[L111] 因此，供应商属于需要进入业务管理范围的外部对象，而不是系统用户。

[L113] ------

[L115] # 三、商品业务规则

[L117] ## 1. 商品与 IP、角色的关系

[L119] 为了体现二次元周边商品特点，同时控制业务复杂度，对商品所属作品和角色采用以下规则：

[L121] - 一个商品最多属于一个 IP；
[L122] - 一个商品最多对应一个具体角色；
[L123] - 如果商品属于某个 IP，但表现的是多个角色或整体群像，则不对应某一个具体角色；
[L124] - 群像商品的 `character_id` 记为 `NULL`；
[L125] - 不考虑同一个商品同时属于多个 IP；
[L126] - 暂不设计一个商品同时对应多个具体角色的复杂关系。

例如：

[L130] “初音未来亚克力立牌”可以属于 VOCALOID IP，并对应“初音未来”这一具体角色。

[L132] “某作品全员合照色纸”可以属于该作品 IP，但由于属于群像商品，因此不对应单一角色。

[L134] 这里的设计主要用于描述商品的业务属性，不意味着商品按照 IP 或角色划分为不同销售类型。

[L136] ------

[L138] # 四、现货销售业务流程

[L140] 当商品已经具有可销售现货库存时，顾客可以直接到店购买。

[L142] 基本流程为：

[L144] **顾客选择商品→ 店员确认商品及数量→ 顾客结账→ 形成销售订单→ 记录订单中的具体商品及数量→ 商品库存减少→ 完成交易。**

[L146] 一笔普通销售订单可以包含多种不同商品，同一种商品也可以购买多个。

[L148] 如果购买者是会员，则同时形成该会员的历史消费记录。

[L150] 随着商品不断销售，库存持续减少。当库存不足时，由库存管理员提出补货需求，再由店长决定实际采购数量。

[L152] ------

[L154] # 五、预售业务流程

[L156] ## 1. 开放预售

[L158] 店铺可以选择某些尚未到货或尚未正式销售的商品开展预售。

[L160] 店长需要确定：

[L162] - 预售商品；
[L163] - 预售开始时间；
[L164] - 预售截止时间；
- 订金；
[L166] - 最晚提货期限等规则。

[L168] 会员在预售期间可以对商品进行预订，并支付一定订金。

[L170] ------

[L172] ## 2. 一次预售预订作为整体处理

[L174] 为了简化预售管理，一次预售预订按照一个整体进行处理。

[L176] 例如会员一次预订某商品 3 件，则这 3 件属于同一次预售预订。

[L178] 项目暂不支持：

[L180] - 预订 3 件后只取消其中 1 件；
[L181] - 到货后只提取其中 1 件，剩余 2 件以后再提取。

即：

[L185] **一次预售预订只能整体取消或整体保留，并最终整体提货。**

[L187] 如果会员决定取消，则该次预订中的全部数量同时取消。

[L189] 如果会员完成提货，则该次预订中的全部商品数量一次性完成提取。

[L191] 这一规则用于控制预售业务复杂度。

[L193] ------

[L195] # 六、预售取消规则

[L197] ## 1. 预售截止之前

[L199] 会员可以自行取消预订。

取消后：

[L203] - 整笔预订失效；
[L204] - 已支付订金退还；
[L205] - 该笔预订不再计入最终有效预订需求。

[L207] ------

[L209] ## 2. 预售截止之后

[L211] 会员仍然可以自行取消整笔预订，但：

[L213] **已经支付的订金不予退还。**

[L215] 如果取消发生在正式采购之前，则该笔预订可以不再计入采购需求。

[L217] 如果取消发生在店铺已经完成采购之后，则采购数量已经确定，对应商品到货后不再为该会员保留，而进入普通现货库存继续销售。

因此：

[L221] **预售截止后允许取消，但顾客需要承担订金损失。**

[L223] 该行为属于预订取消，不属于普通商品售后的退货退款业务。

[L225] ------

[L227] # 七、预售采购规则

[L229] 店铺在预售截止之后统一进行采购。

[L231] 不会因为每增加一次预订就立即向供应商采购。

[L233] 店长决定实际采购数量时主要考虑：

[L235] 1. 当前仍然有效的预订数量；
[L236] 2. 店内已有相关库存情况；
[L237] 3. 额外备货策略。

因此：

[L241] **实际采购数量不一定等于预订数量。**

例如：

[L245] 某款商品在准备采购时有 40 件有效预订。

[L247] 店长判断商品正式到货以后仍可能具有较好的现货销售需求，因此额外备货 10 件。

最终采购：

[L251] **50 件。**

其中：

[L255] - 40 件用于满足已有预售需求；
[L256] - 10 件属于计划额外备货。

[L258] 当前额外备货数量由店长人工确定。

[L260] 暂时不实现自动进货算法。

[L262] 未来可以利用：

[L264] - 当前库存；
[L265] - 历史销量；
[L266] - 近期销量；
[L267] - 商品所属 IP 的销售表现；
[L268] - 不同角色相关商品的销售表现；
[L269] - 会员历史购买情况；

[L271] 辅助制定额外备货策略。

[L273] ------

[L275] # 八、商品到货与预售库存转现货

[L277] 供应商完成供货以后，由库存管理员验收商品。

[L279] 通过预售需求产生的采购商品到货以后，首先用于满足仍然有效的预售需求。

[L281] 剩余商品进入普通现货库存继续销售。

[L283] 剩余商品主要可能来自两部分：

[L285] 1. 店铺主动进行的额外备货；
[L286] 2. 店铺已经采购后，部分会员取消预订而产生的多余商品。

例如：

[L290] 实际采购 50 件。

[L292] 采购以后，有 2 件对应的预订被取消，最后仍然需要完成的预售提货数量为 38 件。

[L294] 那么商品到货以后：

[L296] - 38 件用于完成预售；
[L297] - 12 件进入普通现货库存。

[L299] 因此，同一个商品可以首先通过预售方式销售，之后剩余数量又进入现货销售。

[L301] 项目不存在固定的“预售商品”和“现货商品”两种商品类别，而是存在**预售销售和现货销售两种业务方式**。

[L303] ------

[L305] # 九、预售提货流程

[L307] 预售商品到货以后，仍具有有效预订的会员可以到店提货。

[L309] 基本流程为：

[L311] **商品到货→ 会员到店→ 店员确认预订→ 会员支付尾款→ 形成预售提货销售订单→ 一次性提取该笔预订中的全部商品→ 完成预售。**

[L313] ------

[L315] ## 1. 一次预订对应一笔预售提货销售订单

项目规定：

[L319] **一次预售预订最终对应一笔预售提货销售订单。**

[L321] 即一个会员的一次预售行为，在最终提货时独立完成结账，并形成对应的销售订单。

暂不考虑：

[L325] > 一个会员同时存在多个不同预售活动的预订，并在一次结账中把这些不同预售活动的商品一起提走。

例如：

[L329] 会员参加了 A 商品的预售和 B 商品的另一场预售。

[L331] 即使两种商品恰好同时到货，当前项目仍将其视为两次独立预售业务：

[L333] - A 预订形成一笔预售提货销售订单；
[L334] - B 预订形成另一笔预售提货销售订单。

[L336] 这样可以保证预售活动、预订和最终销售之间的关系清晰。

[L338] ------

[L340] # 十、最晚提货规则

[L342] 商品到货后，店铺为预售顾客设置最晚提货期限。

[L344] 会员应当在期限内完成：

[L346] - 尾款支付；
[L347] - 整笔预订商品提取。

[L349] 如果超过最晚提货期限仍未提货，则视为会员主动放弃该次预订。

此时：

[L353] - 整笔预订失效；
[L354] - 订金不予退还；
[L355] - 原本为该会员保留的全部商品转入普通现货库存。

[L357] 项目不支持只放弃其中部分商品。

[L359] ------

[L361] # 十一、普通现货补货流程

[L363] 普通现货随着销售持续减少。

[L365] 基本补货流程为：

[L367] **商品销售→ 库存下降→ 库存管理员检查库存→ 发现库存不足→ 提出补货需求→ 店长决定采购数量→ 向供应商采购→ 商品到货→ 验收入库→ 增加现货库存。**

[L369] 普通商品采用批量补货，而不是每销售一件商品就采购一件。

[L371] 店长可以结合：

[L373] - 当前库存；
[L374] - 历史销量；
[L375] - 近期销售情况；
[L376] - 经营经验；

[L378] 决定采购数量。

[L380] 当前采购决策由人工完成。

[L382] ------

[L384] # 十二、两种销售业务之间的关系

[L386] 项目存在两种主要销售方式。

[L388] ## 1. 现货销售

[L390] 商品已经具有可销售库存时：

[L392] **现货库存→ 顾客购买→ 销售订单→ 库存减少。**

[L394] ## 2. 预售销售

[L396] 商品尚未到货时：

[L398] **开展预售→ 会员预订并支付订金→ 预售截止→ 汇总有效需求→ 决定采购数量→ 统一采购→ 商品到货→ 会员补尾款并整体提货→ 形成预售提货销售订单。**

[L400] 预售中产生的剩余商品进入普通现货库存。

因此：

[L404] **商品不是“预售商品”或“现货商品”，而是同一种商品可以在不同经营阶段采用不同销售方式。**

[L406] ------

[L408] # 十三、总体业务闭环

[L410] ## 现货业务

[L412] **采购→ 商品到货→ 验收入库→ 现货库存→ 顾客购买→ 销售订单→ 库存减少→ 库存不足→ 再次补货。**

[L414] ## 预售业务

[L416] **店铺开展预售→ 会员整体预订并支付订金→ 截止前可以整体取消并退订金→ 预售截止→ 截止后仍可以整体取消但订金不退→ 根据有效预订量、库存和额外备货策略确定采购量→ 统一采购→ 商品到货→ 会员在期限内支付尾款并整体提货→ 一次预订形成一笔预售提货销售订单→ 未提货、采购后取消和额外备货产生的剩余商品进入普通现货库存。**

### 4. 第二周写的“域”，第三周要真正变成 SQL 约束

这一点我认为会是第三周的核心之一。

例如第二周写：

```sql

```

而应该真正把这个业务范围写进数据库，例如用：

### 5. 但不是所有业务规则都应该在第三周硬塞进 CHECK

这里我会比较克制。

### 6. 第二周设计里有一个 SQL Server 实现时必须修正的问题

这是我目前发现最重要的一点。

第二周的 `SalesOrder` 设计中：

```text
reservation_id FK → PresaleReservation
UNIQUE(reservation_id)
```

目的是保证“一条预售预订最多对应一笔预售提货订单”。同时文档认为：

> `reservation_id` 为 NULL 的普通订单不受这个规则影响。fileciteturn0file5L594-L629

从**业务设计**角度完全合理。

但如果在 SQL Server 里直接写：

```sql
reservation_id INT UNIQUE
```

会有问题。

SQL Server 的单列 `UNIQUE` 对 `NULL` 的处理并不是“可以无限多个 NULL”。这样会妨碍多笔普通现货订单都把：

```text
reservation_id = NULL
```

存进去。

因此实际落地时，我不会把这里直接实现成普通 `UNIQUE` 约束，而会采用类似：

```sql
CREATE UNIQUE INDEX ...
ON SalesOrder(reservation_id)
WHERE reservation_id IS NOT NULL;
```

也就是：

**只要求非 NULL 的 reservation_id 唯一。**

这样才能准确表达你们真正的业务规则：

```text
普通订单：
reservation_id = NULL
可以有任意多笔

预售订单：
reservation_id != NULL
同一个 reservation_id 最多出现一次
```

这属于典型的“第二周逻辑模型没错，但到了具体 DBMS 实现必须微调”的地方。

### 7. Product 的 IP—角色一致性也是第三周值得重点验证的地方

你们第二周这里设计得比较有代表性。

`Product` 同时存：

```text
ip_id
character_id
```

并要求不能出现：

```text
原神 + 三月七
```

这样的错误组合。fileciteturn0file5L196-L252

因此你们设置了：

```text
CharacterInfo UNIQUE(character_id, ip_id)
```

以及：

```text
Product(character_id, ip_id)
    FK → CharacterInfo(character_id, ip_id)
```

这个在 SQL Server 中可以真正实现。

但是还有一条：

```text
character_id IS NULL
OR
ip_id IS NOT NULL
```

也必须单独写成 `CHECK`。

否则由于复合外键涉及 `NULL` 时的行为，仅靠复合 FK 并不能完整阻止：

```text
ip_id = NULL
character_id = 1
```

这种数据。

因此这个地方第三周实际 SQL 最好同时存在：

```text
ip_id 的普通 FK
+
(character_id, ip_id) 的复合 FK
+
character_id IS NULL OR ip_id IS NOT NULL 的 CHECK
```

这个会是非常好的“我们真的理解了约束为什么这样设计”的实验内容。

### 9. CRUD 我不会拿正式样例记录随便删

第三周明确要求至少对商品、库存、订单相关数据分别做插入、查询、修改和删除。fileciteturn0file2L75-L83


这种失败本身当然可以说明 FK 生效，但它不是“正常 DELETE 演示”。


给它建立 Inventory，然后：

```text

→ SELECT
→ UPDATE
→ SELECT
→ DELETE Inventory
→ DELETE Product
```

```text

→ 创建订单明细
→ 查询
→ 修改状态
→ 查询
→ 先删除明细
→ 再删除订单
```

这样既展示 CRUD，也顺便体现了：

> 删除时通常按照外键依赖的相反顺序。

| PK | `product_id` |
| UQ | `product_code` |
| FK | `category_id → ProductCategory` |
| FK | `ip_id → AnimeIP` |
| FK | `character_id → CharacterInfo` |
| 复合 FK | `(character_id, ip_id) → CharacterInfo(character_id, ip_id)` |
| DEFAULT | `product_status='ON_SALE'`；`created_at=当前时间` |
| CHECK | `product_id > 0` |
| CHECK | `sale_price > 0` |
| CHECK | `product_status IN ('PENDING','ON_SALE','STOPPED')` |
| CHECK | `character_id IS NULL OR ip_id IS NOT NULL` |

这里最关键的是最后两层约束。

仅仅：

```text
character_id FK → CharacterInfo
```

只能证明“这个角色存在”。

它不能阻止：

```text
ip_id = 原神
character_id = 三月七
```

所以还需要：

```text
(character_id, ip_id)
→ CharacterInfo(character_id, ip_id)
```

来保证角色和 IP 是同一组合。

同时复合 FK 遇到 `NULL` 时不能替代：

```text
character_id IS NULL OR ip_id IS NOT NULL
```

所以这个 `CHECK` 也应保留。

也就是说，这里看起来约束有点重复，但实际上每一层解决的问题不同。

## 9. Inventory

第二周库存定义非常适合直接用 `CHECK` 实现。fileciteturn0file5L283-L327

| 类型 | 实现 |
|---|---|
| PK | `product_id` |
| FK | `product_id → Product(product_id)` |
| DEFAULT | `on_hand_qty = 0` |
| DEFAULT | `reserved_qty = 0` |
| DEFAULT | `reorder_point = 0` |
| DEFAULT | `updated_at = 当前时间` |
| CHECK | `on_hand_qty >= 0` |
| CHECK | `reserved_qty >= 0` |
| CHECK | `reorder_point >= 0` |
| CHECK | `reserved_qty <= on_hand_qty` |

因此：

```text
available_qty
```

仍然不建立字段，而是在查询时：

```text
on_hand_qty - reserved_qty
```

计算。fileciteturn0file5L303-L317

这里有一个关系数据库上的小细节值得知道。

你们第二周写：

```text
Product : Inventory = 1 : 1
```

但现在这种设计实际上能够直接保证的是：

```text
一个 Product 最多有一条 Inventory
```

因为 `Inventory.product_id` 是 PK。

它**不能仅靠这个 FK 保证每一个 Product 创建后立刻一定有一条 Inventory**。

也就是数据库结构本身更准确地说是：

```text
Product → Inventory = 1 : 0..1
```

实际业务上通过“新增商品时同时建立 Inventory”维持 1:1 即可。

我不建议为了强行实现数学意义上的严格 1:1 再把结构复杂化。

## 14. SalesOrder

这是另一张需要特别处理的表。第二周的业务规则是：普通销售不关联预订；预售提货订单必须关联一条预订，而且一条预订最多形成一笔销售订单。fileciteturn0file5L594-L610

| 类型 | 实现 |
|---|---|
| PK | `order_id` |
| UQ | `order_no` |
| FK | `member_id → Member` |
| FK | `cashier_id → Employee` |
| FK | `reservation_id → PresaleReservation` |
| DEFAULT | `order_status = 'CREATED'` |
| CHECK | `order_id > 0` |
| CHECK | `order_type IN ('SPOT','PRESALE')` |
| CHECK | `order_status IN ('CREATED','COMPLETED','CANCELLED')` |
| CHECK | 普通订单与预售订单的字段组合是否合法 |
| 特殊唯一性 | 非 NULL 的 `reservation_id` 必须唯一 |

这个组合约束可以表达为：

```text
SPOT:
    reservation_id 必须为 NULL
    member_id 可以 NULL，也可以非 NULL

PRESALE:
    reservation_id 必须非 NULL
    member_id 必须非 NULL
```

这个完全属于单行规则，所以很适合第三周直接写 `CHECK`。

### reservation_id 的 UNIQUE 需要改变实现方式

第二周关系模式写的是：

```text
UNIQUE(reservation_id)
```

但真实业务要求其实是：

```text
NULL 可以出现很多次；
非 NULL 值不能重复。
```

SQL Server 对普通单列 `UNIQUE` 的处理是：用于唯一性判断时两个 `NULL` 会被视为相同，因此一个普通唯一索引中只能存在一个 `NULL`。Microsoft 官方文档明确说明了这一点。citeturn491138search2turn491138search3

因此这里不要直接创建普通：

```sql
UNIQUE(reservation_id)
```

而应该在建完表后创建：

```sql
CREATE UNIQUE INDEX ...
ON SalesOrder(reservation_id)
WHERE reservation_id IS NOT NULL;
```

Microsoft 官方文档也正是用这种 filtered unique index 来实现“只要求非 NULL 唯一”。citeturn491138search0

这是目前第二周设计到第三周落地过程中最明确的一处 **DBMS 实现调整**。

## 3. 这里有几个地方值得你真正理解

这部分以后实验答辩很容易被问。

### `Product` 为什么有三个跟角色有关的 FK？

现在存在：

```sql
FOREIGN KEY (ip_id)
REFERENCES AnimeIP(ip_id)
```

保证 IP 本身存在。

```sql
FOREIGN KEY (character_id)
REFERENCES CharacterInfo(character_id)
```

保证角色本身存在。

以及：

```sql
FOREIGN KEY (character_id, ip_id)
REFERENCES CharacterInfo(character_id, ip_id)
```

保证**这个角色确实属于这个 IP**。

所以：

```text
原神 + 甘雨
```

可以。

但：

```text
原神 + 三月七
```

会被拒绝。

这正对应第二周对 IP—角色一致性的设计。fileciteturn0file5L1508-L1532

---

### `Inventory` 为什么 `product_id` 同时是 PK 和 FK？

因为一件商品在这个单门店模型中最多只有一条库存记录。

于是：

```text
Inventory.product_id
```

既表示：

> 这条库存属于哪个商品

又表示：

> 每个商品不能出现两条库存记录。

第二周就是这样设计 `Product : Inventory = 1 : 1` 的。fileciteturn0file5L283-L317

严格来说，当前结构直接保证的是：

```text
一个 Product 最多一条 Inventory
```

至于每个商品**必须**存在 Inventory，由新增商品时同时建立库存记录这一业务流程保证。

---

### 为什么 `PresaleReservation` 没有这个？

```sql
UNIQUE(presale_id, member_id)
```

因为你们明确允许：

```text
会员参加 PS001
↓
取消
↓
后来重新参加 PS001
```

因此可以留下：

```text
R001  PS001  M001  CANCELLED
R006  PS001  M001  ACTIVE
```

两条历史记录。fileciteturn0file5L789-L809

---

### 为什么 `SalesOrder.reservation_id` 用 INDEX 而不是 UNIQUE？

你们的业务要求：

```text
普通订单：
reservation_id = NULL

预售订单：
reservation_id = 某预订编号
```

普通订单显然会很多，因此：

```text
NULL
NULL
NULL
NULL
...
```

必须允许重复。

但：

```text
reservation_id = 1
```

最多只能出现一次。

所以使用：

```sql
CREATE UNIQUE INDEX ...
WHERE reservation_id IS NOT NULL;
```

正好表达：

> **只约束非 NULL 的预订编号唯一。**

# 二、先做一次样例数据人工检查

完成插入后，可以运行几个非常简单的查询，确认数据链不是“每张表各自有数据，但是互相没关系”。

### 1. 商品—IP—角色

```sql
SELECT

    ON p.ip_id = ip.ip_id

    ON p.character_id = c.character_id
ORDER BY p.product_id;
```

应该能看到类似：


这也验证了“群像商品可以有 IP、没有具体角色”的第二周设计。fileciteturn0file5L196-L252

### 2. 查看库存可售量

```sql
SELECT
    p.product_code,
    p.product_name,
    i.on_hand_qty,
    i.reserved_qty,
    i.on_hand_qty - i.reserved_qty AS available_qty,
    i.reorder_point
FROM dbo.Inventory AS i
JOIN dbo.Product AS p
    ON i.product_id = p.product_id
ORDER BY p.product_id;
```

这里继续遵守第二周设计：`available_qty` 不存数据库，而由 `on_hand_qty - reserved_qty` 得出。fileciteturn0file5L283-L317

# 四、这套 CRUD 为什么比直接改 P001 更适合作业

第三周要求的不是证明你敢执行 `DELETE`，而是展示你理解关系数据库的数据修改过程。

例如测试商品形成：

```text
Product 9001
    ↓
Inventory 9001
```

因此删除必须：

```text
DELETE Inventory
        ↓
DELETE Product
```

销售则形成：

```text
SalesOrder 9001
        ↓
SalesOrderItem 9001
```

所以也是：

```text
DELETE SalesOrderItem
        ↓
DELETE SalesOrder
```

这正好把第三周任务书提醒的“先创建被外码引用的表，删除时通常按相反顺序”真正演示出来。fileciteturn0file2L88-L93

同时，每一个 `UPDATE`、`DELETE` 前都有同条件的：

```sql
SELECT ...
WHERE ...
```

这也是任务书明确建议的操作习惯。fileciteturn0file2L90-L93

## 三、SQL 脚本组成

第三周目前包含四个主要 SQL 文件。

### 1. `00_create_database.sql`

用于创建数据库：

```text
AnimeGoodsStoreDB
```

如果数据库已经存在，则不会重复创建。

脚本完成数据库创建后切换到该数据库，为后续建表做好准备。

### 2. `01_create_tables.sql`

根据第二周确定的关系模式创建全部 15 张数据表。

脚本中实现了以下主要完整性约束：

- `PRIMARY KEY`：保证每张表中的主要标识唯一；
- `UNIQUE`：保证商品编号、订单编号、会员编号等业务编号不重复；
- `FOREIGN KEY`：保证不同表之间引用的数据真实存在；
- `NOT NULL`：保证必要业务字段必须填写；
- `DEFAULT`：为状态、时间和部分数值字段设置合理默认值；
- `CHECK`：限制价格、数量、状态等字段的合法取值范围。

例如：

- 商品售价必须大于 0；
- 库存数量不能为负数；
- 预留库存不能超过实际库存；
- 销售数量和采购数量必须大于 0；
- 实际到货数量不能超过采购数量；
- 商品状态只能取 `PENDING`、`ON_SALE` 或 `STOPPED`；
- 订单状态只能取规定的状态值。

此外，对商品的 IP 和角色关系进行了组合约束，防止出现角色与所属 IP 不一致的数据。

对于销售订单中的 `reservation_id`，普通现货订单允许其为 `NULL`，而同一条非空预售预订最多只能对应一笔预售提货订单，因此使用了过滤唯一索引实现这一规则。

### 3. `02_insert_sample_data.sql`

用于向数据库中插入样例数据。

样例数据覆盖：

- 商品类别；
- IP 与角色；
- 商品；
- 库存；
- 会员；
- 员工与经营角色；
- 供应商；
- 普通销售订单；
- 预售活动和预订；
- 普通补货和预售采购。

第二周已有的核心样例数据继续保留，同时增加少量测试数据，使后续能够进行更有意义的连接查询、销售统计、库存统计和会员消费统计。

样例数据之间并不是相互独立的。

例如，一笔销售订单会对应真实存在的商品和员工；预售提货订单会关联对应的预订记录；预售采购会关联相应的预售活动；采购明细中的商品也必须在商品表中真实存在。

### 4. `03_crud.sql`

该脚本用于展示商品、库存和销售订单相关数据的基本 CRUD 操作。

CRUD 分别表示：

```text
Create：新增
Read：查询
Update：修改
Delete：删除
```

为了避免修改正式样例数据，CRUD 测试使用独立的测试编号，例如：

```text
product_id = 9001
order_id = 9001
```

测试结束后会删除这些临时数据，因此不会影响原有业务样例。

## 四、主要 CRUD 实验

### 1. 商品 CRUD

首先新增一件测试商品，并查询确认商品已经成功写入。

随后修改：

- 商品名称；
- 商品售价。

修改前先使用相同的 `WHERE` 条件进行查询，确认需要修改的目标记录，修改后再次查询并比较结果。

最后删除该测试商品。

由于商品存在对应库存记录，因此删除时必须先删除：

```text
Inventory
```

中的库存记录，再删除：

```text
Product
```

中的商品记录。

该过程同时验证了数据库外键关系对删除顺序的限制。

### 2. 库存 CRUD

为测试商品建立库存记录，设置：

- 实际库存；
- 预留库存；
- 补货警戒值。

随后查询库存，并通过：

```text
available_qty = on_hand_qty - reserved_qty
```

计算当前可销售库存。

之后修改实际库存和补货警戒值，并再次查询确认修改结果。

库存测试数据最终随测试商品一起删除。

### 3. 销售订单 CRUD

创建一笔测试普通现货订单，初始状态设置为：

```text
CREATED
```

随后增加订单明细，并通过连接查询查看：

- 订单编号；
- 商品；
- 数量；
- 历史成交单价；
- 当前订单金额。

之后将订单状态由：

```text
CREATED
```

修改为：

```text
COMPLETED
```

并记录实际交易时间。

同时测试修改订单明细中的购买数量。

删除订单时，由于 `SalesOrderItem` 通过外键引用 `SalesOrder`，需要先删除订单明细，再删除销售订单。

## 五、数据完整性设计说明

本周尽可能将第二周确定的单表业务规则落实到了数据库约束中。

```text

ordered_qty > 0
received_qty >= 0
received_qty <= ordered_qty
reserved_qty >= 0
reserved_qty <= on_hand_qty
```

这些规则都能够直接通过 `CHECK` 约束表达。

这些规则暂时由业务流程保证，后续可以结合权限、事务、存储过程和触发器等内容进一步实现。
