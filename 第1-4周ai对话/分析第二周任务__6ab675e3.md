[L127] ## 1. 开放预售

[L131] 店长需要确定：

[L133] - 开放预售的商品；
[L134] - 预售开始时间；
[L135] - 预售截止时间；
[L136] - 订金等相关经营规则。

[L138] 会员在预售期间可以提交预订，并支付一定订金。

[L142] ## 2. 预售截止前取消

[L144] 在预售截止之前，会员可以自行取消预订。

取消后：

[L148] - 该预订不再有效；
[L149] - 已支付订金退还；
[L150] - 该预订原则上不再计入最终采购需求。

[L152] 因此预售截止前，有效预订数量可能持续发生变化。

[L154] ------

[L156] ## 3. 预售截止

[L158] 到达预售截止时间以后，店铺统计当前有效预订需求。

[L160] 预售截止以后，顾客仍然可以自行取消预订，但：

[L162] **订金不予退回。**

[L164] 如果取消发生在正式采购以前，则该取消需求可以不再纳入采购需求。

[L166] 如果取消发生在店铺已经采购之后，则采购数量已经无法相应减少。该顾客原本对应的商品到货后不再为其保留，而转入普通现货库存继续销售。

[L168] ------

[L170] # 五、预售采购规则

[L172] 店铺在预售截止之后统一进行采购，而不是每增加一个预订就立即采购。

[L174] 采购数量主要综合考虑：

[L176] 1. 当前有效预订数量；
[L177] 2. 当前相关库存情况；
[L178] 3. 店铺设置的额外备货策略。

因此：

[L182] **实际采购数量不一定严格等于预订数量。**

例如：

[L186] 某款商品在预售截止时有 40 件有效预订。

[L188] 店长认为该商品正式到货后仍有较好的现货销售需求，因此决定额外备货 10 件。

最终：

[L192] **实际采购数量 = 50 件。**

其中：

[L196] - 40 件用于满足当前预售需求；
[L197] - 另外 10 件计划作为到货后的普通现货。

[L199] 如果采购以后又有部分顾客取消预订，则实际用于预售提货的数量进一步减少，对应的剩余商品也进入普通现货库存。

[L201] 当前阶段只设置上述采购规则和经营逻辑。

[L203] 具体额外备货数量由店长人工确定，暂时不实现自动进货算法。

[L205] 未来可以考虑根据历史销量、库存情况、商品所属 IP 或角色的销售表现以及会员历史购买情况辅助制定备货策略。

[L211] 采购完成后，供应商向店铺供货。

[L219] 实际采购 50 件；

[L221] 其中最终仍有 38 件有效预订；

[L225] - 38 件用于预售顾客提货；
[L226] - 剩余 12 件进入普通现货库存。

[L228] 剩余商品可能来自两部分：

[L230] 1. 店铺主动进行的额外备货；
[L231] 2. 采购完成后顾客取消预订而产生的剩余商品。

[L237] # 七、预售提货规则

[L239] 预售商品到货以后，仍具有有效预订的会员可以到店提货。

[L241] 主要流程为：

[L243] **商品到货→ 顾客前往门店→ 店员确认预订→ 顾客支付剩余款项→ 完成提货→ 预售交易完成。**

此时：

[L251] - 已支付订金不予退还；
[L252] - 该预订不再继续保留；
[L253] - 原本为顾客保留的商品转入普通现货库存。

## 3.2 Inventory 库存表

一个商品只有一条当前库存记录，因此：

```text

```

| 字段 | 类型 | NULL | 默认值 / 域 | 键 | 含义 |
|---|---|---:|---|---|---|
| product_id | INT | 否 | — | PK、FK → Product | 商品 |

| reserved_qty | INT | 否 | 0，>=0 | — | 已到货但为预售顾客保留的数量 |

| updated_at | DATETIME2 | 否 | 当前时间 | — | 最近库存更新时间 |

要求：

```text
0 <= reserved_qty <= on_hand_qty
```

```text
available_qty = on_hand_qty - reserved_qty
```

这样避免三个库存数字互相矛盾。

```text

)
```

```text
  ↓
```

```text
  ↓
PresaleActivity
  ↓
PresaleReservation
  ↓

  ↓

PurchaseOrderItem
```

# 十、当前设计中几个重要约定

### 1. 商品最多一个 IP、一个角色

```text
Product.ip_id
Product.character_id
```

均允许 NULL。

当前不处理多 IP、多角色。

---

### 2. 群像商品

例如：

```text
原神群像徽章套装
```

记录为：

```text
ip_id = 原神
character_id = NULL
```

---

### 3. 商品不是“预售商品”或“现货商品”

`Product` 中不设置：

```text
is_presale
```

是否开展预售由：

```text
PresaleActivity
```

决定。

因此同一个商品可以：

```text
先预售
→ 到货
→ 剩余商品转现货
→ 后续继续普通销售
```

---

### 4. 非会员顾客不单独建立顾客表

普通顾客完成现货交易：

```text
SalesOrder.member_id = NULL
```

会员购买：

```text
SalesOrder.member_id = 对应会员
```

这样避免为每一名临时到店顾客建立无意义资料。

---

### 5. 不存重复的可计算库存

数据库只记录：

```text
on_hand_qty
reserved_qty
```

可销售数量：

```text
on_hand_qty - reserved_qty
```

---

### 6. 历史成交价格必须进入订单明细

即使：

```text
Product.sale_price
```

以后发生变化，

历史：

```text
SalesOrderItem.unit_price
```

仍保持交易发生时的价格。

---

### 7. 预售采购和普通补货统一建模

统一使用：

```text
PurchaseOrder
PurchaseOrderItem
```

通过：

```text
purchase_type
```

区分：

```text
PRESALE
RESTOCK
```

这样第三、第四阶段不需要再维护两套采购逻辑。

---

# 第一轮：每一个事实到底应该存几次？

这是关系数据库最基本的问题：

> 一个事实最好只有一个权威来源；如果同一事实存在两个地方，就必须解释为什么两份都要存，以及如何保证它们永远一致。

目前几个关键点如下。

| 当前设计 | 判断 | 原因 |
|---|---|---|
| `Inventory.on_hand_qty` | 保留 | 当前实际库存，是业务状态 |
| `Inventory.reserved_qty` | 保留 | 与实际库存不同，是预售占用状态 |
| `available_qty` 不存 | **很好** | `on_hand_qty - reserved_qty` 可计算 |
| `SalesOrderItem.unit_price` | **必须保留** | 它是历史成交价，不能以后跟着 Product.sale_price 改 |
| `SalesOrder.total_amount` | 建议删除 | 完全可由订单明细 `SUM(quantity × unit_price)` 得到 |
| `PresaleReservation.balance_paid` | 建议删除 | 已有预售价格、数量、订金，可以计算 |
| `PresaleReservation.pickup_time` | 建议删除 | 已经有最终 `SalesOrder.order_time` 表示完成提货交易时间 |
| `decision_demand_qty` | 保留 | 是“做采购决策当时”的需求快照 |
| `extra_stock_qty` | 保留 | 是店长人为决策 |
| `planned_purchase_qty` | 保留 | 是计划量，与后来真正采购量不是同一个事实 |
| `PurchaseOrderItem.received_qty` | 保留 | 表示实际收货状态 |

这里最值得修改的是 `SalesOrder.total_amount`。

例如：

```text
SO001
P001 × 2 × ¥68
P002 × 1 × ¥45
```

销售额天然就是：

```text
2×68 + 1×45 = 181
```

如果同时再存：

```text
SalesOrder.total_amount = 181
```

将来有人修改订单明细，却忘了修改 total_amount，就出现：

```text
明细算出来 = 181
total_amount = 200
```

数据库无法判断哪个才是真。

而且第四周本来就要求做聚合、销售额统计和统计视图，直接从订单明细计算反而很适合作为后续实验内容。第四周明确要求用聚合、GROUP BY 等统计销量和销售额。fileciteturn0file3L84-L103

所以我的第一处正式修改建议是：

> **删除 `SalesOrder.total_amount`。**

# 第二轮：检查主码、候选码、外码能不能真正约束业务

这一轮发现三个值得修正的地方。

## 1. `Product.ip_id + character_id` 存在隐藏的不一致问题

你希望：

```text
Product
    ip_id
    character_id
```

都直接存在商品表，并允许 NULL。

这是完全可以的。

问题在于：

```text
CharacterInfo
character_id = 3
ip_id = 2
character_name = 三月七
```

而商品可以被错误地写成：

```text
Product
ip_id = 1         -- 原神
character_id = 3 -- 三月七
```

两个普通 FK 都合法：

```text
ip_id=1 确实存在
character_id=3 也确实存在
```

但组合起来业务错误。

因此应该补一个“组合一致性约束”。

推荐设计成：

```text
CharacterInfo
(
    character_id PK,
    ip_id FK,
    character_name,

    UNIQUE(character_id, ip_id)
)
```

然后 Product 除两个普通字段外，把：

```text
(character_id, ip_id)
```

作为组合外码引用：

```text
CharacterInfo(character_id, ip_id)
```

同时要求：

```text
character_id IS NULL
OR
ip_id IS NOT NULL
```

效果就是：

```text
原神 + 甘雨       √
原神 + NULL       √
NULL + NULL       √

原神 + 三月七     ×
NULL + 甘雨       ×
```

这正好符合你现在“一商品最多一 IP、一角色”的简化。

---

## 2. `PresaleReservation(presale_id, member_id)` 不应该直接设成候选码

之前方案规定：

```text
UNIQUE(presale_id, member_id)
```

看似合理，但它实际上偷偷加入了一条你们第一周**从未定义的业务规则**：

> 一个会员参加过一次某预售后，就永远不能再为这个活动产生第二条预订记录。

假设：

```text
9月3日 预订
9月5日 截止前取消
9月7日 改变主意再次预订
```

第一周业务规则并没有说第二次预订禁止。

而 UNIQUE 会直接阻止。

从第一性原则上，不应该因为数据库设计方便而创造新的经营规则。

因此我建议：

```text
reservation_id PK
reservation_no UNIQUE
```

保留。

但是删除：

```text
UNIQUE(presale_id, member_id)
```

如果以后真的希望“同一会员同一活动最多存在一个当前有效预订”，那是：

> **最多一个 ACTIVE 记录**

而不是：

> 历史上一辈子只能有一条记录。

这两者差别很大。

---

## 3. `Employee.phone` 不适合当前作为候选码

原方案：

```text
phone NULL
UNIQUE
```

这里首先存在实现层面的麻烦，其次从业务语义上电话号码也不是员工最稳定的业务身份。

已经有：

```text
employee_no UNIQUE
```

足够作为候选码。

所以建议：

```text
Employee.phone
```

保留普通字段，但去掉候选码身份。

# 第三轮：把它当成状态机检查

数据库不只是保存“对象”，更重要的是保存对象**从什么状态变成什么状态**。

## 1. 销售订单

之前默认：

```text

```

这不太合理。

因为以后第三阶段做“订单事务”时，一个合理流程其实是：

```text
   ↓

   ↓
检查库存
   ↓
结账成功
   ↓
COMPLETED
```

如果中途失败：


所以建议：

```text
COMPLETED
```

默认：


只有：

```text
COMPLETED
```

才能算销量、减少库存。

这对后面的事务实验尤其重要。

算出来。

# 二次元周边商品店——第二周关系模式设计

## 一、设计范围与基本约定

本项目为一家小型线下二次元周边商品店。数据库主要管理商品、商品库存、会员、员工、销售订单、预售、供应商、采购及补货等经营数据。

在第一周业务需求基础上，为控制数据库项目复杂度，本阶段采用以下三项简化假设：

1. **一个商品最多属于一个 IP，并最多对应一个具体角色。**  
   商品可以只对应 IP 而不对应具体角色，例如群像商品；无明确 IP 或角色的商品，相应字段允许为 NULL。

2. **一次预售预订作为一个整体进行处理。**  
   暂不支持部分取消或部分提货。例如会员预订 3 件商品时，不考虑只取消其中 1 件或只提取其中 2 件的情况。

3. **一条预售预订最终最多对应一笔预售提货销售订单。**  
   暂不考虑一次结账同时提取多个不同预售活动商品的情况。

此外，普通现货销售和预售最终提货统一进入销售订单系统；普通补货和预售采购统一进入采购订单系统。

## 4.1 Inventory 库存表

一个商品在当前单门店经营模式下只有一条当前库存记录，因此：

```text
Product : Inventory = 1 : 1
```

### 字段定义

| 字段 | 类型 | NULL | 默认值/域 | 键 | 含义 |
|---|---|---:|---|---|---|
| product_id | INT | 否 | — | PK、FK → Product | 对应商品 |
| on_hand_qty | INT | 否 | 0，>=0 | — | 当前实际在库数量 |
| reserved_qty | INT | 否 | 0，>=0 | — | 已到货但为预售顾客预留的数量 |
| reorder_point | INT | 否 | 0，>=0 | — | 补货警戒值 |
| updated_at | DATETIME2 | 否 | 当前时间 | — | 最近更新时间 |

```text
0 <= reserved_qty <= on_hand_qty
```

不单独保存可销售库存字段。

可销售库存由：

```text
available_qty = on_hand_qty - reserved_qty
```

计算得到。

### 关系模式

```text

    product_id PK FK → Product.product_id,
    on_hand_qty,
    reserved_qty,
    reorder_point,
    updated_at
)
```

### 样例元组

| product_id | on_hand_qty | reserved_qty | reorder_point |
|---:|---:|---:|---:|
| 1 | 8 | 0 | 5 |
| 2 | 5 | 0 | 4 |
| 3 | 2 | 0 | 3 |

例如商品 P003：


## 9.1 PresaleActivity 预售活动表

商品本身不划分为“预售商品”和“现货商品”。

是否开展预售由 `PresaleActivity` 表示，因此一个商品以后可以开展多次预售活动。

| 字段 | 类型 | NULL | 默认值/域 | 键 | 含义 |

| product_id | INT | 否 | — | FK → Product | 预售商品 |
| start_time | DATETIME2 | 否 | — | — | 预售开始时间 |
| end_time | DATETIME2 | 否 | > start_time | — | 预售截止时间 |
| presale_unit_price | DECIMAL(10,2) | 否 | >0 | — | 本次预售商品单价 |
| deposit_per_unit | DECIMAL(10,2) | 否 | >=0 | — | 每件商品要求的订金 |
| pickup_deadline | DATETIME2 | 是 | NULL | — | 最晚提货期限 |
| decision_demand_qty | INT | 是 | NULL，>=0 | — | 店长做采购决策时的有效预订需求量 |
| extra_stock_qty | INT | 否 | 0，>=0 | — | 店长决定的额外备货数量 |
| planned_purchase_qty | INT | 是 | NULL，>=0 | — | 店长最终计划采购数量 |
| created_by | INT | 否 | — | FK → Employee | 创建预售活动的管理员 |
| presale_status | VARCHAR(20) | 否 | PLANNED | 枚举 | 当前预售状态 |

### presale_status 域

```text
PLANNED
OPEN
CLOSED
PURCHASING
ARRIVED
FINISHED
```

```text
start_time < end_time
```

`pickup_deadline` 在商品实际到货并开放提货后确定。

例如：



## 9.2 PresaleReservation 预订记录表

一个会员可以参加多个预售。

同一会员也允许在同一次预售中留下多条历史预订记录，例如：

```text
第一次预订
→ 截止前取消
→ 后来重新预订
```

因此：

```text
(presale_id, member_id)
```

**不设置为候选码。**

每条预订通过独立的 `reservation_id` 和 `reservation_no` 标识。

### 字段定义

| 字段 | 类型 | NULL | 默认值/域 | 键 | 含义 |
|---|---|---:|---|---|---|
| reservation_id | INT | 否 | 正整数 | PK | 预订内部编号 |
| reservation_no | VARCHAR(20) | 否 | — | UNIQUE候选码 | 预订业务编号 |
| presale_id | INT | 否 | — | FK → PresaleActivity | 所属预售活动 |
| member_id | INT | 否 | — | FK → Member | 预订会员 |
| quantity | INT | 否 | >0 | — | 预订数量 |
| reserved_at | DATETIME2 | 否 | 当前时间 | — | 预订时间 |
| deposit_paid | DECIMAL(10,2) | 否 | >=0 | — | 已实际支付订金总额 |
| deposit_refunded | DECIMAL(10,2) | 否 | 0，>=0 | — | 已退还订金金额 |
| reservation_status | VARCHAR(20) | 否 | ACTIVE | 枚举 | 当前预订状态 |
| cancelled_at | DATETIME2 | 是 | NULL | — | 实际取消时间 |

不单独保存：

```text
balance_paid
pickup_time
```

原因：

预售完成时商品完整成交价格已经进入：

```text
SalesOrderItem.unit_price
```

预售实际完成提货时间则由：

```text
SalesOrder.order_time
```

记录。

这样可以避免同一笔交易的信息在两个位置重复保存。

### reservation_status 域

```text
ACTIVE
CANCELLED
PICKED_UP
EXPIRED
```

其中：

```text
ACTIVE
   ├── CANCELLED
   ├── PICKED_UP
   └── EXPIRED
```

取消发生在预售截止前还是截止后，不增加不同状态，而通过：

```text
cancelled_at
```

与：

```text
PresaleActivity.end_time
```

比较得到。

### 订金规则

截止前取消：

```text
reservation_status = CANCELLED
cancelled_at <= end_time
deposit_refunded = deposit_paid
```

截止后取消：

```text
reservation_status = CANCELLED
cancelled_at > end_time
deposit_refunded = 0
```

超过最晚提货期限：

```text
reservation_status = EXPIRED
deposit_refunded = 0
```

### 关系模式

```text
PresaleReservation(
    reservation_id PK,
    reservation_no UNIQUE,
    presale_id FK → PresaleActivity.presale_id,
    member_id FK → Member.member_id,
    quantity,
    reserved_at,
    deposit_paid,
    deposit_refunded,
    reservation_status,
    cancelled_at
)
```

### 样例元组

| reservation_id | reservation_no | presale_id | member_id | quantity | reserved_at | deposit_paid | deposit_refunded | reservation_status | cancelled_at |
|---:|---|---:|---:|---:|---|---:|---:|---|---|
| 1 | R001 | 1 | 1 | 1 | 2026-09-05 | 30.00 | 0.00 | PICKED_UP | NULL |
| 2 | R002 | 1 | 2 | 1 | 2026-09-06 | 30.00 | 0.00 | CANCELLED | 2026-09-18 |
| 3 | R003 | 2 | 2 | 1 | 2026-09-22 | 20.00 | 0.00 | ACTIVE | NULL |

R002 所属预售活动截止时间为：

```text
2026-09-15
```

而取消时间为：

```text
2026-09-18
```

所以属于截止后取消，订金不退：

```text
deposit_refunded = 0
```

| created_by | INT | 否 | — | FK → Employee | 创建采购订单的员工 |

| received_time | DATETIME2 | 是 | NULL | — | 实际完成验收时间 |
| received_by | INT | 是 | NULL | FK → Employee | 实际验收员工 |
| purchase_status | VARCHAR(30) | 否 | CREATED | 枚举 | 采购订单状态 |

### purchase_type 域

```text

```

### purchase_status 域

```text
CREATED
ORDERED
PARTIAL_RECEIVED

CANCELLED
```

### 业务规则

预售采购：

```text
purchase_type = PRESALE
→ presale_id 不应为 NULL
```

```text
purchase_type = RESTOCK
→ presale_id 通常为 NULL
```

```text
received_time = NULL
received_by = NULL
```


# 十一、主要业务流程与数据表对应关系

## 11.1 普通现货销售

```text
Product
  ↓
查询 Inventory
  ↓
计算 available_qty
  ↓
创建 SalesOrder(CREATED)
  ↓
创建 SalesOrderItem
  ↓
确认库存和结账
  ↓
SalesOrder → COMPLETED
  ↓
Inventory.on_hand_qty 减少
```

例如：

```text
on_hand_qty = 10
reserved_qty = 3
```

则：

```text
available_qty = 7
```

普通顾客购买 2 件后：

```text
on_hand_qty = 8
reserved_qty = 3
available_qty = 5
```

---

## 11.2 预售正常完成

```text
Product
  ↓
PresaleActivity
  ↓
PresaleReservation
  ↓
预售截止
  ↓
统计有效需求
  ↓
店长决定额外备货
  ↓
PurchaseOrder(PRESALE)
  ↓
PurchaseOrderItem
  ↓
供应商到货
  ↓
库存管理员验收
  ↓
Inventory.on_hand_qty 增加
  ↓
有效预订对应数量进入 reserved_qty
  ↓
会员到店提货
  ↓
SalesOrder(PRESALE)
  ↓
SalesOrderItem
  ↓
订单 COMPLETED
  ↓
on_hand_qty 与 reserved_qty 同时减少
  ↓
Reservation → PICKED_UP
```

---

## 11.3 预售采购后取消

例如采购：

```text
有效预订需求 = 2
额外备货 = 1
计划采购 = 3
```

采购完成后其中一名会员取消。

商品最终到货 3 件时，只剩 1 件需要为有效预订保留：

```text
on_hand_qty += 3
reserved_qty += 1
```

因此：

```text
available_qty = 3 - 1 = 2
```

这两件普通现货分别来源于：

```text
1件原计划额外备货
+
1件采购后取消产生的剩余商品
```

无需建立“预售库存”和“普通库存”两套独立库存。

---

## 11.4 超过最晚提货期限

假设：

```text
on_hand_qty = 5
reserved_qty = 2
```

其中一个预订超过最晚提货期限。

则：

```text
Reservation → EXPIRED
```

商品仍在店内，所以：

```text
on_hand_qty = 5
```

但不再为该会员保留：

```text
reserved_qty: 2 → 1
```

因此：

```text
available_qty:
5 - 2 = 3
→
5 - 1 = 4
```

该商品自然重新进入普通现货销售。

---

## 11.5 普通补货

```text
商品持续销售
  ↓
Inventory可销售库存下降
  ↓
达到或低于reorder_point
  ↓
库存管理员发现库存不足
  ↓
店长决定采购数量
  ↓
PurchaseOrder(RESTOCK)
  ↓
PurchaseOrderItem
  ↓
供应商到货
  ↓
库存管理员验收
  ↓
received_by / received_time记录
  ↓
Inventory.on_hand_qty增加
```

# 十三、主要设计原则与理由

## 13.1 商品不设置“是否预售”字段

商品本身不是永久的“预售商品”。

是否预售由：

```text
PresaleActivity
```

表达。

因此同一个商品可以经历：

```text
首次预售
→ 到货
→ 作为普通现货销售
→ 以后再次开展新的预售活动
```

---

## 13.2 普通顾客不建立独立顾客记录

非会员顾客完成现货购买时：

```text
SalesOrder.member_id = NULL
```

只有注册会员才进入：

```text
Member
```

避免保存没有后续经营意义的临时顾客资料。

---

## 13.3 预售和现货最终统一形成销售记录

完成提货的预售交易和普通现货交易均进入：

```text
SalesOrder
SalesOrderItem
```

以后统计：

- 商品销量；
- IP销量；
- 类别销量；
- 会员历史消费；
- 总销售额；

均可以使用统一的数据来源。

---

## 13.4 历史成交价格单独保存

```text
Product.sale_price
```

表示当前售价。

```text
SalesOrderItem.unit_price
```

表示历史交易实际成交价格。

商品以后即使调价，也不会改变历史订单。

---

## 13.5 不保存可直接计算的销售订单总金额

订单金额可以通过：

```text
SUM(quantity × unit_price)
```

计算。

因此不在：

```text
SalesOrder
```

中重复保存 `total_amount`，避免订单明细与订单总金额发生矛盾。

---

## 13.6 库存只保存基本状态

保存：

```text
on_hand_qty
reserved_qty
```

不保存：

```text
available_qty
```

因为：

```text
available_qty
=
on_hand_qty - reserved_qty
```

可以随时计算。

---

## 13.7 预售预订不重复保存最终交易信息

`PresaleReservation` 负责记录：

```text
会员预订
订金
取消
预订状态
```

真正完成提货以后：

```text
成交价格 → SalesOrderItem
交易时间 → SalesOrder
```

因此不再在 `PresaleReservation` 重复保存：

```text
balance_paid
pickup_time
```

---

## 13.8 同一会员允许在同一活动中留下多条历史预订

不设置：

```text
UNIQUE(presale_id, member_id)
```

原因是业务可能出现：

```text
预订
→ 截止前取消
→ 后来重新预订
```

每一次业务记录均应保留下来。

---

## 13.9 IP和角色必须保持一致

因为 Product 同时直接保存：

```text
ip_id
character_id
```

所以数据库必须防止：

```text
原神 + 三月七
```

这样的组合。

角色存在时，其：

```text
(character_id, ip_id)
```

必须共同引用同一条 `CharacterInfo` 记录。

---

## 13.10 普通补货与预售采购使用统一采购结构

均使用：

```text
PurchaseOrder
PurchaseOrderItem
```

通过：

```text
purchase_type
```

区分：

```text
RESTOCK
PRESALE
```

减少两套相似采购表和采购逻辑。

---

# 十四、最终关系模式汇总


# 十五、第二周阶段结论

本阶段共设计 15 张数据表。

数据库以商品为核心，将商品类别、IP和角色作为基础资料；将库存作为商品的当前经营状态；通过销售订单和订单明细记录普通销售及完成提货的预售交易；通过预售活动和预订记录表示预售业务；通过采购订单和采购明细统一表示预售采购与普通库存补货。

各核心业务对象均具有明确主码，并通过候选码保证业务编号等属性的唯一性，通过外码建立商品、会员、订单、预售、采购、供应商和员工之间的联系。

当前设计能够支持后续：

- 数据库建表和样例数据导入；
- 商品、库存、订单和采购 CRUD；
- 多表连接查询；
- 商品、IP和类别销量统计；
- 会员消费统计；
- 库存状态查询；
- 预售需求统计；
- 供应商及采购统计；
- 数据完整性约束；
- 不同经营角色的权限划分；
- 后续基于历史销售数据的销量分析和补货决策。

在当前阶段暂不纳入物流、退换货、复杂营销、财务会计、多门店经营、自动采购算法以及复杂会员画像等业务。
