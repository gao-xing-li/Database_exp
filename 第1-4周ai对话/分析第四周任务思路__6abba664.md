[L111] 因此，供应商属于需要进入业务管理范围的外部对象，而不是系统用户。

[L113] ------

[L115] # 三、商品业务规则

[L117] ## 1. 商品与 IP、角色的关系

[L119] 为了体现二次元周边商品特点，同时控制业务复杂度，对商品所属作品和角色采用以下规则：

[L121] - 一个商品最多属于一个 IP；
[L122] - 一个商品最多对应一个具体角色；
[L123] - 如果商品属于某个 IP，但表现的是多个角色或整体群像，则不对应某一个具体角色；
[L124] - 群像商品的 `character_id` 记为 `NULL`；
[L125] - 不考虑同一个商品同时属于多个 IP；
[L126] - 暂不设计一个商品同时对应多个具体角色的复杂关系。

例如：

[L130] “初音未来亚克力立牌”可以属于 VOCALOID IP，并对应“初音未来”这一具体角色。

[L132] “某作品全员合照色纸”可以属于该作品 IP，但由于属于群像商品，因此不对应单一角色。

[L134] 这里的设计主要用于描述商品的业务属性，不意味着商品按照 IP 或角色划分为不同销售类型。

[L136] ------

[L138] # 四、现货销售业务流程

[L140] 当商品已经具有可销售现货库存时，顾客可以直接到店购买。

[L142] 基本流程为：

[L144] **顾客选择商品→ 店员确认商品及数量→ 顾客结账→ 形成销售订单→ 记录订单中的具体商品及数量→ 商品库存减少→ 完成交易。**

[L146] 一笔普通销售订单可以包含多种不同商品，同一种商品也可以购买多个。

[L148] 如果购买者是会员，则同时形成该会员的历史消费记录。

[L150] 随着商品不断销售，库存持续减少。当库存不足时，由库存管理员提出补货需求，再由店长决定实际采购数量。

[L152] ------

[L154] # 五、预售业务流程

[L156] ## 1. 开放预售

[L158] 店铺可以选择某些尚未到货或尚未正式销售的商品开展预售。

[L160] 店长需要确定：

[L162] - 预售商品；
[L163] - 预售开始时间；
[L164] - 预售截止时间；
- 订金；
[L166] - 最晚提货期限等规则。

[L168] 会员在预售期间可以对商品进行预订，并支付一定订金。

[L170] ------

[L172] ## 2. 一次预售预订作为整体处理

[L174] 为了简化预售管理，一次预售预订按照一个整体进行处理。

[L176] 例如会员一次预订某商品 3 件，则这 3 件属于同一次预售预订。

[L178] 项目暂不支持：

[L180] - 预订 3 件后只取消其中 1 件；
[L181] - 到货后只提取其中 1 件，剩余 2 件以后再提取。

即：

[L185] **一次预售预订只能整体取消或整体保留，并最终整体提货。**

[L187] 如果会员决定取消，则该次预订中的全部数量同时取消。

[L189] 如果会员完成提货，则该次预订中的全部商品数量一次性完成提取。

[L191] 这一规则用于控制预售业务复杂度。

[L193] ------

[L195] # 六、预售取消规则

[L197] ## 1. 预售截止之前

[L199] 会员可以自行取消预订。

取消后：

[L203] - 整笔预订失效；
[L204] - 已支付订金退还；
[L205] - 该笔预订不再计入最终有效预订需求。

[L207] ------

[L209] ## 2. 预售截止之后

[L211] 会员仍然可以自行取消整笔预订，但：

[L213] **已经支付的订金不予退还。**

[L215] 如果取消发生在正式采购之前，则该笔预订可以不再计入采购需求。

[L217] 如果取消发生在店铺已经完成采购之后，则采购数量已经确定，对应商品到货后不再为该会员保留，而进入普通现货库存继续销售。

因此：

[L221] **预售截止后允许取消，但顾客需要承担订金损失。**

[L223] 该行为属于预订取消，不属于普通商品售后的退货退款业务。

[L225] ------

[L227] # 七、预售采购规则

[L229] 店铺在预售截止之后统一进行采购。

[L231] 不会因为每增加一次预订就立即向供应商采购。

[L233] 店长决定实际采购数量时主要考虑：

[L235] 1. 当前仍然有效的预订数量；
[L236] 2. 店内已有相关库存情况；
[L237] 3. 额外备货策略。

因此：

[L241] **实际采购数量不一定等于预订数量。**

例如：

[L245] 某款商品在准备采购时有 40 件有效预订。

[L247] 店长判断商品正式到货以后仍可能具有较好的现货销售需求，因此额外备货 10 件。

最终采购：

[L251] **50 件。**

其中：

[L255] - 40 件用于满足已有预售需求；
[L256] - 10 件属于计划额外备货。

[L258] 当前额外备货数量由店长人工确定。

[L260] 暂时不实现自动进货算法。

[L262] 未来可以利用：

[L264] - 当前库存；
[L265] - 历史销量；
[L266] - 近期销量；
[L267] - 商品所属 IP 的销售表现；
[L268] - 不同角色相关商品的销售表现；
[L269] - 会员历史购买情况；

[L271] 辅助制定额外备货策略。

[L273] ------

[L275] # 八、商品到货与预售库存转现货

[L277] 供应商完成供货以后，由库存管理员验收商品。

[L279] 通过预售需求产生的采购商品到货以后，首先用于满足仍然有效的预售需求。

[L281] 剩余商品进入普通现货库存继续销售。

[L283] 剩余商品主要可能来自两部分：

[L285] 1. 店铺主动进行的额外备货；
[L286] 2. 店铺已经采购后，部分会员取消预订而产生的多余商品。

例如：

[L290] 实际采购 50 件。

[L292] 采购以后，有 2 件对应的预订被取消，最后仍然需要完成的预售提货数量为 38 件。

[L294] 那么商品到货以后：

[L296] - 38 件用于完成预售；
[L297] - 12 件进入普通现货库存。

[L299] 因此，同一个商品可以首先通过预售方式销售，之后剩余数量又进入现货销售。

[L301] 项目不存在固定的“预售商品”和“现货商品”两种商品类别，而是存在**预售销售和现货销售两种业务方式**。

[L303] ------

[L305] # 九、预售提货流程

[L307] 预售商品到货以后，仍具有有效预订的会员可以到店提货。

[L309] 基本流程为：

[L311] **商品到货→ 会员到店→ 店员确认预订→ 会员支付尾款→ 形成预售提货销售订单→ 一次性提取该笔预订中的全部商品→ 完成预售。**

[L313] ------

[L315] ## 1. 一次预订对应一笔预售提货销售订单

项目规定：

[L319] **一次预售预订最终对应一笔预售提货销售订单。**

[L321] 即一个会员的一次预售行为，在最终提货时独立完成结账，并形成对应的销售订单。

暂不考虑：

[L325] > 一个会员同时存在多个不同预售活动的预订，并在一次结账中把这些不同预售活动的商品一起提走。

例如：

[L329] 会员参加了 A 商品的预售和 B 商品的另一场预售。

[L331] 即使两种商品恰好同时到货，当前项目仍将其视为两次独立预售业务：

[L333] - A 预订形成一笔预售提货销售订单；
[L334] - B 预订形成另一笔预售提货销售订单。

[L336] 这样可以保证预售活动、预订和最终销售之间的关系清晰。

[L338] ------

[L340] # 十、最晚提货规则

[L342] 商品到货后，店铺为预售顾客设置最晚提货期限。

[L344] 会员应当在期限内完成：

[L346] - 尾款支付；
[L347] - 整笔预订商品提取。

[L349] 如果超过最晚提货期限仍未提货，则视为会员主动放弃该次预订。

此时：

[L353] - 整笔预订失效；
[L354] - 订金不予退还；
[L355] - 原本为该会员保留的全部商品转入普通现货库存。

[L357] 项目不支持只放弃其中部分商品。

[L359] ------

[L361] # 十一、普通现货补货流程

[L363] 普通现货随着销售持续减少。

[L365] 基本补货流程为：

[L367] **商品销售→ 库存下降→ 库存管理员检查库存→ 发现库存不足→ 提出补货需求→ 店长决定采购数量→ 向供应商采购→ 商品到货→ 验收入库→ 增加现货库存。**

[L369] 普通商品采用批量补货，而不是每销售一件商品就采购一件。

[L371] 店长可以结合：

[L373] - 当前库存；
[L374] - 历史销量；
[L375] - 近期销售情况；
[L376] - 经营经验；

[L378] 决定采购数量。

[L380] 当前采购决策由人工完成。

[L382] ------

[L384] # 十二、两种销售业务之间的关系

[L386] 项目存在两种主要销售方式。

[L388] ## 1. 现货销售

[L390] 商品已经具有可销售库存时：

[L392] **现货库存→ 顾客购买→ 销售订单→ 库存减少。**

[L394] ## 2. 预售销售

[L396] 商品尚未到货时：

[L398] **开展预售→ 会员预订并支付订金→ 预售截止→ 汇总有效需求→ 决定采购数量→ 统一采购→ 商品到货→ 会员补尾款并整体提货→ 形成预售提货销售订单。**

[L400] 预售中产生的剩余商品进入普通现货库存。

因此：

[L404] **商品不是“预售商品”或“现货商品”，而是同一种商品可以在不同经营阶段采用不同销售方式。**

[L406] ------

[L408] # 十三、总体业务闭环

[L410] ## 现货业务

[L412] **采购→ 商品到货→ 验收入库→ 现货库存→ 顾客购买→ 销售订单→ 库存减少→ 库存不足→ 再次补货。**

[L414] ## 预售业务

[L416] **店铺开展预售→ 会员整体预订并支付订金→ 截止前可以整体取消并退订金→ 预售截止→ 截止后仍可以整体取消但订金不退→ 根据有效预订量、库存和额外备货策略确定采购量→ 统一采购→ 商品到货→ 会员在期限内支付尾款并整体提货→ 一次预订形成一笔预售提货销售订单→ 未提货、采购后取消和额外备货产生的剩余商品进入普通现货库存。**

## 3. `constraint.sql` 是我认为最需要把握尺度的一部分

你现在其实已经有大量约束了。例如 `Inventory` 已经限制：

还有商品售价、状态、订单类型、外键、唯一性等大量约束。

**第一部分：检查已有约束是否已经覆盖主要数据完整性。**

**第二部分：找 2～4 个现在确实遗漏、又适合数据库 CHECK 表达的规则进行补充。**

例如，我目前认为比较值得考虑的有：

- `deposit_refunded <= deposit_paid`
- 如果 `reservation_status='CANCELLED'`，则 `cancelled_at` 应当非空

- `pickup_deadline` 如果已经确定，应晚于预售结束时间
- 完成的销售订单应具有 `order_time`

这些最终还要逐个审一下业务语义，不能看到“似乎合理”就全部写进去。

然后 `constraint.sql` 的真正重点是设计**正反例**：

合法数据：

```text
合法 INSERT / UPDATE
→ 成功
```

非法数据：

```text
负库存
重复业务编号
不存在的外键
reserved_qty > on_hand_qty
错误状态值
退还订金 > 已付订金
……
→ 被数据库拒绝
```

也就是说，这份文件应该承担“证明数据库约束确实生效”的职责，而不只是定义约束。

而且你第三周已经正确区分了两类规则：有些规则适合 CHECK/FK，有些需要跨表查询或完整业务流程，比如“销售员工必须是销售角色”“完成销售自动扣库存”等，这些不应该现在强行塞进复杂 CHECK，后面用权限、事务、过程或触发器解决更合适。fileciteturn0file6L242-L275

> 找出累计销售额超过 100 元的商品。

例如逻辑上：

```text
GROUP BY product
HAVING SUM(quantity) >= 2
```

为什么不是 `WHERE`？

因为条件作用的不是某一行：

```text
quantity >= 2
```

而是作用于分组后的：

```text
SUM(quantity)
```

所以必须用 `HAVING`。

为了让实验效果明显，阈值不要设得太高。你当前样例数据量比较小，所以这里最好根据实际运行结果选一个能筛掉一部分、又保留一部分的阈值。

我倾向用：

```text
累计销量 >= 2
```

比“销售额 > 100”更直观。

### Q8 子查询：消费额高于会员平均值的会员

这个是目前八条中相对最“查询题”一点的。

业务问题：

> 哪些会员的累计消费金额高于所有有消费会员的平均累计消费金额？

不是：

```text
某笔订单 > 平均订单金额
```

而是：

先得到：

```text
会员A → 总消费
会员B → 总消费
会员C → 总消费
```

然后求这些会员消费额的平均数，再筛：

```text
member_total > average_member_total
```

所以大致逻辑会是：

```text
第一层：
每个会员 SUM(...)

第二层：
AVG(每个会员的 SUM(...))

最终：
筛选高于这个平均值的会员
```

这个查询可以用：

- 嵌套子查询；
- 派生表；
- CTE；

都能完成。

如果课程当前主要讲“子查询”，我建议优先用普通子查询 / 派生表，不急着提前引入更复杂写法。

### 这里有几个关键设计点

**T1～T5 不需要重新创建对应约束。** 它们本来就已经存在于 `01_create_tables.sql`。例如商品售价 `> 0`、库存 `reserved_qty <= on_hand_qty` 已通过 CHECK 落实；商品编号有 UNIQUE，商品类别有 FK。fileciteturn0file8L239-L280 fileciteturn0file8L308-L326

T5 尤其值得保留。你现在同时有：

```sql
FOREIGN KEY (ip_id)
    REFERENCES AnimeIP(ip_id)

FOREIGN KEY (character_id)
    REFERENCES CharacterInfo(character_id)

FOREIGN KEY (character_id, ip_id)
    REFERENCES CharacterInfo(character_id, ip_id)
```

前两个只能分别证明“原神存在”和“三月七存在”，只有第三个复合外键才能证明：

> **三月七并不属于原神。**

这正是第二周专门设计 `(character_id, ip_id)` 组合约束的原因。fileciteturn0file5L1508-L1532

**T6 是这周真正新增的约束。** 目前原表只保证 `deposit_paid >= 0`、`deposit_refunded >= 0`，并没有比较二者大小。fileciteturn0file8L424-L484 因而：

```text
支付订金 20 元
退款 30 元
```

第三周数据库实际上可能接受；第四周补充：

```sql
CHECK (deposit_refunded <= deposit_paid)
```

就有明确的“发现缺口 → 增补约束 → 构造反例证明”的实验过程。

### 为什么统一用了事务

比如 T2 中先临时创建商品：

```text
9202
```

然后插入非法库存。

非法库存被 CHECK 拒绝以后，`CATCH` 中：

```sql
ROLLBACK TRAN;
```

会连同前面创建的 9202 商品一起撤销。因此无论重复执行多少次，都不会因为上一次测试留下垃圾数据而影响下一次。

同理，正例虽然真正能插入成功，但测试完也主动回滚。

最终两条：

```sql
SELECT *
FROM Product
WHERE product_id BETWEEN 9100 AND 9299;
```

应该返回 **0 行**，相当于再证明测试没有污染业务数据。

### 为什么 T6 没有把退款规则进一步限制为“0 或全额”

业务文档目前规定截止前取消全退、截止后取消不退。fileciteturn0file5L883-L907 理论上可以写成更严格规则，但那还涉及：

```text
cancelled_at
        与
PresaleActivity.end_time
```

之间的跨表比较。

这就超出了普通单表 CHECK 的自然能力。因此第四周这里只落实最基础、确定且能可靠表达的不变量：

\[
0\le deposit\_refunded\le deposit\_paid
\]

而“应该全退还是不退”继续留给后续业务过程/事务处理，这是比较清晰的边界。

### 几个设计点

第一，**没有使用 `db_owner`、`db_datareader`、`db_datawriter`**。任务明确提醒不要为了方便直接授予数据库所有权限。fileciteturn0file3L111-L115 我们逐对象、甚至逐列授权，例如：

```sql
GRANT UPDATE (received_time, received_by, purchase_status)
```

比直接：

```sql
GRANT UPDATE ON PurchaseOrder
```

更符合最小权限。

第二，第四周创建的视图真正参与了权限设计。例如销售店员可以：

```sql
SELECT * FROM dbo.vw_OrderDetail;
```

却不需要因此获得对所有订单相关基础表的任意查询权限。库存角色同样可以通过：

```sql
vw_InventoryStatus
```

获得适合工作的库存信息。这就让前面的“查询→视图→权限”成为一个连续设计。

第三，测试中的 `WITHOUT LOGIN` 用户只是**实验身份**：

```text
u_test_sales
u_test_inventory
u_test_manager
```

它们不等于 `Employee` 表里的李晨、周宁、王敏，也不会自动根据 `Employee.role_id` 获得权限。`BusinessRole` 本身记录的是现实经营角色，第二周已经明确说明它“不等同于 SQL Server 中创建的数据库权限角色”。fileciteturn0file5L396-L427

第四，这也意味着当前权限设计只保证：

> “一个销售数据库用户能做什么”。

暂时不能保证：

> “登录的销售用户一定只能以 Employee 表中自己的 employee_id 创建订单”。

这种“数据库登录身份 ↔ 具体员工记录”的绑定属于更进一步的应用身份/存储过程设计，不需要第四周硬做。

第五，**会员继续不创建 SQL Server 数据库角色**。第一周业务上确实把会员定义为可以查看自己的订单和预订的系统角色。fileciteturn0file4L79-L91 但目前如果简单执行：

```sql
GRANT SELECT ON SalesOrder TO dbrole_member;
```

会员就可能看到别人的订单。因此当前 v0.1 更合理的说明是：

> 会员属于应用层业务角色。第一阶段暂不直接向会员开放数据库表权限；“只能访问本人数据”将在后续应用层或更细粒度的数据访问机制中实现。

这样不但不是遗漏，反而能解释为什么**数据库权限角色和业务角色并非机械的一一对应**。

# 三、多表连接与经营统计查询

## 3.1 查询设计原则

`04_query.sql` 中的查询并非单纯为了展示 SQL 语法，而是围绕店铺实际可能关心的经营问题设计。

查询覆盖：

- `INNER JOIN`
- `LEFT JOIN`
- 多表连接
- 聚合函数
- `GROUP BY`
- `HAVING`
- 计算字段
- 子查询

对于销售相关统计，只统计状态为：

```text
COMPLETED
```

的订单，避免尚未完成或已取消的订单被错误计入实际经营数据。

销售金额统一根据销售订单明细中的历史成交单价计算，而不是使用商品当前售价，从而避免商品后续调价影响历史交易统计。

---

## 3.2 完整销售订单明细查询

第一类查询用于查看完整销售订单信息。

连接的主要数据表包括：

```text
SalesOrder
SalesOrderItem
Product
Employee
Member
```

查询结果能够展示：

- 订单编号；
- 订单类型；
- 订单状态；
- 成交时间；
- 会员信息；
- 收银员工；
- 商品；
- 商品数量；
- 历史成交单价；
- 订单明细金额。

其中会员表采用 `LEFT JOIN`。

原因是普通非会员顾客也可以进行现货购买，此时：

```text
SalesOrder.member_id = NULL
```

如果使用普通 `INNER JOIN Member`，这些非会员订单会从查询结果中消失。

---

## 3.3 商品累计销量与销售额

第二类查询统计每种商品的：

```text
累计销量
累计销售额
```

分别通过：

```text
SUM(quantity)
```

以及：

```text
SUM(quantity × unit_price)
```

计算。

查询从商品表出发并使用外连接，因此即使某个商品暂时没有任何销售记录，也可以继续显示在统计结果中，其销量和销售额为 0。

这种设计使统计结果能够反映全部商品，而不是只显示“已经卖出去的商品”。

---

## 3.4 按 IP 统计销售表现

为了体现二次元周边商品店的业务特点，进一步按照作品或 IP 统计：

- 累计销量；
- 累计销售额。

其主要连接关系为：

```text
AnimeIP
    ↓
Product
    ↓
SalesOrderItem
    ↓
SalesOrder
```

该查询可以用于观察不同作品/IP相关商品的整体销售表现。

---

## 3.5 按商品类别统计销售表现

除了按 IP 分析，还保留了普通零售业务中较常见的商品类别统计。

例如可以分别比较：

```text
徽章
亚克力制品
玩偶
色纸
```

等类别的累计销量和销售额。

因此，IP统计和商品类别统计分别从“作品属性”和“商品形态”两个不同角度分析销售数据。

---

## 3.6 会员消费统计

会员消费查询统计每位会员：

- 已完成订单数量；
- 累计消费金额。

查询从 `Member` 表出发，并使用 `LEFT JOIN` 连接销售订单。

因此即使某位会员已经注册但暂时没有消费记录，也仍然会出现在结果中。

对于一张订单包含多个商品的情况，订单数使用：

```text
COUNT(DISTINCT order_id)
```

避免一笔多商品订单被重复统计为多笔消费。

---

## 3.7 库存不足查询

库存查询根据：

```text
available_qty
=
on_hand_qty - reserved_qty
```

实时计算可销售库存。

然后筛选：

```text
available_qty <= reorder_point
```

得到当前达到或低于补货警戒值的商品。

该查询能够直接支持库存检查和人工补货判断。

---

## 3.8 当前预售有效需求查询

预售统计根据预订状态计算当前仍然有效的预订需求。

当前有效需求主要统计：

```text
reservation_status = 'ACTIVE'
```

的预订数量。

查询同时展示：

```text
decision_demand_qty
extra_stock_qty
planned_purchase_qty
```

从而可以区分：

```text
当前实时有效需求
```

和：

```text
店长当时进行采购决策时保存的需求历史快照
```

两种不同含义的数据。

---

## 3.9 HAVING 查询

为验证对分组后结果进行筛选，设计了累计销量达到指定阈值的商品查询。

例如：

```text
累计销量 >= 2
```

这里的筛选条件作用于：

```text
SUM(quantity)
```

而不是某一条订单明细，因此使用：

```sql
HAVING
```

而不是普通 `WHERE`。

---

## 3.10 子查询

设计了“累计消费金额高于会员平均累计消费金额”的会员查询。

查询首先得到每位有消费记录会员的累计消费金额，再计算这些会员累计消费金额的平均值，最后筛选高于平均水平的会员。

该查询用于验证嵌套统计和子查询的使用。

# 五、完整性约束补充与验证

## 5.1 处理原则

数据库在前期建表时已经建立了大量：

```text
PRIMARY KEY
UNIQUE
FOREIGN KEY
NOT NULL
DEFAULT
CHECK
```

约束。

第四周没有重复建立这些约束，而是重点检查其实际效果，并根据已有业务规则补充明显遗漏。

---

## 5.2 新增订金退款约束

原数据库已经规定：

```text
deposit_paid >= 0

deposit_refunded >= 0
```

但原有约束尚未限制：

```text
deposit_refunded
```

不能超过：

```text
deposit_paid
```

因此补充：

```text
deposit_refunded <= deposit_paid
```

对应约束：

```text
CK_PresaleReservation_RefundNotExceedPaid
```

该约束用于防止出现例如：

```text
实际支付订金 = 20
实际退款金额 = 30
```

这样的明显不合理数据。

## 6.2 非法数据测试

第四周主要完成以下六项反例测试：

### T1 商品售价为负数

测试：

```text
sale_price = -10
```

预期由商品售价 `CHECK` 约束拒绝。

### T2 预留库存超过实际库存

测试：

```text

```

预期由：

```text
reserved_qty <= on_hand_qty
```

对应的库存约束拒绝。

---

### T3 重复商品业务编号

数据库中已经存在：

```text
product_code = 'P001'
```

再次插入相同业务编号。

预期由 `UNIQUE` 约束拒绝。

---

### T4 引用不存在的商品类别

插入商品时使用数据库中不存在的：

```text
category_id
```

预期由商品类别外键拒绝。

---

### T5 商品 IP 与角色不一致

测试组合：

```text
ip_id = 原神
character_id = 三月七
```

其中：

```text
原神
```

本身存在，

```text
三月七
```

本身也存在，

但三月七属于另一个 IP。

因此单独检查 `ip_id` 和 `character_id` 都无法发现错误。

数据库通过：

```text
(character_id, ip_id)
```

复合外键保证角色和 IP 必须属于同一条角色记录，从而拒绝该错误组合。

这是本项目中较有业务特点的一项完整性验证。

---

### T6 退款金额超过实际支付订金

测试：

```text
deposit_paid = 20
deposit_refunded = 30
```

预期由第四周新增的：

```text
CK_PresaleReservation_RefundNotExceedPaid
```

约束拒绝。

---

## 6.3 测试组织方式

所有非法测试统一采用：

```text
BEGIN TRY
    执行预期失败的 SQL
END TRY

BEGIN CATCH
    捕获数据库约束错误
END CATCH
```

测试结果明确输出：

```text
[PASS]
```

或者：

```text
[FAIL]
```

并显示数据库返回的具体错误信息。

同时，各测试使用独立测试编号，并放在事务中执行。

测试结束后统一：

```text
ROLLBACK
```

因此完整性验证不会污染正式样例数据，也能够重复执行。

# 七、数据库角色与权限划分

## 7.1 数据库角色

根据店铺内部员工职责，目前创建三个 SQL Server 数据库角色：

```text
dbrole_sales_clerk
dbrole_inventory_manager
dbrole_store_manager
```

分别对应：

```text
销售 / 收银店员
库存管理员
店长 / 管理员
```

数据库权限角色与业务数据表中的：

```text
BusinessRole
```

概念相关，但并不是同一个对象。

`BusinessRole` 用于记录现实经营中的员工角色，而 SQL Server 数据库角色用于真正控制数据库访问权限。

---

## 7.2 销售 / 收银店员权限

销售店员主要具有：

- 查看商品；
- 查看库存状态；
- 查看订单详情；
- 查询、登记和修改会员；
- 查看预售活动和预订；
- 创建销售订单；
- 创建销售订单明细；
- 完成订单；
- 更新预售提货相关状态。

销售店员不能：

- 直接修改库存数量；
- 管理供应商；
- 创建或修改采购订单；
- 管理员工。

---

## 7.3 库存管理员权限

库存管理员主要具有：

- 查询商品；
- 查询库存；
- 修改实际库存、预留库存和补货警戒值；
- 查看采购订单；
- 查看采购明细；
- 登记采购到货时间和验收员工；
- 更新采购订单验收状态；
- 登记实际到货数量。

库存管理员不能：

- 查看会员个人数据；
- 创建销售订单；
- 决定采购内容；
- 管理员工信息。

---

## 7.4 店长 / 管理员权限

店长具有相对完整的经营管理权限，包括：

- 商品类别管理；
- IP 和角色资料管理；
- 商品管理；
- 员工和经营角色管理；
- 供应商管理；
- 预售活动管理；
- 采购订单及采购明细管理；
- 查看库存；
- 查看会员；
- 查看销售数据；
- 查看经营统计视图。

店长可以制定：

```text
reorder_point
```

但当前设计中，日常实际库存数量仍主要由库存管理员维护。

虽然店长权限较高，但仍未直接授予：

```text
db_owner
```

等数据库全权限角色，而是根据业务对象逐项授权。

# 十一、会员权限的阶段性处理

在业务设计中，会员可以查看自己的订单和预订信息。

但当前第四周没有直接为会员创建 SQL Server 数据库角色。

原因是简单授予：

```text
SalesOrder
PresaleReservation
```

表级查询权限后，会员可能获得查看其他会员数据的能力，与“只能访问本人数据”的业务要求冲突。

因此当前阶段将会员视为应用层业务角色：

```text
会员
→ 后续通过应用程序或更细粒度访问机制访问本人数据
```

而不是：

```text
会员
→ 直接登录数据库并查询基础表
```

第四周 SQL Server 权限设计主要针对店铺内部员工。
