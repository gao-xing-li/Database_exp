# Database_exp —— 二次元周边商品店数据库实验（第 1–4 周阶段）

本项目是《数据库原理》课程的数据库实验作业，围绕一家**小型线下二次元周边商品店**，完成从业务需求分析、关系模式设计到 SQL Server 数据库实现、查询统计、完整性验证与权限管理的完整第一阶段闭环。

------

## 一、项目范围说明

### 1.1 经营场景

店铺主要销售徽章、亚克力立牌、挂件、色纸、玩偶等二次元周边商品，采用**单门店线下现货销售**为主、**会员预售**为辅的经营模式：

- 商品由店铺从不同供应商处采购，到货后验收并纳入库存管理；
- 顾客可直接到店购买现货，也可注册成为会员；
- 会员除普通现货购买外，还可参加商品预售（支付订金 → 到货后补尾款提货）；
- 商品不固定划分为"预售商品"和"现货商品"，同一商品可在不同经营阶段采用不同销售方式。

### 1.2 纳入系统管理的业务

- 商品管理（类别、IP、角色、价格）；
- 库存管理（实际库存、预留库存、补货警戒值）；
- 会员管理；
- 员工与经营角色管理；
- 现货销售与销售订单管理；
- 预售活动、预订、取消与提货管理；
- 采购（普通补货 + 预售采购）与到货验收管理。

### 1.3 暂不纳入范围的内容

线上商城、购物车、物流配送、多门店及连锁经营、跨门店调拨、售后退换货、复杂营销活动、财务会计、自动采购/推荐算法、一次预订的部分取消或部分提货等（详见 `第1-4周业务产出/第一周 业务设计.md` 第十五节）。

### 1.4 数据库环境

- **DBMS**：Microsoft SQL Server
- **数据库名**：`AnimeGoodsStoreDB`
- **数据表数量**：15 张（ProductCategory、AnimeIP、CharacterInfo、Product、Inventory、Member、BusinessRole、Employee、Supplier、SalesOrder、SalesOrderItem、PresaleActivity、PresaleReservation、PurchaseOrder、PurchaseOrderItem）

## 二、业务角色及其职责

### 系统角色（店铺内部员工，对应 SQL Server 数据库角色）

| 业务角色 | 数据库角色 | 主要职责 |
| --- | --- | --- |
| **店长 / 管理员** | `dbrole_store_manager` | 管理商品、员工、供应商信息；决定预售商品及起止时间；确定采购和补货数量；制定额外备货策略；查看销售、库存和经营统计。具有相对完整的数据管理权限 |
| **销售 / 收银店员** | `dbrole_sales_clerk` | 查询商品及可售库存；完成现货结账；创建销售订单；查询和维护会员信息；确认预售提货、完成尾款结算。不负责采购决策和员工管理 |
| **库存管理员** | `dbrole_inventory_manager` | 商品到货验收与入库；库存盘点；检查库存不足情况；维护实际库存、预留库存和补货警戒值；登记采购验收结果。不接触会员个人数据和销售订单 |

### 系统用户（不设 SQL Server 数据库角色）

| 角色 | 说明 |
| --- | --- |
| **会员** | 可购买现货、参与预售、取消自己的预订、查看本人订单和预订状态、到货后支付尾款并提货。只能访问与本人相关的数据，第一阶段作为应用层业务角色处理，不直接授予基础表权限 |

### 外部业务参与者（不拥有系统账号）

| 角色 | 说明 |
| --- | --- |
| **普通顾客** | 到店浏览并购买现货，无需系统账号，不参与会员专属预售业务 |
| **供应商** | 向店铺供货，其信息和采购关系由店铺员工记录维护，不登录系统、不作为权限设计中的系统角色 |

## 三、核心业务流程梳理

### 3.1 现货销售流程

```
顾客选择商品
→ 店员查询 Inventory 并计算可售库存（available_qty = on_hand_qty - reserved_qty）
→ 创建 SalesOrder（CREATED）及 SalesOrderItem（保存历史成交单价 unit_price）
→ 结账完成，SalesOrder → COMPLETED 并记录 order_time
→ Inventory.on_hand_qty 减少
```

一笔订单可包含多种商品；会员购买同时形成消费记录；普通顾客 `member_id = NULL`。

### 3.2 预售业务流程

```
店长开展预售（PresaleActivity：单价、订金、起止时间）
→ 会员在预售期内整体预订并支付订金（PresaleReservation）
→ 截止前可整体取消（全额退订金）；截止后可整体取消（订金不退）
→ 预售截止，汇总有效预订需求（decision_demand_qty 历史快照）
→ 店长确定额外备货量（extra_stock_qty），得出计划采购量（planned_purchase_qty）
→ 创建 PRESALE 类型采购订单，统一向供应商采购
→ 商品到货，库存管理员验收入库
→ 有效预订数量进入 reserved_qty（预留库存）
→ 会员在期限内到店：店员确认预订 → 支付尾款 → 生成 PRESALE 销售订单 → 整体提货
→ on_hand_qty 与 reserved_qty 同时减少，预订状态 → PICKED_UP
```

关键规则：

- **一次预订整体处理**：只支持整体取消、整体提货；
- **一条预订对应一笔预售提货订单**：通过 `(reservation_id, member_id)` 复合外键与 `UNIQUE(reservation_id)` 过滤唯一索引保证；
- **超过最晚提货期限**：预订 → EXPIRED，订金不退，预留商品释放回普通现货库存（`reserved_qty` 减少）；
- **剩余商品转现货**：额外备货 + 采购后取消 + 逾期未提货产生的多余商品进入普通现货库存继续销售。

### 3.3 普通补货流程

```
商品销售使库存下降
→ 可售库存达到或低于 reorder_point（库存状态视图判定为 LOW_STOCK / OUT_OF_STOCK）
→ 库存管理员发现库存不足，提出补货需求
→ 店长决定采购数量，形成 RESTOCK 类型采购订单
→ 供应商到货 → 验收（received_time / received_by / received_qty）
→ Inventory.on_hand_qty 增加
```

项目不单独建立"补货申请表"，采购订单即最终实际执行的补货决策。

### 3.4 总体业务闭环

- **现货业务**：采购 → 到货验收入库 → 现货库存 → 顾客购买 → 销售订单 → 库存减少 → 库存不足 → 再次补货；
- **预售业务**：开展预售 → 会员整体预订付订金 → 截止前取消退订金 / 截止后取消不退 → 汇总有效需求 + 额外备货 → 统一采购 → 到货验收 → 会员期限内付尾款整体提货 → 剩余商品转普通现货。

跨表流程类规则（如库存联动、订金自动核算、状态机迁移等）当前由样例数据和业务流程保持一致，完整清单见 `后续阶段待实现业务规则.md`，计划在后续事务、存储过程与触发器阶段实现。

## 四、数据库脚本执行顺序

全部脚本位于 `第1-4周业务产出/` 目录，必须按编号顺序执行：

| 顺序 | 脚本 | 作用 |
| --- | --- | --- |
| 1 | `00_create_database.sql` | 数据库不存在时创建 `AnimeGoodsStoreDB`，已存在则直接复用 |
| 2 | `01_create_tables.sql` | 按外键依赖逆序删除已有视图和 15 张业务表，重新建表并创建主键、唯一、外键、非空、默认值、CHECK 约束（**会清空业务表数据**） |
| 3 | `02_insert_sample_data.sql` | 导入覆盖商品、库存、会员、员工、供应商、销售、预售、采购的样例数据 |
| 4 | `03_crud.sql` | 使用独立测试编号（9001 系列）演示商品、库存、销售订单的增删改查，结束后清理临时数据 |
| 5 | `04_query.sql` | 多表连接（INNER/LEFT JOIN）、聚合、GROUP BY、HAVING、子查询等经营统计查询 |
| 6 | `05_view.sql` | 创建 4 个统计视图：`vw_OrderDetail`、`vw_ProductSalesSummary`、`vw_InventoryStatus`、`vw_MemberConsumptionSummary` |
| 7 | `06_constraint.sql` | 补充订金退款等约束，并执行 14 组非法数据反例测试（T1–T14，按预期错误号与约束名判定） |
| 8 | `07_role.sql` | 创建 3 个数据库角色、按最小权限授权、创建 WITHOUT LOGIN 测试用户，执行 3 组正常权限测试（P1–P3）与 3 组越权测试（N1–N3） |

**执行顺序说明**：

- 该执行链采用**确定性重建**方式，首次运行与已有数据库上的完整链重复运行均按同一顺序执行，无需额外 reset 脚本；
- 重新执行 `01` 会清空业务表数据回到样例初始状态；若希望保留已有业务数据，不要从 `01` 开始重建；
- `05` 使用 `CREATE OR ALTER VIEW`，`06` 的补充约束、`07` 的角色和测试用户均带存在性判断，可重复执行。

## 五、实验复现步骤

### 5.1 环境准备

1. 安装 **Microsoft SQL Server**（任一受支持的版本，如 Developer / Express Edition）；
2. 安装 **SQL Server Management Studio（SSMS）** 或其他可执行 T-SQL 脚本的客户端。

### 5.2 完整复现流程

1. **克隆 / 下载本仓库**，进入 `第1-4周业务产出/` 目录；
2. **打开 SSMS**，连接到本地 SQL Server 实例；
3. **按第四节顺序依次打开并执行脚本**（每个脚本可整体执行，脚本内部使用 `GO` 分批）：

   ```
   00_create_database.sql
   01_create_tables.sql
   02_insert_sample_data.sql
   03_crud.sql
   04_query.sql
   05_view.sql
   06_constraint.sql
   07_role.sql
   ```

4. **核验执行结果**：
   - `03` 执行后：商品、库存、销售订单 CRUD 各步骤均正常，测试编号 9001 数据已被清理；
   - `04` 执行后：可看到完整订单明细、商品/IP/类别销量统计、会员消费统计、库存不足查询、预售有效需求查询等结果；
   - `05` 执行后：`SELECT * FROM dbo.vw_InventoryStatus;` 等视图可正常查询；
   - `06` 执行后：T1–T14 反例测试全部输出 `[PASS]`（因预期约束拒绝），正例测试成功；
   - `07` 执行后：P1–P3 正常权限测试输出 `[PASS]`，N1–N3 越权测试输出 `[PASS]`（错误号 229，权限拒绝）。

### 5.3 重复运行说明

- 需要回到**确定的课程样例初始状态**时，从 `00 → 01` 开始完整重跑执行链即可；
- `02` 与 `03` 按阶段链使用，不设计为脱离 `01` 在任意业务数据状态下单独反复初始化。
