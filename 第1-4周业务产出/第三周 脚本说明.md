# 二次元周边商品店数据库——第三周 DDL 与数据修改说明

## 一、本周目标

第三周主要完成数据库的初步实现工作。

在第一周业务需求分析和第二周关系模式设计的基础上，将已经确定的数据表、字段、主码、候选码、外码和字段取值范围实际转换为 SQL Server 中可运行的数据库结构，并加入能够体现业务关系的样例数据。

本周主要完成以下内容：

1. 创建二次元周边商品店数据库；
2. 根据第二周设计创建 15 张数据表；
3. 建立主键、唯一约束、外键、非空约束、默认值和检查约束；
4. 插入能够体现商品、库存、销售、预售和采购关系的样例数据；
5. 对商品、库存和销售订单进行典型的增、删、改、查操作；
6. 验证全部脚本能够按照规定顺序正常运行。

本周主要关注数据库结构和基础数据操作，不涉及第四周的多表统计查询、视图和数据库角色权限，也暂不实现触发器、存储过程以及自动库存处理等后续功能。

## 二、数据库与数据表

本项目数据库名称为：

```
AnimeGoodsStoreDB
```

根据第二周关系模式设计，本周共创建 15 张数据表：

| 表名               | 主要用途        |
| ------------------ | --------------- |
| ProductCategory    | 商品类别        |
| AnimeIP            | 作品 / IP       |
| CharacterInfo      | IP 中的具体角色 |
| Product            | 商品基本信息    |
| Inventory          | 商品当前库存    |
| Member             | 会员信息        |
| BusinessRole       | 员工经营角色    |
| Employee           | 员工信息        |
| Supplier           | 供应商信息      |
| SalesOrder         | 销售订单        |
| SalesOrderItem     | 销售订单明细    |
| PresaleActivity    | 预售活动        |
| PresaleReservation | 会员预售预订    |
| PurchaseOrder      | 采购订单        |
| PurchaseOrderItem  | 采购订单明细    |

表之间通过主键和外键建立业务联系。

例如：

- 商品属于一个商品类别；
- 商品可以属于某个 IP，并可以对应一个具体角色；
- 每个商品最多有一条当前库存记录；
- 销售订单可以对应会员，并由员工进行结账；
- 销售订单通过订单明细关联具体商品；
- 预售活动对应某个商品；
- 会员通过预售预订参加预售活动；
- 采购订单对应供应商，并通过采购明细记录具体采购商品。

## 三、SQL 脚本组成

第三周目前包含四个主要 SQL 文件。

### 1. `00_create_database.sql`

用于创建数据库：

```
AnimeGoodsStoreDB
```

如果数据库已经存在，则直接复用现有数据库，不重复创建。业务表和视图的重建由下一步 `01_create_tables.sql` 统一处理。

脚本完成数据库创建或复用后切换到该数据库，为后续建表做好准备。

### 2. `01_create_tables.sql`

根据第二周确定的关系模式创建全部 15 张数据表。为了兼容已有数据库上的完整链重复运行，脚本会先删除本项目已有的统计视图，再按外键依赖的逆序删除 15 张业务表，随后重新创建表结构。

因此该脚本既可以用于首次建表，也可以作为课程实验中的“模式重建入口”。重新执行会清空这些业务表中的现有数据，以保证后续样例数据和测试从确定的初始状态开始。

脚本中实现了以下主要完整性约束：

- `PRIMARY KEY`：保证每张表中的主要标识唯一；
- `UNIQUE`：保证商品编号、订单编号、会员编号等业务编号不重复；
- `FOREIGN KEY`：保证不同表之间引用的数据真实存在；
- `NOT NULL`：保证必要业务字段必须填写；
- `DEFAULT`：为状态、时间和部分数值字段设置合理默认值；
- `CHECK`：限制价格、数量、状态等字段的合法取值范围。

例如：

- 商品售价必须大于 0；
- 库存数量不能为负数；
- 预留库存不能超过实际库存；
- 销售数量和采购数量必须大于 0；
- 实际到货数量不能超过采购数量；
- 商品状态只能取 `PENDING`、`ON_SALE` 或 `STOPPED`；
- 订单状态只能取规定的状态值。

此外，对商品的 IP 和角色关系进行了组合约束，防止出现角色与所属 IP 不一致的数据。

对于销售订单中的 `reservation_id`，普通现货订单允许其为 `NULL`，而同一条非空预售预订最多只能对应一笔预售提货订单，因此使用了过滤唯一索引实现这一规则。

### 3. `02_insert_sample_data.sql`

用于向数据库中插入样例数据。

样例数据覆盖：

- 商品类别；
- IP 与角色；
- 商品；
- 库存；
- 会员；
- 员工与经营角色；
- 供应商；
- 普通销售订单；
- 预售活动和预订；
- 普通补货和预售采购。

第二周已有的核心样例数据继续保留，同时增加少量测试数据，使后续能够进行更有意义的连接查询、销售统计、库存统计和会员消费统计。

样例数据之间并不是相互独立的。

例如，一笔销售订单会对应真实存在的商品和员工；预售提货订单会关联对应的预订记录；预售采购会关联相应的预售活动；采购明细中的商品也必须在商品表中真实存在。

### 4. `03_crud.sql`

该脚本用于展示商品、库存和销售订单相关数据的基本 CRUD 操作。

CRUD 分别表示：

```
Create：新增
Read：查询
Update：修改
Delete：删除
```

为了避免修改正式样例数据，CRUD 测试使用独立的测试编号，例如：

```
product_id = 9001
order_id = 9001
```

测试结束后会删除这些临时数据，因此不会影响原有业务样例。

## 四、主要 CRUD 实验

### 1. 商品 CRUD

首先新增一件测试商品，并查询确认商品已经成功写入。

随后修改：

- 商品名称；
- 商品售价。

修改前先使用相同的 `WHERE` 条件进行查询，确认需要修改的目标记录，修改后再次查询并比较结果。

最后删除该测试商品。

由于商品存在对应库存记录，因此删除时必须先删除：

```
Inventory
```

中的库存记录，再删除：

```
Product
```

中的商品记录。

该过程同时验证了数据库外键关系对删除顺序的限制。

### 2. 库存 CRUD

为测试商品建立库存记录，设置：

- 实际库存；
- 预留库存；
- 补货警戒值。

随后查询库存，并通过：

```
available_qty = on_hand_qty - reserved_qty
```

计算当前可销售库存。

之后修改实际库存和补货警戒值，并再次查询确认修改结果。

库存测试数据最终随测试商品一起删除。

### 3. 销售订单 CRUD

创建一笔测试普通现货订单，初始状态设置为：

```
CREATED
```

随后增加订单明细，并通过连接查询查看：

- 订单编号；
- 商品；
- 数量；
- 历史成交单价；
- 当前订单金额。

在订单仍处于 `CREATED` 状态时，先测试修改订单明细中的购买数量并确认明细内容；随后再将订单状态由：

```
CREATED
```

修改为：

```
COMPLETED
```

并记录实际交易时间。这样 CRUD 演示顺序与“先确认明细、再完成交易”的业务语义保持一致。

删除订单时，由于 `SalesOrderItem` 通过外键引用 `SalesOrder`，需要先删除订单明细，再删除销售订单。

## 五、数据完整性设计说明

本周尽可能将第二周确定的单表业务规则落实到了数据库约束中。

例如：

```
sale_price > 0
quantity > 0
ordered_qty > 0
received_qty >= 0
received_qty <= ordered_qty
reserved_qty >= 0
reserved_qty <= on_hand_qty
```

这些规则都能够直接通过 `CHECK` 约束表达。

同时，主键、候选码和外键也在数据库中实际建立，而不是仅在设计文档中描述。

部分规则需要跨表比较、状态迁移或库存联动，不适合在第一阶段通过简单声明式约束强行实现。当前由样例数据和业务流程保持一致，后续计划结合事务、存储过程和触发器等内容实现；完整清单统一记录在 `后续阶段待实现业务规则.md` 中。

## 六、脚本执行顺序

首次运行以及已有数据库上的完整链重复运行，都按照以下顺序执行：

```
00_create_database.sql
        ↓
01_create_tables.sql
        ↓
02_insert_sample_data.sql
        ↓
03_crud.sql
```

各脚本作用分别为：

```
创建或复用数据库
        ↓
重建表结构和基础约束
        ↓
导入业务样例数据
        ↓
执行 CRUD 测试
```

当前执行链采用确定性重建方式：数据库不存在时由 `00` 创建；数据库已经存在时由 `00` 复用，随后 `01` 重建本项目表结构。这样无需额外的 reset 脚本，同一套执行顺序即可覆盖首次运行和完整链再次运行。

`02_insert_sample_data.sql` 和 `03_crud.sql` 仍按阶段链使用，不设计为脱离 `01` 后在任意已有业务数据状态下单独反复初始化；需要重新得到课程样例初始状态时，应从 `00 → 01` 开始完整执行。

因此数据库能够完成从数据库创建/复用、表结构重建、样例数据导入到基础数据修改操作的完整流程。
