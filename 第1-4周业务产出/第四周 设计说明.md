# 二次元周边商品店数据库——第四周连接、视图、完整性与授权说明

## 一、本周目标

第四周在已经建立的二次元周边商品店数据库结构和样例数据基础上，进一步完善数据库的数据查询、统计分析、完整性验证和访问权限控制能力。

本周不新增业务范围，也不新增核心业务实体，主要围绕已有的商品、库存、会员、销售订单、预售和采购等数据开展以下工作：

1. 编写具有明确业务含义的多表连接查询；
2. 使用聚合、`GROUP BY`、`HAVING` 和子查询完成经营统计；
3. 将部分需要反复使用的查询封装为数据库视图；
4. 检查已有完整性约束，并补充必要的数据约束；
5. 使用合法数据和非法数据验证完整性约束是否真正生效；
6. 根据店铺经营角色建立 SQL Server 数据库角色；
7. 按照最小权限原则分配数据库访问权限；
8. 使用测试用户验证正常操作能够执行、越权操作会被拒绝。

本周重点不在扩展数据库规模，而在于使已有数据库能够更方便地回答经营问题，并通过执行结果证明数据规则和权限划分确实生效。

# 三、多表连接与经营统计查询

## 3.1 查询设计原则

`04_query.sql` 中的查询并非单纯为了展示 SQL 语法，而是围绕店铺实际可能关心的经营问题设计。

查询覆盖：

- `INNER JOIN`
- `LEFT JOIN`
- 多表连接
- 聚合函数
- `GROUP BY`
- `HAVING`
- 计算字段
- 子查询

对于销售相关统计，只统计状态为：

```
COMPLETED
```

的订单，避免尚未完成或已取消的订单被错误计入实际经营数据。

销售金额统一根据销售订单明细中的历史成交单价计算，而不是使用商品当前售价，从而避免商品后续调价影响历史交易统计。

------

## 3.2 完整销售订单明细查询

第一类查询用于查看完整销售订单信息。

连接的主要数据表包括：

```
SalesOrder
SalesOrderItem
Product
Employee
Member
```

查询结果能够展示：

- 订单编号；
- 订单类型；
- 订单状态；
- 成交时间；
- 会员信息；
- 收银员工；
- 商品；
- 商品数量；
- 历史成交单价；
- 订单明细金额。

其中会员表采用 `LEFT JOIN`。

原因是普通非会员顾客也可以进行现货购买，此时：

```
SalesOrder.member_id = NULL
```

如果使用普通 `INNER JOIN Member`，这些非会员订单会从查询结果中消失。

------

## 3.3 商品累计销量与销售额

第二类查询统计每种商品的：

```
累计销量
累计销售额
```

分别通过：

```
SUM(quantity)
```

以及：

```
SUM(quantity × unit_price)
```

计算。

查询从商品表出发并使用外连接，因此即使某个商品暂时没有任何销售记录，也可以继续显示在统计结果中，其销量和销售额为 0。

这种设计使统计结果能够反映全部商品，而不是只显示“已经卖出去的商品”。

------

## 3.4 按 IP 统计销售表现

为了体现二次元周边商品店的业务特点，进一步按照作品或 IP 统计：

- 累计销量；
- 累计销售额。

其主要连接关系为：

```
AnimeIP
    ↓
Product
    ↓
SalesOrderItem
    ↓
SalesOrder
```

该查询可以用于观察不同作品/IP相关商品的整体销售表现。

------

## 3.5 按商品类别统计销售表现

除了按 IP 分析，还保留了普通零售业务中较常见的商品类别统计。

例如可以分别比较：

```
徽章
亚克力制品
玩偶
色纸
```

等类别的累计销量和销售额。

因此，IP统计和商品类别统计分别从“作品属性”和“商品形态”两个不同角度分析销售数据。

------

## 3.6 会员消费统计

会员消费查询统计每位会员：

- 已完成订单数量；
- 累计消费金额。

查询从 `Member` 表出发，并使用 `LEFT JOIN` 连接销售订单。

因此即使某位会员已经注册但暂时没有消费记录，也仍然会出现在结果中。

对于一张订单包含多个商品的情况，订单数使用：

```
COUNT(DISTINCT order_id)
```

避免一笔多商品订单被重复统计为多笔消费。

------

## 3.7 库存不足查询

库存查询根据：

```
available_qty
=
on_hand_qty - reserved_qty
```

实时计算可销售库存。

然后筛选：

```
available_qty <= reorder_point
```

得到当前达到或低于补货警戒值的商品。

该查询能够直接支持库存检查和人工补货判断。

------

## 3.8 当前预售有效需求查询

预售统计根据预订状态计算当前仍然有效的预订需求。

当前有效需求主要统计：

```
reservation_status = 'ACTIVE'
```

的预订数量。

查询同时展示：

```
decision_demand_qty
extra_stock_qty
planned_purchase_qty
```

从而可以区分：

```
当前实时有效需求
```

和：

```
店长当时进行采购决策时保存的需求历史快照
```

两种不同含义的数据。

------

## 3.9 HAVING 查询

为验证对分组后结果进行筛选，设计了累计销量达到指定阈值的商品查询。

例如：

```
累计销量 >= 2
```

这里的筛选条件作用于：

```
SUM(quantity)
```

而不是某一条订单明细，因此使用：

```
HAVING
```

而不是普通 `WHERE`。

------

## 3.10 子查询

设计了“累计消费金额高于会员平均累计消费金额”的会员查询。

查询首先得到每位有消费记录会员的累计消费金额，再计算这些会员累计消费金额的平均值，最后筛选高于平均水平的会员。

该查询用于验证嵌套统计和子查询的使用。

------

# 四、统计视图

第四周进一步将部分高频查询封装为数据库视图。

目前建立四个视图：

```
vw_OrderDetail
vw_ProductSalesSummary
vw_InventoryStatus
vw_MemberConsumptionSummary
```

------

## 4.1 `vw_OrderDetail`

订单详情视图封装：

```
SalesOrder
SalesOrderItem
Product
Employee
Member
```

之间的连接关系。

以后需要查看某笔订单时，可以直接查询：

```
SELECT *
FROM dbo.vw_OrderDetail;
```

而不需要每次重新编写多表连接。

------

## 4.2 `vw_ProductSalesSummary`

商品销售统计视图提供：

- 商品编号；
- 商品名称；
- 累计销量；
- 累计销售额。

只有已完成订单进入实际销售统计。

同时，没有产生销售记录的商品仍然保留在结果中。

该视图主要用于后续商品经营分析。

------

## 4.3 `vw_InventoryStatus`

库存状态视图在基础库存字段之上计算：

```
available_qty
=
on_hand_qty - reserved_qty
```

并进一步将库存状态划分为：

```
OUT_OF_STOCK
LOW_STOCK
NORMAL
```

其中：

```
available_qty = 0
→ OUT_OF_STOCK

available_qty <= reorder_point
→ LOW_STOCK

其他情况
→ NORMAL
```

因此应用或员工无需每次重复编写库存状态判断逻辑。

------

## 4.4 `vw_MemberConsumptionSummary`

会员消费统计视图记录：

- 会员；
- 已完成订单数量；
- 累计消费金额。

没有产生消费记录的会员仍然保留，其统计值为 0。

该视图可以进一步用于查询高消费会员或尚未消费的会员。

# 五、完整性约束补充与验证

## 5.1 处理原则

数据库在前期建表时已经建立了大量：

```
PRIMARY KEY
UNIQUE
FOREIGN KEY
NOT NULL
DEFAULT
CHECK
```

约束。

第四周没有重复建立这些约束，而是重点检查其实际效果，并根据已有业务规则补充明显遗漏。

------

## 5.2 新增订金退款约束

原数据库已经规定：

```
deposit_paid >= 0

deposit_refunded >= 0
```

但原有约束尚未限制：

```
deposit_refunded
```

不能超过：

```
deposit_paid
```

因此补充：

```
deposit_refunded <= deposit_paid
```

对应约束：

```
CK_PresaleReservation_RefundNotExceedPaid
```

该约束只负责保证退款金额的基本数值关系；截止前全额退款、截止后不退款需要跨表比较预售截止时间，留到后续业务过程统一处理。

该约束用于防止出现例如：

```
实际支付订金 = 20
实际退款金额 = 30
```

这样的明显不合理数据。

------

## 5.3 结构约束复核

在阶段整合复核中，将几项能够直接用声明式约束表达的业务关系补回建表脚本，包括：

- `COMPLETED` 销售订单必须记录 `order_time`；
- `CANCELLED` 预订必须记录 `cancelled_at`，其他状态不记录取消时间；
- 预售提货订单的会员必须与对应预订会员一致；
- `RECEIVED` 采购订单与验收时间、验收员工保持一致；
- 最晚提货期限晚于预售结束时间；
- 每件订金不超过预售价；
- 预计到货时间、实际验收时间不早于采购下单时间。

这些规则均已在 `01_create_tables.sql` 中落实，并在本周反例测试中验证。仍需跨表流程或事务才能强制的规则统一记录在 `后续阶段待实现业务规则.md`。

数据库中已经存在：


### T4 引用不存在的商品类别

### T5 商品 IP 与角色不一致

测试组合：

```

```

```
原神
```

本身存在，

```

```

本身也存在，

但三月七属于另一个 IP。

### T7–T14 结构一致性反例

进一步针对阶段整合后补充的约束验证：

- T7：每件订金高于预售价；
- T8：最晚提货期限早于预售结束时间；
- T9：`CANCELLED` 预订缺少 `cancelled_at`；

- T13：预计到货时间早于下单时间；
- T14：实际验收时间早于下单时间。

这些测试同样只有在预期约束或外键明确触发时才判定为通过。

------

## 6.3 测试组织方式

所有非法测试统一采用 `TRY...CATCH` 捕获数据库错误，但测试判定不再采用“只要 SQL 执行失败就视为通过”的方式。

当前判定原则为：

```
操作因预期的约束原因失败
→ [PASS]

操作成功，或因其他非预期原因失败
→ [FAIL]
```

具体检查数据库返回的 `ERROR_NUMBER()` 和 `ERROR_MESSAGE()`：

- 除 T3 外，T1–T14 的其余反例均要求错误号为 `547`，同时错误信息中必须出现本测试预期触发的 CHECK 或 FOREIGN KEY 约束名；
- T3 要求错误号为 `2601` 或 `2627`，同时错误信息中必须出现 `UQ_Product_ProductCode`；
- 若测试因为主键冲突、测试数据缺失、其他外键/检查约束等非预期原因失败，则输出 `[FAIL]`，并保留实际错误号和错误信息用于排查。

例如 T1 只有在错误明确来自：

```
CK_Product_SalePrice
```

时才判断为通过，而不能因为其他 SQL 错误导致插入失败就误判为约束验证成功。

同时，各测试使用独立测试编号，并放在事务中执行。测试结束后统一回滚：

```
ROLLBACK
```

因此完整性验证既不会污染正式样例数据，又能够区分“预期约束确实生效”和“代码因其他原因执行失败”两种情况。

# 七、数据库角色与权限划分

## 7.1 数据库角色

根据店铺内部员工职责，目前创建三个 SQL Server 数据库角色：

```
dbrole_sales_clerk
dbrole_inventory_manager
dbrole_store_manager
```

分别对应：

```
销售 / 收银店员
库存管理员
店长 / 管理员
```

数据库权限角色与业务数据表中的：

```
BusinessRole
```

概念相关，但并不是同一个对象。

`BusinessRole` 用于记录现实经营中的员工角色，而 SQL Server 数据库角色用于真正控制数据库访问权限。

------

## 7.2 销售 / 收银店员权限

销售店员主要具有：

- 查看商品；
- 查看库存状态；
- 查看订单详情；
- 查询、登记和修改会员；
- 查看预售活动和预订；
- 创建销售订单；
- 创建销售订单明细；
- 完成订单；
- 更新预售提货相关状态字段。

为支持按 `order_id` 定位需要处理的销售订单，额外授予 `SalesOrder.order_id` 的列级 `SELECT` 权限；完整订单信息仍通过 `vw_OrderDetail` 查询，以保持最小权限原则。

当前采用列级权限控制可修改范围，具体合法状态迁移路径将在后续存储过程/事务中进一步限制。

销售店员不能：

- 直接修改库存数量；
- 管理供应商；
- 创建或修改采购订单；
- 管理员工。

------

## 7.3 库存管理员权限

库存管理员主要具有：

- 查询商品；
- 查询库存；
- 修改实际库存、预留库存和补货警戒值；
- 查看采购订单；
- 查看采购明细；
- 登记采购到货时间和验收员工；
- 更新采购订单验收状态字段；
- 登记实际到货数量。

当前列级权限限制了可修改字段，但不负责判定完整的采购状态迁移路径；合法迁移规则留待后续数据库编程阶段统一处理。

库存管理员不能：

- 查看会员个人数据；
- 创建销售订单；
- 决定采购内容；
- 管理员工信息。

------

## 7.4 店长 / 管理员权限

店长具有相对完整的经营管理权限，包括：

- 商品类别管理；
- IP 和角色资料管理；
- 商品管理；
- 员工和经营角色管理；
- 供应商管理；
- 预售活动管理；
- 采购订单及采购明细管理；
- 查看库存；
- 查看会员；
- 查看销售数据；
- 查看经营统计视图。

店长可以制定：

```
reorder_point
```

但当前设计中，日常实际库存数量仍主要由库存管理员维护。

虽然店长权限较高，但仍未直接授予：

```
db_owner
```

等数据库全权限角色，而是根据业务对象逐项授权。

```

vw_ProductSalesSummary
vw_InventoryStatus
vw_MemberConsumptionSummary
```

这样可以让不同员工看到完成工作所需的信息，而不必为了查询统计结果获得所有相关基础表的完整权限。

# 十、越权访问测试

除了正常操作，还设计越权反例。

越权测试同样不采用“只要执行失败就视为通过”的判定方式。只有 SQL Server 明确返回权限拒绝错误，并且错误指向本次测试的目标对象时，才判断该测试通过。

当前三项测试统一要求：

```
ERROR_NUMBER() = 229
```

同时进一步检查错误信息中的对象名：

- N1 应指向 `PurchaseOrder`；
- N2 应指向 `Member`；
- N3 应指向 `Inventory`。

如果操作因为语法错误、约束冲突、对象不存在或其他非权限原因失败，则输出 `[FAIL]` 并打印实际错误号和错误信息。这样可以证明越权操作确实是被权限系统拒绝，而不是仅仅“没有执行成功”。

## N1 销售店员修改采购订单

```
PurchaseOrder
```

预期由于没有相应 `UPDATE` 权限而失败。

# 十一、会员权限的阶段性处理

在业务设计中，会员可以查看自己的订单和预订信息。

但当前第四周没有直接为会员创建 SQL Server 数据库角色。

原因是简单授予：

```
SalesOrder
PresaleReservation
```

表级查询权限后，会员可能获得查看其他会员数据的能力，与“只能访问本人数据”的业务要求冲突。

因此当前阶段将会员视为应用层业务角色：

```
会员
→ 后续通过应用程序或更细粒度访问机制访问本人数据
```

而不是：

```
会员
→ 直接登录数据库并查询基础表
```

第四周 SQL Server 权限设计主要针对店铺内部员工。

# 十二、阶段复现与重复运行

第一阶段完整复现统一按照：

```
00_create_database.sql
→ 01_create_tables.sql
→ 02_insert_sample_data.sql
→ 03_crud.sql
→ 04_query.sql
→ 05_view.sql
→ 06_constraint.sql
→ 07_role.sql
```

执行。`00` 在数据库不存在时创建数据库、存在时直接复用；`01` 会删除本项目已有视图和业务表并按依赖关系重新建表，因此完整执行链可以在已有数据库上再次运行并回到确定的样例初始状态。`05` 使用 `CREATE OR ALTER VIEW`，`06` 的补充约束带存在性判断，`07` 的角色、测试用户和角色成员关系也带存在性判断或可重复授权逻辑。

这里的重复运行是课程实验的“完整重建”语义：重新执行 `01` 会清空当前业务表数据。若只是希望保留已有业务数据，不应从 `01` 开始重建。

# 十四、本周阶段结论

第四周没有继续扩大数据库业务规模，而是在已有关系模式和样例数据基础上，将数据库从“能够保存和修改数据”进一步扩展为：

```
能够回答经营问题
        ↓
能够复用常见统计结果
        ↓
能够拒绝已由约束覆盖的典型非法记录
        ↓
能够限制不同角色对主要对象和字段的操作范围
```

多表查询验证了销售、商品、会员、库存、IP、预售等业务数据之间的关联能够支持实际经营分析。

统计视图将部分高频查询封装为稳定的数据访问方式。

完整性实验通过合法和非法数据正反例，验证了当前已由 `CHECK`、`UNIQUE`、`FOREIGN KEY` 和复合外键覆盖的数据规则能够实际发挥作用，并补齐了若干状态、时间和预售身份一致性约束。反例测试同时核对实际错误号和对应约束名，避免把其他原因造成的执行失败误判为测试通过。

权限实验将现实经营角色进一步映射为 SQL Server 数据库角色，通过最小权限授权和正常/越权测试，验证了不同员工在当前对象级、列级权限范围内能够完成典型操作，并会被拒绝访问未授权对象或字段。复杂状态迁移和跨表业务规则将在后续数据库编程与事务阶段继续收紧。越权测试进一步核对 SQL Server 权限拒绝错误及目标对象，确保测试失败原因与预期一致。

因此，目前第四周“连接、视图、完整性与授权”的主体业务工作已经形成完整闭环。
