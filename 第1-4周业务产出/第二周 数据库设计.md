# 二次元周边商品店——第二周关系模式设计

## 一、设计范围与基本约定

本项目为一家小型线下二次元周边商品店。数据库主要管理商品、商品库存、会员、员工、销售订单、预售、供应商、采购及补货等经营数据。

在第一周业务需求基础上，为控制数据库项目复杂度，本阶段采用以下三项简化假设：

1. **一个商品最多属于一个 IP，并最多对应一个具体角色。**
   商品可以只对应 IP 而不对应具体角色，例如群像商品；无明确 IP 或角色的商品，相应字段允许为 NULL。
2. **一次预售预订作为一个整体进行处理。**
   暂不支持部分取消或部分提货。例如会员预订 3 件商品时，不考虑只取消其中 1 件或只提取其中 2 件的情况。
3. **一条预售预订最终最多对应一笔预售提货销售订单。**
   暂不考虑一次结账同时提取多个不同预售活动商品的情况。

此外，普通现货销售和预售最终提货统一进入销售订单系统；普通补货和预售采购统一进入采购订单系统。

### 候选码

```
(ip_id, character_name)
```

即一个 IP 内不允许出现两个相同名称的角色。

为了保证商品中的 `ip_id` 与 `character_id` 能够进行组合一致性检查，后续实现时还保留：

```
UNIQUE(character_id, ip_id)
```

### 关系模式

```
CharacterInfo(
    character_id PK,
    ip_id FK → AnimeIP.ip_id,
    character_name,
    UNIQUE(ip_id, character_name),
    UNIQUE(character_id, ip_id)
)
```

### 样例元组

| character_id | ip_id | character_name |
| ------------ | ----- | -------------- |
| 1            | 1     | 甘雨           |
| 2            | 1     | 派蒙           |
| 3            | 2     | 三月七         |

```
PENDING    尚未正式销售
ON_SALE    正常销售
STOPPED    停止销售
```

### IP与角色一致性规则

允许：

```
ip_id = NULL，character_id = NULL
```

表示无明确作品和角色。

允许：

```
ip_id = 原神，character_id = NULL
```

表示原神群像或没有具体角色归属的商品。

允许：

```
ip_id = 原神，character_id = 甘雨
```

但是不允许：

```
ip_id = 原神，character_id = 三月七
```

也不允许：

```
ip_id = NULL，character_id = 甘雨
```

因此需要满足：

```
character_id IS NULL
OR
ip_id IS NOT NULL
```

如果角色不为 NULL，则：

```
(Product.character_id, Product.ip_id)
```

必须对应：

```
CharacterInfo(character_id, ip_id)
```

中的同一条角色记录。

### 关系模式

```
Product(
    product_id PK,
    product_code UNIQUE,
    product_name,
    category_id FK → ProductCategory.category_id,
    ip_id FK → AnimeIP.ip_id NULL,
    character_id FK → CharacterInfo.character_id NULL,
    sale_price,
    product_status,
    created_at,

    FK(character_id, ip_id)
      → CharacterInfo(character_id, ip_id)
)
```

# 四、库存

## 4.1 Inventory 库存表

一个商品在当前单门店经营模式下最多对应一条当前库存记录，因此数据库关系为：

```
Product : Inventory = 1 : 0..1
```

正常经营流程中，可经营商品会初始化对应的库存记录；当前表结构通过 `Inventory.product_id` 的主键保证同一商品不会出现多条当前库存记录。

### 字段定义

| 字段          | 类型      | NULL | 默认值/域 | 键               | 含义                         |
| ------------- | --------- | ---- | --------- | ---------------- | ---------------------------- |
| product_id    | INT       | 否   | —         | PK、FK → Product | 对应商品                     |
| on_hand_qty   | INT       | 否   | 0，>=0    | —                | 当前实际在库数量             |
| reserved_qty  | INT       | 否   | 0，>=0    | —                | 已到货但为预售顾客预留的数量 |
| reorder_point | INT       | 否   | 0，>=0    | —                | 补货警戒值                   |
| updated_at    | DATETIME2 | 否   | 当前时间  | —                | 库存记录更新时间，由库存修改语句同步维护 |

库存应满足：

```
0 <= reserved_qty <= on_hand_qty
```

不单独保存可销售库存字段。

可销售库存由：

```
available_qty = on_hand_qty - reserved_qty
```

计算得到。

### 关系模式

```
Inventory(
    product_id PK FK → Product.product_id,
    on_hand_qty,
    reserved_qty,
    reorder_point,
    updated_at
)
```

### 样例元组

| product_id | on_hand_qty | reserved_qty | reorder_point |
| ---------- | ----------- | ------------ | ------------- |
| 1          | 8           | 0            | 5             |
| 2          | 5           | 0            | 4             |
| 3          | 2           | 0            | 3             |

例如商品 P003：

```
实际库存 = 2
预留库存 = 0
可销售库存 = 2 - 0 = 2
```

# 八、销售订单

## 8.1 SalesOrder 销售订单表

普通现货销售和完成提货后的预售销售统一记录在此表中。

普通顾客购买时不要求建立顾客档案，因此：

```
member_id = NULL
```

会员购买时填写对应会员。

### 字段定义

| 字段           | 类型        | NULL | 默认值/域 | 键                      | 含义             |
| -------------- | ----------- | ---- | --------- | ----------------------- | ---------------- |
| order_id       | INT         | 否   | 正整数    | PK                      | 销售订单内部编号 |
| order_no       | VARCHAR(20) | 否   | —         | UNIQUE候选码            | 销售订单业务编号 |
| order_type     | VARCHAR(20) | 否   | —         | 枚举                    | 销售类型         |
| member_id      | INT         | 是   | NULL      | FK → Member             | 购买会员         |
| cashier_id     | INT         | 否   | —         | FK → Employee           | 经办销售店员     |
| reservation_id | INT         | 是   | NULL      | FK → PresaleReservation | 对应预售记录     |
| order_time     | DATETIME2   | 是   | NULL      | —                       | 实际完成交易时间 |
| order_status   | VARCHAR(20) | 否   | CREATED   | 枚举                    | 订单状态         |

不单独保存订单总金额。

订单总金额通过：

```
SUM(SalesOrderItem.quantity × SalesOrderItem.unit_price)
```

计算。

这样可以避免订单总金额和订单明细发生数据不一致。

### order_type 域

```
SPOT       普通现货销售
PRESALE    预售提货销售
```

### order_status 域

```
CREATED
COMPLETED
CANCELLED
```

新订单首先：

```
CREATED
```

完成库存检查、商品明细和结账后变成：

```
COMPLETED
```

此时 `order_time` 必须记录实际完成交易时间；未完成的 `CREATED` 或 `CANCELLED` 订单不记录完成交易时间。

失败或取消则：

```
CANCELLED
```

### 普通现货订单规则

```
order_type = SPOT
reservation_id = NULL
member_id 可以为 NULL
```

### 预售提货订单规则

```
order_type = PRESALE
reservation_id 不为 NULL
member_id 不为 NULL
```

一条预订最多对应一个最终预售提货订单，因此预售类型订单中的 `reservation_id` 应具有唯一性。

同时，预售提货订单中的 `member_id` 必须与该 `reservation_id` 所对应预订记录的会员一致。实现时使用 `(reservation_id, member_id)` 复合外键进行校验。

### 关系模式

```
SalesOrder(
    order_id PK,
    order_no UNIQUE,
    order_type,
    member_id FK → Member.member_id NULL,
    cashier_id FK → Employee.employee_id,
    reservation_id FK → PresaleReservation.reservation_id NULL,
    order_time,
    order_status,

    FK(reservation_id, member_id)
      → PresaleReservation(reservation_id, member_id),
    UNIQUE(reservation_id)
)
```

其中 `reservation_id` 为 NULL 的普通订单不受“一条预订一笔订单”规则影响。

### 样例元组

| order_id | order_no | order_type | member_id | cashier_id | reservation_id | order_time       | order_status |
| -------- | -------- | ---------- | --------- | ---------- | -------------- | ---------------- | ------------ |
| 1        | SO001    | SPOT       | NULL      | 1          | NULL           | 2026-09-22 14:30 | COMPLETED    |

# 九、预售业务

## 9.1 PresaleActivity 预售活动表

商品本身不划分为“预售商品”和“现货商品”。

是否开展预售由 `PresaleActivity` 表示，因此一个商品以后可以开展多次预售活动。

### 字段定义

| 字段                 | 类型          | NULL | 默认值/域    | 键            | 含义                             |
| -------------------- | ------------- | ---- | ------------ | ------------- | -------------------------------- |
| presale_id           | INT           | 否   | 正整数       | PK            | 预售活动内部编号                 |
| presale_code         | VARCHAR(20)   | 否   | —            | UNIQUE候选码  | 预售活动业务编号                 |
| product_id           | INT           | 否   | —            | FK → Product  | 预售商品                         |
| start_time           | DATETIME2     | 否   | —            | —             | 预售开始时间                     |
| end_time             | DATETIME2     | 否   | > start_time | —             | 预售截止时间                     |
| presale_unit_price   | DECIMAL(10,2) | 否   | >0           | —             | 本次预售商品单价                 |
| deposit_per_unit     | DECIMAL(10,2) | 否   | >=0          | —             | 每件商品要求的订金               |
| pickup_deadline      | DATETIME2     | 是   | NULL         | —             | 最晚提货期限                     |
| decision_demand_qty  | INT           | 是   | NULL，>=0    | —             | 店长做采购决策时的有效预订需求量 |
| extra_stock_qty      | INT           | 否   | 0，>=0       | —             | 店长决定的额外备货数量           |
| planned_purchase_qty | INT           | 是   | NULL，>=0    | —             | 店长最终计划采购数量             |
| created_by           | INT           | 否   | —            | FK → Employee | 创建预售活动的管理员             |
| presale_status       | VARCHAR(20)   | 否   | PLANNED      | 枚举          | 当前预售状态                     |

### presale_status 域

```
PLANNED
OPEN
CLOSED
PURCHASING
ARRIVED
FINISHED
```

日期与金额要求：

```
start_time < end_time

pickup_deadline IS NULL
OR pickup_deadline > end_time

0 <= deposit_per_unit <= presale_unit_price
```

`pickup_deadline` 在商品实际到货并开放提货后确定。第一阶段先保证其不早于预售结束时间；与实际到货时间的进一步联动留待后续事务阶段处理。

### 三个采购决策字段的含义

例如：

```
预售截止时有效预订 = 40
店长额外备货 = 10
最终计划采购 = 50
```

分别保存：

```
decision_demand_qty = 40
extra_stock_qty = 10
planned_purchase_qty = 50
```

`decision_demand_qty` 是经营决策发生时的历史快照，因此即使之后有人取消预订，也不修改这一历史值。

### 关系模式

```
PresaleActivity(
    presale_id PK,
    presale_code UNIQUE,
    product_id FK → Product.product_id,
    start_time,
    end_time,
    presale_unit_price,
    deposit_per_unit,
    pickup_deadline,
    decision_demand_qty,
    extra_stock_qty,
    planned_purchase_qty,
    created_by FK → Employee.employee_id,
    presale_status
)
```

| ---------- | ------------ | ---------- | ---------- | ---------- | ------ | -------- | --------------- | ------------------- | --------------- | -------------------- | ---------- | -------- |
| 1          | PS001        | 3          | 2026-09-01 | 2026-09-15 | 129.00 | 30.00    | 2026-10-10      | 2                   | 1               | 3                    | 3          | FINISHED |

## 9.2 PresaleReservation 预订记录表

一个会员可以参加多个预售。

同一会员也允许在同一次预售中留下多条历史预订记录，例如：

```
第一次预订
→ 截止前取消
→ 后来重新预订
```

因此：

```
(presale_id, member_id)
```

**不设置为候选码。**

每条预订通过独立的 `reservation_id` 和 `reservation_no` 标识。

### 字段定义

| 字段               | 类型          | NULL | 默认值/域 | 键                   | 含义               |
| ------------------ | ------------- | ---- | --------- | -------------------- | ------------------ |
| reservation_id     | INT           | 否   | 正整数    | PK                   | 预订内部编号       |
| reservation_no     | VARCHAR(20)   | 否   | —         | UNIQUE候选码         | 预订业务编号       |
| presale_id         | INT           | 否   | —         | FK → PresaleActivity | 所属预售活动       |
| member_id          | INT           | 否   | —         | FK → Member          | 预订会员           |
| quantity           | INT           | 否   | >0        | —                    | 预订数量           |
| reserved_at        | DATETIME2     | 否   | 当前时间  | —                    | 预订时间           |
| deposit_paid       | DECIMAL(10,2) | 否   | >=0       | —                    | 已实际支付订金总额 |
| deposit_refunded   | DECIMAL(10,2) | 否   | 0，>=0    | —                    | 已退还订金金额     |
| reservation_status | VARCHAR(20)   | 否   | ACTIVE    | 枚举                 | 当前预订状态       |
| cancelled_at       | DATETIME2     | 是   | NULL      | —                    | 实际取消时间       |

不单独保存：

```
balance_paid
pickup_time
```

原因：

预售完成时商品完整成交价格已经进入：

```
SalesOrderItem.unit_price
```

预售实际完成提货时间则由：

```
SalesOrder.order_time
```

记录。

这样可以避免同一笔交易的信息在两个位置重复保存。

### reservation_status 域

```
ACTIVE
CANCELLED
PICKED_UP
EXPIRED
```

其中：

```
ACTIVE
   ├── CANCELLED
   ├── PICKED_UP
   └── EXPIRED
```

`CANCELLED` 状态必须记录 `cancelled_at`，其他状态下 `cancelled_at` 保持为空。

取消发生在预售截止前还是截止后，不增加不同状态，而通过：

```
cancelled_at
```

与：

```
PresaleActivity.end_time
```

比较得到。

### 订金规则

截止前取消：

```
reservation_status = CANCELLED
cancelled_at <= end_time
deposit_refunded = deposit_paid
```

截止后取消：

```
reservation_status = CANCELLED
cancelled_at > end_time
deposit_refunded = 0
```

超过最晚提货期限：

```
reservation_status = EXPIRED
deposit_refunded = 0
```

第一阶段数据库保存取消时间、状态和退款金额，并保证退款金额的基本数值合法性；“截止前全额退、截止后不退”需要跨表比较预售截止时间，统一列入后续数据库编程与事务阶段实现。

### 关系模式

```
PresaleReservation(
    reservation_id PK,
    reservation_no UNIQUE,
    presale_id FK → PresaleActivity.presale_id,
    member_id FK → Member.member_id,
    quantity,
    reserved_at,
    deposit_paid,
    deposit_refunded,
    reservation_status,
    cancelled_at,
    UNIQUE(reservation_id, member_id)  -- 作为 SalesOrder 复合外键的引用键
)
```

### 样例元组

| reservation_id | reservation_no | presale_id | member_id | quantity | reserved_at | deposit_paid | deposit_refunded | reservation_status | cancelled_at |
| -------------- | -------------- | ---------- | --------- | -------- | ----------- | ------------ | ---------------- | ------------------ | ------------ |
| 1              | R001           | 1          | 1         | 1        | 2026-09-05  | 30.00        | 0.00             | PICKED_UP          | NULL         |
| 2              | R002           | 1          | 2         | 1        | 2026-09-06  | 30.00        | 0.00             | CANCELLED          | 2026-09-18   |
| 3              | R003           | 2          | 2         | 1        | 2026-09-22  | 20.00        | 0.00             | ACTIVE             | NULL         |

R002 所属预售活动截止时间为：

```
2026-09-15
```

而取消时间为：

```
2026-09-18
```

所以属于截止后取消，订金不退：

```
deposit_refunded = 0
```

# 十、采购业务

## 10.1 PurchaseOrder 采购订单表

普通库存补货和预售采购统一使用采购订单，通过：

```
purchase_type
```

进行区分。

### 字段定义

| 字段             | 类型        | NULL | 默认值/域 | 键                   | 含义               |
| ---------------- | ----------- | ---- | --------- | -------------------- | ------------------ |
| purchase_id      | INT         | 否   | 正整数    | PK                   | 采购订单内部编号   |
| purchase_no      | VARCHAR(20) | 否   | —         | UNIQUE候选码         | 采购业务编号       |
| supplier_id      | INT         | 否   | —         | FK → Supplier        | 供应商             |
| purchase_type    | VARCHAR(20) | 否   | —         | 枚举                 | 采购类型           |
| presale_id       | INT         | 是   | NULL      | FK → PresaleActivity | 对应预售活动       |
| created_by       | INT         | 否   | —         | FK → Employee        | 创建采购订单的员工 |
| order_time       | DATETIME2   | 否   | 当前时间  | —                    | 向供应商下单时间   |
| expected_arrival | DATETIME2   | 是   | NULL      | —                    | 预计到货时间       |
| received_time    | DATETIME2   | 是   | NULL      | —                    | 实际完成验收时间   |
| received_by      | INT         | 是   | NULL      | FK → Employee        | 实际验收员工       |
| purchase_status  | VARCHAR(30) | 否   | CREATED   | 枚举                 | 采购订单状态       |

### purchase_type 域

```
RESTOCK
PRESALE
```

### purchase_status 域

```
CREATED
ORDERED
PARTIAL_RECEIVED
RECEIVED
CANCELLED
```

### 业务规则

预售采购：

```
purchase_type = PRESALE
→ presale_id 不应为 NULL
```

普通补货：

```
purchase_type = RESTOCK
→ 正常业务流程中 presale_id = NULL
```

当前第一阶段只强制 `PRESALE` 类型必须关联预售活动；`RESTOCK` 类型是否禁止填写 `presale_id` 暂不额外增加约束。

采购尚未完成验收时：

```
received_time = NULL
received_by = NULL
```

完成验收后：

```
purchase_status = RECEIVED
received_time 不为 NULL
received_by 不为 NULL
```

同时保持基本时间顺序：

```
expected_arrival IS NULL OR expected_arrival >= order_time
received_time IS NULL OR received_time >= order_time
```

当前项目不单独建立“补货申请表”。

采用的简化流程为：

```
库存低于补货警戒值
→ 库存管理员发现库存不足
→ 店长决定采购数量
→ 直接形成 RESTOCK 类型采购订单
```

采购订单表示最终实际执行的补货决策。

### 关系模式

```
PurchaseOrder(
    purchase_id PK,
    purchase_no UNIQUE,
    supplier_id FK → Supplier.supplier_id,
    purchase_type,
    presale_id FK → PresaleActivity.presale_id NULL,
    created_by FK → Employee.employee_id,
    order_time,
    expected_arrival,
    received_time,
    received_by FK → Employee.employee_id NULL,
    purchase_status
)
```

### 样例元组

| purchase_id | purchase_no | supplier_id | purchase_type | presale_id | created_by | order_time | expected_arrival | received_time | received_by | purchase_status |
| ----------- | ----------- | ----------- | ------------- | ---------- | ---------- | ---------- | ---------------- | ------------- | ----------- | --------------- |
| 1           | PO001       | 1           | PRESALE       | 1          | 3          | 2026-09-16 | 2026-09-25       | 2026-09-25    | 2           | RECEIVED        |
| 2           | PO002       | 2           | RESTOCK       | NULL       | 3          | 2026-09-20 | 2026-09-30       | NULL          | NULL        | ORDERED         |

# 十一、主要业务流程与数据表对应关系

## 11.1 普通现货销售

```
Product
  ↓
查询 Inventory
  ↓
计算 available_qty
  ↓
创建 SalesOrder(CREATED)
  ↓
创建 SalesOrderItem
  ↓
确认库存和结账
  ↓
SalesOrder → COMPLETED
  ↓
Inventory.on_hand_qty 减少
```

例如：

```
on_hand_qty = 10
reserved_qty = 3
```

则：

```
available_qty = 7
```

普通顾客购买 2 件后：

```
on_hand_qty = 8
reserved_qty = 3
available_qty = 5
```

------

## 11.2 预售正常完成

```
Product
  ↓
PresaleActivity
  ↓
PresaleReservation
  ↓
预售截止
  ↓
统计有效需求
  ↓
店长决定额外备货
  ↓
PurchaseOrder(PRESALE)
  ↓
PurchaseOrderItem
  ↓
供应商到货
  ↓
库存管理员验收
  ↓
Inventory.on_hand_qty 增加
  ↓
有效预订对应数量进入 reserved_qty
  ↓
会员到店提货
  ↓
SalesOrder(PRESALE)
  ↓
SalesOrderItem
  ↓
订单 COMPLETED
  ↓
on_hand_qty 与 reserved_qty 同时减少
  ↓
Reservation → PICKED_UP
```

------

## 11.3 预售采购后取消

例如采购：

```
有效预订需求 = 2
额外备货 = 1
计划采购 = 3
```

采购完成后其中一名会员取消。

商品最终到货 3 件时，只剩 1 件需要为有效预订保留：

```
on_hand_qty += 3
reserved_qty += 1
```

因此：

```
available_qty = 3 - 1 = 2
```

这两件普通现货分别来源于：

```
1件原计划额外备货
+
1件采购后取消产生的剩余商品
```

无需建立“预售库存”和“普通库存”两套独立库存。

------

## 11.4 超过最晚提货期限

假设：

```
on_hand_qty = 5
reserved_qty = 2
```

其中一个预订超过最晚提货期限。

则：

```
Reservation → EXPIRED
```

商品仍在店内，所以：

```
on_hand_qty = 5
```

但不再为该会员保留：

```
reserved_qty: 2 → 1
```

因此：

```
available_qty:
5 - 2 = 3
→
5 - 1 = 4
```

该商品自然重新进入普通现货销售。

------

## 11.5 普通补货

```
商品持续销售
  ↓
Inventory可销售库存下降
  ↓
达到或低于reorder_point
  ↓
库存管理员发现库存不足
  ↓
店长决定采购数量
  ↓
PurchaseOrder(RESTOCK)
  ↓
PurchaseOrderItem
  ↓
供应商到货
  ↓
库存管理员验收
  ↓
received_by / received_time记录
  ↓
Inventory.on_hand_qty增加
```

# 十三、主要设计原则与理由

## 13.1 商品不设置“是否预售”字段

商品本身不是永久的“预售商品”。

是否预售由：

```
PresaleActivity
```

表达。

因此同一个商品可以经历：

```
首次预售
→ 到货
→ 作为普通现货销售
→ 以后再次开展新的预售活动
```

------

## 13.2 普通顾客不建立独立顾客记录

非会员顾客完成现货购买时：

```
SalesOrder.member_id = NULL
```

只有注册会员才进入：

```
Member
```

避免保存没有后续经营意义的临时顾客资料。

------

## 13.3 预售和现货最终统一形成销售记录

完成提货的预售交易和普通现货交易均进入：

```
SalesOrder
SalesOrderItem
```

以后统计：

- 商品销量；
- IP销量；
- 类别销量；
- 会员历史消费；
- 总销售额；

均可以使用统一的数据来源。

------

## 13.4 历史成交价格单独保存

```
Product.sale_price
```

表示当前售价。

```
SalesOrderItem.unit_price
```

表示历史交易实际成交价格。

商品以后即使调价，也不会改变历史订单。

------

## 13.5 不保存可直接计算的销售订单总金额

订单金额可以通过：

```
SUM(quantity × unit_price)
```

计算。

因此不在：

```
SalesOrder
```

中重复保存 `total_amount`，避免订单明细与订单总金额发生矛盾。

------

## 13.6 库存只保存基本状态

保存：

```
on_hand_qty
reserved_qty
```

不保存：

```
available_qty
```

因为：

```
available_qty
=
on_hand_qty - reserved_qty
```

可以随时计算。

------

## 13.7 预售预订不重复保存最终交易信息

`PresaleReservation` 负责记录：

```
会员预订
订金
取消
预订状态
```

真正完成提货以后：

```
成交价格 → SalesOrderItem
交易时间 → SalesOrder
```

因此不再在 `PresaleReservation` 重复保存：

```
balance_paid
pickup_time
```

------

## 13.8 同一会员允许在同一活动中留下多条历史预订

不设置：

```
UNIQUE(presale_id, member_id)
```

原因是业务可能出现：

```
预订
→ 截止前取消
→ 后来重新预订
```

每一次业务记录均应保留下来。

------

## 13.9 IP和角色必须保持一致

因为 Product 同时直接保存：

```
ip_id
character_id
```

所以数据库必须防止：

```
原神 + 三月七
```

这样的组合。

角色存在时，其：

```
(character_id, ip_id)
```

必须共同引用同一条 `CharacterInfo` 记录。

------

## 13.10 普通补货与预售采购使用统一采购结构

均使用：

```
PurchaseOrder
PurchaseOrderItem
```

通过：

```
purchase_type
```

区分：

```
RESTOCK
PRESALE
```

减少两套相似采购表和采购逻辑。

------

# 十五、第二周阶段结论

本阶段共设计 15 张数据表。

数据库以商品为核心，将商品类别、IP和角色作为基础资料；将库存作为商品的当前经营状态；通过销售订单和订单明细记录普通销售及完成提货的预售交易；通过预售活动和预订记录表示预售业务；通过采购订单和采购明细统一表示预售采购与普通库存补货。

各核心业务对象均具有明确主码，并通过候选码保证业务编号等属性的唯一性，通过外码建立商品、会员、订单、预售、采购、供应商和员工之间的联系。

当前设计能够支持后续：

- 数据库建表和样例数据导入；
- 商品、库存、订单和采购 CRUD；
- 多表连接查询；
- 商品、IP和类别销量统计；
- 会员消费统计；
- 库存状态查询；
- 预售需求统计；
- 供应商及采购统计；
- 数据完整性约束；
- 不同经营角色的权限划分；
- 后续基于历史销售数据的销量分析和补货决策。

在当前阶段暂不纳入物流、退换货、复杂营销、财务会计、多门店经营、自动采购算法以及复杂会员画像等业务。
