# 后续阶段待实现业务规则

本文件记录第一阶段已经明确业务含义、但不适合仅通过当前的 `CHECK`、`UNIQUE`、`FOREIGN KEY` 或列级权限强制完成的规则。

第一阶段的样例数据和业务流程按这些规则组织；后续结合数据库应用、存储过程、触发器和事务逐步实现。这样既保留当前关系模式的简洁性，也为后续阶段留下明确的实现目标。

## 一、预售预订与取消

| 待实现规则 | 当前阶段处理 | 后续建议 |
| --- | --- | --- |
| 会员只能在预售开放期间预订 | 样例数据遵守，未跨表校验 `reserved_at` 与活动起止时间/状态 | 通过创建预订的存储过程统一校验 |
| 实际订金应与 `quantity × deposit_per_unit` 对应 | 当前分别保存数量和实付订金 | 在预订过程中计算并写入 |
| 截止前取消全额退订金、截止后取消不退 | 当前保存取消时间和退款金额，并保证基本数值合法 | 取消预订过程跨表比较 `cancelled_at` 与 `end_time` 后确定退款 |
| `PICKED_UP` 状态应对应真实完成的预售销售订单 | 当前状态与订单由业务流程保持一致 | 提货事务中同时完成订单与预订状态更新 |

## 二、预售提货与预售采购

| 待实现规则 | 当前阶段处理 | 后续建议 |
| --- | --- | --- |
| 预售销售订单商品必须与预订所属活动商品一致 | 当前已保证订单会员与预订会员一致，但商品仍需跨表核对 | 提货存储过程统一生成订单明细 |
| 预售销售数量必须等于该次预订数量，保持整体提货 | 样例数据遵守 | 提货事务校验并一次性完成 |
| 预售成交价应使用该活动的预售价 | 当前 `SalesOrderItem.unit_price` 独立保存历史成交价 | 提货时自动取 `presale_unit_price` |
| 预售采购应在预售截止后形成 | 样例业务流程遵守 | 创建预售采购时校验活动状态与截止时间 |
| `PRESALE` 采购明细商品必须与对应预售活动商品一致 | 当前采购订单可关联活动，明细商品尚未跨表强制匹配 | 采购过程统一生成/校验采购明细 |
| `RESTOCK` 类型是否严格禁止填写 `presale_id` | 当前正常流程填写 `NULL`，第一阶段只强制 `PRESALE` 必须关联活动 | 后续流程固定类型与关联规则，必要时再收紧数据库约束 |
| 采购订单状态应与各明细 `received_qty` 一致 | 当前分别记录订单状态和明细验收数量 | 验收入库事务根据明细统一推进采购状态 |

## 五、后续实现顺序建议

优先把规则放入对应业务事务，而不是为每条规则单独堆叠触发器：

1. **预售预订/取消过程**：处理活动时间、订金和退款；
2. **销售完成/预售提货事务**：处理订单、订单明细、预订状态和库存；
3. **采购验收入库事务**：处理验收数量、采购状态和库存；
4. **状态与角色校验**：在上述过程入口统一限制合法操作者和状态迁移；
5. **会员应用访问**：在后续数据库应用中实现本人数据范围控制。
